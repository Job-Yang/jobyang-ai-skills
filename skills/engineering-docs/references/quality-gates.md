# 质量门禁

## 门禁状态

每道门只有四种结果：

| 状态 | 机器值 | 含义 | 后续动作 |
| --- | --- | --- | --- |
| 通过 | `pass` | 已有足够证据满足要求 | 进入下一道门 |
| 退回 | `revise` | 材料足够，但当前文档没有写对或写全 | 修改后重检 |
| 不适用 | `not_applicable` | 当前任务确实不存在这类问题 | 写明理由后跳过 |
| 阻塞 | `blocked` | 缺少会改变核心决定的输入或权限 | 保持草案，补证或找责任人 |

`not_applicable` 必须写理由。任何阻塞项存在时，文档不能进入 `in_review`、`decided`、`implementable` 或 `implemented`。

## 裁决口径

### 足够证据

关键事实同时满足：

- 能回到原始来源。
- 适用范围和时间、版本或分支明确。
- 能直接支持结论，或写清中间推导。
- 与其他关键证据没有未解释的冲突。

非关键细节可以作为假设继续使用。

### 高风险

命中以下任意情况，默认按高风险处理：

- 不可逆数据变更。
- 资金和交易正确性。
- 权限、鉴权和隐私。
- 核心可用性。
- 失败后影响无法快速隔离。

作者先识别，决定责任人或指定领域评审人最终裁决。存在分歧时从严。

### 责任分工

- 技能：识别关键事实，检查证据，暴露缺口。
- 事实源负责人：关闭事实冲突。
- 决定责任人：确认现有证据足以支持决定，并接受方案和代价。
- 领域评审人：负责高风险专项结论。

对应负责人无法确认，争议保持为阻塞项。

## 门禁清单

### G0 文档契约门

通过条件：

- 能一句话说明谁基于什么，对什么问题作出什么决定或动作。
- 文档标题、类型、状态、作者和范围明确。
- 主要读者和期望动作明确。

常见失败：

- 只知道“写份方案”，不知道要推动什么决定。
- 读者和实施者混在一起，没有主读者。
- 范围只写“做什么”，没有说明不做什么。

### G1 事实证据门

通过条件：

- 现状、主要链路、接口、数据和关键约束有可追溯依据。
- 事实、推导、假设没有混写。
- 证据冲突已经关闭，或明确成为阻塞项。

硬裁决：

> 关键事实不可证时，G1 必须为 `blocked`。只交付已确认事实、候选假设和最少追问。

常见失败：

- 凭服务名或目录名猜调用链。
- 使用已经过期的方案说明当前系统。
- 代码中存在某分支，就断言本次运行一定命中。
- 把模型常识写成当前工程事实。

### G2 问题成立门

通过条件：

- 问题描述独立于推荐解法。
- 当前状态、目标状态、差距和影响清楚。
- 能说明保持现状的结果。

常见失败：

- 用“引入缓存”“上微服务”代替问题。
- 背景只复制需求文档，没有工程判断。
- 没有影响，也没有不处理的后果。

### G3 目标边界门

通过条件：

- 每个目标都有可观察的验收证据。
- 会影响决定或实施的范围边界已经说清。
- 业务、技术、组织和时间约束清楚。

常见失败：

- 只写“提升稳定性”“优化体验”。
- 为了套模板硬写一节“非目标”，内容只是空泛否定。
- 验收口径到实施后才决定。

### G4 方案取舍门

存在真实选择时，通过条件：

- 候选都真实可行。
- 使用同一组、从目标和约束推导出的比较标准。
- 推荐结论、拒绝理由和接受的代价明确。

方案唯一时：

- 写明哪些约束收敛了方案空间。
- G4 标为 `not_applicable`。
- `reason` 不得为空。

硬裁决：

> 存在真实选择，却无法解释比较标准、替代方案和代价时，G4 为 `revise`。

常见失败：

- 只有推荐方案，没有说明其他合理路径。
- 用明显不可行的方案陪跑。
- 优缺点与最后选择没有关系。
- 使用“业界常用”“扩展性好”等空判断。

### G5 设计闭环门

通过条件：

- 系统边界和职责清楚。
- 主流程能闭环。
- 重要异常、超时、重试、并发和边界有处理办法。
- 接口、数据、状态和兼容契约明确。
- 改造落点足以支撑任务拆分。
- 结构、时序、状态、数据或排期关系仅靠文字难以稳定理解时，已经选择合适视图；不需要图时没有为模板凑图。

常见失败：

- 只有架构名词，没有职责和交互。
- 只写正常流程。
- 堆满代码和接口，却说不清哪个决定依赖这些细节。

### G6 影响风险门

通过条件：

- 已检查受影响入口、调用方、上下游、数据和存量能力。
- 风险触发矩阵命中的项目都有结论。
- 公共逻辑变更有调用方和回归范围证据。

常见失败：

- 把新增能力当成零影响。
- 只看当前入口，不查复用方。
- 只写风险名称，没有触发条件和影响。

### G7 交付控制门

通过条件：

- 验证方法能证明目标和关键契约成立。
- 感知办法能在风险发生时发现它。
- 灰度、迁移和回退与风险相匹配。
- 失败后知道由谁执行什么止损动作。

硬裁决：

> 高风险改动缺少必要的验证、感知或止损办法时，G7 必须为 `blocked`，文档只能保持草案。

常见失败：

- 只写“充分测试”。
- 代码可回滚，但数据无法逆转。
- 使用随机灰度，破坏重试幂等。
- 有监控项，没有阈值、责任人和处置动作。

### G8 一致性门

通过条件：

- 正文、图、表、术语、接口和证据使用同一套事实。
- 现状和目标状态没有混写。
- 图中关系有名称和方向，抽象层级一致。
- 每张图有明确的问题、范围和状态，元素与关系能回到证据。
- 图源已在实际交付载体真实渲染，未发现箭头、连线、裁切和文字可读性问题；本地文件交付不需要在线平台账号。
- 流程图的分支条件、并行汇合、重试边界和终态与正文一致，未为布局改变控制语义。
- 定量图的单位、样本、时间、分母、聚合与尺度明确；关键数字可从源数据复算，缺测与合成数据如实标明。
- 甘特与里程碑共用有效计划；标注的关键路径有计算依据，不以颜色代替计算。

常见失败：

- 图里出现正文没有的系统。
- 同一字段、服务或状态使用多个名称。
- 图漂亮，但链路与代码或接口不符。
- 只检查 Mermaid、PlantUML 或 SVG 源码，没有看渲染结果。
- 同图混合系统、服务、类和部署节点，或混合现状与目标。

### G9 可读性门

通过条件：

- 摘要先给结论、关键依据、代价和阻塞项。
- 章节围绕读者的真实问题组织，标题本身有信息。
- 细节按需下钻，正文没有重复资料。
- 术语对目标读者足够清楚。
- 内部门禁、证据账本和文档契约没有泄漏到默认正文。
- 图放在它所支撑的判断附近，图前说明问题，图后给出结论；正文没有逐框复述。
- 正文、画板、幻灯片和打印按各自尺寸检查。正文缩放后的字和线可读，不能用大画布原图的可读性替代正文验收。
- 图按类型组织层级和视觉重点，颜色有第二条识别线索，数据轴与色标不误导读者。

常见失败：

- 读完整篇仍不知道推荐什么。
- 把模板的每个章节都填满。
- 同一判断在开头、正文和小结重复三次。
- 代码流水账代替业务和工程语言。
- 正文直接展示 G0 至 G12、完整证据账本或“文档契约”。

### G10 可执行门

通过条件：

- 研发能指出改哪里、依赖谁、先做什么。
- 测试能指出验什么、用什么证据判定。
- 评审人能指出主要代价和风险。

常见失败：

- 方案听起来合理，但无法拆任务。
- 只有远景架构，没有当前落点。
- 没有负责人和依赖关系。

### G11 生命周期门

通过条件：

- 作者、决定责任人、状态、更新时间和适用版本明确。
- 实现偏离和新事实出现时有状态回退规则。
- 旧决定不会被直接覆盖。
- 图源与文档一起版本化，记录适用范围、状态和最后核验时间。
- 图源和预览随正文以相对引用交付；在线发布地址不是唯一副本，跨平台转换后重新核对。

复检要求：

- 实现完成且核心决定未变，至少重跑 G1、G8 和 G11。
- 新事实可能改变决定，进入 `revalidation`，重跑 G1 至 G12。
- 没有复检记录，不能进入 `implemented`。

### G12 独立读者门

通过条件：

- 测试前已锁定标准答案。
- 独立读者只读取文档。
- 五个问题全部命中核心信息。
- 读者没有补出文档不存在的假设。

五个问题：

1. 现在的问题是什么，证据在哪里。
2. 最终建议做什么，为什么选择它。
3. 决定的适用边界是什么，接受了什么代价。
4. 具体改哪里，主要风险和依赖是什么。
5. 怎么证明实施正确，失败后怎么退。

测试失败时，记录问题、回答和暴露的缺口，返回对应门禁修改。G12 只证明可理解性，不证明技术事实正确。

## 风险触发矩阵

结构化记录中的机器值如下：

| 机器值 | 触发条件 | 必查控制 |
| --- | --- | --- |
| `public_interface` | 改公共接口、协议或数据结构 | 兼容范围、版本策略、调用方影响、迁移顺序 |
| `data_write` | 改数据写入、状态机或跨服务事务 | 幂等、一致性、重试补偿、数据回退 |
| `concurrency_async` | 改并发、缓存、队列或异步链路 | 顺序、重复、丢失、锁、容量和降级 |
| `security_privacy` | 涉及资金、鉴权、隐私和敏感数据 | 权限边界、审计、最小暴露、失败策略、专项评审 |
| `performance_capacity` | 涉及性能和容量目标 | 基线、目标、压测口径、瓶颈假设、观测指标 |
| `migration_refactor` | 涉及迁移、替换和重构 | 双跑、校验、切换条件、旧链路退出、回滚窗口 |
| `user_visible` | 改用户可见行为 | 异常体验、兼容版本、灰度范围、客服和运营感知 |
| `observability_ops` | 改监控、告警或运维流程 | 信号有效性、阈值依据、责任人、处置动作 |

没有命中的项目不为完整感硬写进正文。结构化门禁报告可以标为 `not_applicable`。

## 状态所需门禁

| 目标状态 | 必须关闭的门禁 | 其他要求 |
| --- | --- | --- |
| `draft` | 无 | 结构合法即可 |
| `in_review` | G0 至 G11 | 无阻塞项 |
| `decided` | G0 至 G11 | 决定责任人和接受时间明确 |
| `implementable` | G0 至 G12 | 无阻塞项；风险控制关闭 |
| `implemented` | G0 至 G12 | 有实现与复检证据 |
| `revalidation` | 无 | `review_from` 和复核原因明确 |
| `rejected` | 无 | 否决或撤回理由明确 |
| `superseded` | 无 | 替代文档明确 |

## 自动校验的边界

`scripts/engineering_docs.py` 可以检查：

- JSON 结构和枚举值。
- 门禁状态是否齐全。
- 目标状态所需门禁是否关闭。
- 关键字段、证据元数据和阻塞项。
- 风险触发项是否有对应控制。
- 已登记图示的类型、问题、范围、图源和事实来源是否完整。
- 进入可实施或已实施状态前，图示是否有真实渲染和复核证据。
- 状态流转是否合法。
- 默认 Markdown 是否仍有占位提示。
- 默认正文是否泄漏“证据账本”“质量门禁”“文档契约”或 G 编号。
- 独立读者答案是否锁定并记录结果。

脚本不能判断：

- 代码和系统事实是否真的正确。
- 方案是不是业务上最优。
- 图表是否忠实反映真实链路。
- 人工评审是否专业、充分。

机器校验通过，只表示记录具备接受评审的结构，不代表技术方案自动获批。

正文完成、本地图已验收和在线发布完成分别报告。可选发布权限缺失不推翻已经完成的本地内容验证；用户明确要求的目标平台交付仍保持未完成，不能把本地预览冒充已发布。
