# 图的交付与视觉语法

技术文档里的图要做到两件事：读者一眼看出重点和阅读顺序；作者和同事以后能改其源文件。

**本文只用于维护旧 `diagram_kit` 图。新图默认走 `archify-bridge.md`，不把本文的卡片原语和旧色板覆盖到新后端。**

## 交付什么

| 文件 | 作用 | 什么时候给 |
| --- | --- | --- |
| `arch.py` | 用 `scripts/diagram_kit.py` 写的生成脚本，改图改它 | 结构图、架构图、流程总览 |
| `arch.svg` | 旧后端矢量产物；是否恢复原生画板节点取决于导入器，不能直接保证 | 旧图矢量交付 |
| `arch.drawio` | 同图 draw.io 版，连线绑定节点 | 读者用 draw.io/Confluence/VS Code 时 |
| `seq.mmd` | Mermaid 源码 | 时序、状态、甘特、类图、思维导图 |
| `arch.png` | 预览，只用于自查或贴到不支持 SVG 的地方 | 不作唯一交付 |

不交付只有 PNG 的图。源文件平台中立，飞书/GitHub/draw.io/Notion 都是发布目标，任何一个不可用都不影响交付（见 `lark-publish.md`）。

## 画之前先选图型

本文是**结构图**（架构、容器、部署、数据流、流程）的视觉语法。时序、状态、ER、泳道等不要用卡片图硬画，先按 `diagram-selection.md` 选图型和工具。

## 画之前回答四个问题

1. 读者记住哪句话？写成标题。"稳定核心随仓库迁移，外围能力插拔"是标题；"系统架构图"不是。
2. 按什么顺序看？从上到下、从左到右，还是编号 1、2、3。
3. 重点是哪个元素？只有它用强调色。
4. 读者要找到什么？核心约束落在哪些部件就画出来（哪个存储唯一写入、哪步可回滚）；新增部分挂在已有系统哪里，已有系统也要出现，可压成灰色区域或一行标签。

## 按信息选版式

| 要表达 | 版式 | 要点 |
| --- | --- | --- |
| 核心稳定、外围可换 | 宿主在上、核心居中、外围在侧 | 区域分开，连线只画跨区关系 |
| 请求/数据流动 | 从左到右泳道，步骤编号 | 每条线写动词；异常用虚线或红色 |
| 分层依赖 | 分层 + 层间真实连线 | 只叠方块不连线，看不出谁调谁 |
| 中心协调多方 | 中心辐射 | 中心卡片最大，外围按职责分组 |
| 改造前后 | 左右对照，相同组件同位 | 只高亮真实变化 |
| 多方案比较 | 矩阵或表格 | 维度少于 3 直接用表 |
| 时序、状态、实体关系 | `render_templates` 的 `sequence` / `state_machine` / `er` | 不用卡片图硬画，见 `diagram-selection.md` |

现状和规划不画成同样式：规划用虚线边框 + 强调色并写进图例。图例每条说明要对全图成立——写了"灰色为已有"，新增元素就不能是灰的。

## 视觉语法

- **三级层次**：区域（浅灰底、标题左上）装卡片；卡片（白底、细边）写名称和一行说明；标签（胶囊）写属性。不要让区域和卡片长得一样。
- **标题图例**：左上标题写结论，副标题写范围和读法；图例只解释不直观的编码（虚线、颜色）。
- **旧引擎颜色**：`theme.json` 分别定义实体浅色面、轻边框、Group底色与边框、清楚的连接线。分类色可显式使用，状态色另有语义，不自动按编号轮换；不再让每个框都用同一重灰轮廓。
- **旧组件保留，旧配色退役**：`verdict_bar`、`category_card`、`status_pill`、`evidence_action_row` 仍可调用；结论条改用浅底深字，类别卡用中性或强调色，只有真实状态用状态色。旧主题名映射到统一主题，`theme="plain"` 保持灰阶。色值和来源见 `visual-design.md`、`doubao_style_tokens.md`。
- **连线**：实线=调用/数据，虚线=规划/反馈；关系不直观写动词标签；线不穿卡片、不压区域标题。
- **阅读路径**：有先后就用编号圆点，和正文步骤一致；栏内箭头方向统一，回流才逆向且用虚线。
- **标签轻重**：深色实心标签只给一类最要紧属性（如唯一写入方）。
- **结论卡**：可选。只有复杂结构图、而且图本身看不出结论时，底部放 2–3 张 `note`；能看出结论就省掉，结论写在图下那句话里。
- **密度**：主卡片 ≤ 12（不含标签和结论卡），超了拆总览+详图，节点名一致。
- **简化靠合并不靠删除**：先把同类部件并成卡片标签、已有系统压成一行，再考虑拆图；正文反复提到的部件至少以标签留名。规则逐项落在一组部件上时用 `card(..., rows=[...])`，每项一行带标签，不写"两个"这种数量。
- **尺寸**：画布宽 960–1440，高宽比 ≤1.3，按 960 设计单位排；800px 文档宽度下主要文字 ≥12px、辅助 ≥9px。

## 用 diagram_kit 画

只依赖 Python 标准库；作者摆位置，样式、文字宽度、连线端点和检查由组件负责。

```python
from diagram_kit import Diagram

d = Diagram(1200, 720, title="写入只经过网关", subtitle="目标架构 · 实线为调用")
d.legend([("line", "调用", "main"), ("line", "规划", "planned")])
api = d.card("api", 60, 200, 300, "任务 API", desc="接收并校验任务", badge="1")
gw = d.card("gw", 440, 200, 300, "网关", code="POST /v1/tasks", tone="accent",
            emphasis=True, badge="2", chips=[("独占写入", "filled", "accent"), "可回放"])
d.zone_around("svc", [api, gw], "服务层")
d.edge(api, gw, label="转发", style="main")
d.note("t1", 60, 440, 360, "只有一条写路径", "所有写入都经过网关鉴权和限流")
d.save("arch.svg", drawio="arch.drawio")   # 放不下/重叠/线穿卡片时抛 LayoutError
```

部件：`zone`/`zone_around`（区域）、`phase_banner`（编号阶段横幅）、`card`（`rows=` 列同类部件）、`chip`、`bar`（横贯共享层）、`note`（结论卡）、`edge`（同侧边多线自动均布端口，`align=` 直线，`via=` 指定拐点）、`legend`（`"line"`/`"card"`/`"chip"`/`"zone"`/`"dot"`）、`cols`、`measure_card`。放不下、超三行、重叠、线穿卡片、标签压边都会报具体位置，按提示加宽/拆分/移位，不缩字号。

结构图示例：`personal-harness/`（核心与外围）、`transactionapp-overview/`（三阶段项目总览）、`config-release/`（发布链路）。其他图型的示例见 `diagram-selection.md`。手写 SVG 也可以，遵守同样语法和下面限制。

## 可移植格式限制

浏览器/GitHub/resvg/draw.io/飞书画板导入器的交集；只在通用平台交付时个别可放宽，但默认遵守，换平台不返工：

- 自包含：有 `xmlns`、`viewBox`，不引外部图片/字体/脚本；文字用 `<text>` 不转路径。
- 只用 `rect`/`circle`/`ellipse`/`line`/`polyline`/`polygon`/`path`/`text`/`g`；滤镜仅 `feDropShadow`（resvg 支持，飞书导入会丢弃，不影响结构）；渐变用 `objectBoundingBox`；不用 `pattern`/`clipPath`/`mask`/`foreignObject`。
- 要导入飞书画板时：圆角不超过高度一半，否则冻结成图片；自由圆柱/任意多边形也会冻结，语义形状优先旋转 45° 的 rect（菱形）、ellipse、叠层 rect。
- 箭头用 `orient="auto"`（`auto-start-reverse` 在 resvg 不旋转）；要固定箭头尺寸给 marker 加 `markerUnits="userSpaceOnUse"`。每张卡片形状+文字放同一个 `<g>`，导入后整体可拖；不要把整图包进一个 `<g>`。

## 自检

1. 跑 `python3 scripts/diagram_check.py arch.svg --png arch.png --doc doc.md`：平台无关格式/字号/色系/比例 + PNG；`--doc` 列出正文常用、图里没有的名字，逐个确认。发布飞书才加 `--board`。
2. 看 PNG：第一眼是不是重点？阅读顺序可见？有线交叉压字吗？颜色都有含义、图例对全图成立吗？名称与正文一致？数字规则在正文找得到、正文标为待确认的图里没画成定论？
3. 图下写一句话告诉读者怎么看，不重复图上文字。

常见错误对应改法：竖长分层每层一色→横向版式、颜色只给重点；满屏白方块→三级层次一个重点；标题写"架构图"→写结论；现状规划同式→规划虚线+图例；字小→拆图或并标签不缩字；为好读删关键部件→以标签留名；栏内箭头方向乱→统一方向、回流虚线；线穿卡片压线→调位置拐点后跑检查。

其他图型：流程语义见 `process-modeling.md`，数据图见 `data-charts.md`，各图型内容要求见 `diagram-guidance.md`，视觉部分以本文为准。
