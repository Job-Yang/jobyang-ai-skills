# 正文格式：用结构代替段落

技术文档是给人**扫**的，不是给人从头读到尾的。读者先看形状（标题、加粗、表头、列表符号、引用块），再决定读哪里。大段文字没有形状，读者只能逐字读，读完还要自己找重点。这正是“一看就是 AI 写的”的来源。

> **默认规则**：能用表格、列表、引用块表达的，就不写成段落。段落只留给“因为…所以…”这种必须连着读的推理，而且要短。

## 先判断内容形状，再选格式

写每一块内容前先问：**它是什么形状？** 按下表选格式，不要默认写段落。

| 内容形状 | 识别信号 | 用什么 | 不要 |
| --- | --- | --- | --- |
| 结论、主张、要读者拍板的事 | “本方案…”“需要确认…” | `>` 引用块 + 开头加粗标签（**结论**：…） | 埋在段落中间 |
| 多个对象 × 多个属性 | 同一组属性反复出现（范围/条件/后果） | 表格 | 每个对象写一段 |
| 方案对比、取舍 | A 和 B、选/不选、代价 | 表格（列：方案/优点/代价/结论） | “A 的好处是…而 B…” |
| 风险、问题清单 | 风险/影响/缓解 | 表格（风险/后果/缓解/负责人） | “主要风险有三个。第一…第二…” |
| 有先后的步骤 | 先、然后、再、最后 | 有序列表 `1.` | 一段里串“首先…其次…” |
| 并列的要点、理由、约束 | 另外、同时、还有 | 无序列表 `-`，每项 ≤ 2 行 | 用逗号串在一句里 |
| “属性：取值”型说明 | 保留期、触发方、上限 | 列表 + 加粗标签（`- **保留期**：30 天`） | 写成连贯叙述 |
| 前提、注意、例外、默认值 | 需要注意、如果…、默认 | `>` 引用块（飞书发布为高亮块 callout） | 混在正文里 |
| 定义 | “X 是指…” | 一行：**术语**：一句话定义 | 一整段介绍 |
| 因果推理、为什么这样选 | 因为、所以、导致 | 1–3 句的短段落 | 拆成碎列表丢掉因果 |
| 数据、参数、接口、字段 | 数字成组出现 | 表格或代码块，长的进附录 | 写进句子 |
| 关系、流程、结构 | 谁调用谁、状态怎么变 | 图（见 diagram-system.md） | 用文字描述拓扑 |

拿不准时：**如果把这段的句子拆开、换个顺序还成立，它就是列表或表格；拆开就断了因果，它才是段落。**

## 每章的形状

一章内容默认按这个骨架排，不是整章段落：

```markdown
## 版本与回滚

回滚 = 把指针切回上一个不可变版本，不重走校验。        ← 一句话结论（可加粗关键词）

- **保留期**：30 天可一键回滚；之后归档，只能手动恢复。   ← 要点/属性用列表
- **触发方**：配置中心自动触发；业务方可手动触发，需填原因。

| 代价 | 量级 | 备选 |                                     ← 对比/代价用表格
| --- | --- | --- |
| 存储 | 约 6GB / 30 天 | 可接受 |

> **待评审**：业务方失去回滚时机控制，是否接受？           ← 要读者注意/决定的用引用块
```

**章首第一块**可以是一句话段落、带加粗标签的引用块，或者一句话后紧跟表格。要求只有一条：读者看第一块就知道本章结论。

## 硬指标（doc_check 会查）

| 指标 | 线 | 超了怎么办 |
| --- | --- | --- |
| 单段长度 | ≤ 120 字（约 3 行） | 拆成列表，或把数据挪进表格 |
| 连续段落 | 不超过 2 段纯段落连排 | 中间插入列表/表格/引用块，或删掉一段 |
| 一章里的格式 | 超过 300 字的章节至少有 1 个表格或列表 | 按上面的形状表重新选格式 |
| 全文段落占比 | 纯段落字数 ≤ 全文 55% | 说明在“写散文”，回到形状表 |
| 加粗长度 | 一处加粗 ≤ 16 字 | 只加粗关键词或数字，不加粗整句 |
| 加粗密度 | 每段/每个列表项最多 1 处 | 同一段两处都重要，说明这段该拆 |

## 加粗、引用块、高亮怎么用

格式是层级，不是装饰。三种强调各管一层：

| 层级 | 格式 | 管什么 | 密度 |
| --- | --- | --- | --- |
| 全文级 | `>` 引用块 + **加粗标签** | 结论、待拍板、关键前提 | 首屏 1–2 个；每章最多 1 个 |
| 段落级 | **加粗关键词** | 一段/一项里读者扫一眼要抓住的词或数字 | 每段/每项 ≤ 1 处 |
| 列表级 | `- **标签**：内容` | 属性型列表的“键” | 不受密度限制，标签是结构不是强调 |

- 加粗的是**词**：**25 分钟**、**自动回滚**、**不改接口**。不是整句。
- 引用块开头用固定标签：**结论**、**待拍板**、**前提**、**注意**、**默认**、**不做**。读者看标签就知道这块是什么。
- 不用 emoji 当强调（✅❌ 在表格里作状态符号可以）。

## 列表写法

- 每项 ≤ 2 行；超过就是段落伪装成了列表，拆成子项或表格。
- 同一列表里的项**同类、同语法**：要么都是名词短语，要么都是动作，要么都是“标签：内容”。
- 3 项以上、每项都有 2 个以上属性 → 换表格。
- 嵌套最多两层。第三层说明该拆成小节或表格。
- 列表项可以是短语，不要求完整句；但列表前面要有一句话说明这组是什么（“为什么是四批：”）。

## 改写示例

改写前（信息都在，全是段落）：

```markdown
## 风险

主要风险有三个。第一是指标采集延迟，如果指标延迟超过观察窗口，判定会基于不完整的数据，
可能误放行，缓解方式是判定前检查指标时间戳。第二是多个变更同时灰度时指标互相干扰，无法
判断是哪个变更导致异常，缓解方式是同一服务同一时间只允许一个变更在灰度中。第三是配置中心
自身故障，这时回滚也无法执行，缓解方式是保留直接写入实例的应急通道。
```

改写后（同样信息，表格一眼看完）：

```markdown
## 风险

三项风险都有缓解手段，**配置中心故障**是唯一会让回滚失效的一项。

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| 指标延迟 > 观察窗口 | 误放行 | 判定前校验指标时间戳 |
| 多变更同时灰度 | 无法定位异常来源 | 同服务同时只允许一个灰度 |
| 配置中心故障 | 回滚失效 | 保留直写实例的应急通道 |
```

改写前（首屏一段话）：

```markdown
当前配置变更一次性全量下发，过去三个月有 4 次错误配置在 2 分钟内影响全部实例，平均恢复
耗时 25 分钟。本方案把配置发布改成分批灰度……需要评审确认两件事：是否接受发布总时长从
1 分钟增加到约 40 分钟，以及是否同意由配置中心而不是业务方负责回滚判定。
```

改写后：

```markdown
> **结论**：配置发布从「一次全量」改为「四批灰度 + 自动回滚」。
>
> **为什么现在**：近 3 个月 4 次错误配置 2 分钟内打满全量，平均恢复 **25 分钟**。

**待拍板**：

1. 发布时长 1 分钟 → 约 40 分钟，是否接受？
2. 回滚判定权从业务方移交配置中心，是否同意？
```

## 发布到飞书时的映射

| Markdown | 飞书文档 |
| --- | --- |
| `> **结论**：…` / `> **待拍板**：…` | 高亮块（callout），结论用蓝/绿，风险用红/橙 |
| `> **注意**：…` / `> **前提**：…` | 高亮块（黄/灰） |
| 其他 `>` 引用 | 引用块 |
| 表格、列表、加粗、代码块 | 原样 |

本地 Markdown 是唯一源；平台映射只换承载方式，不改结构。
