# 默认决策模型

## 决策链

所有研发文档共用一条内部检查链：

```text
文档契约
→ 事实与现状
→ 问题
→ 目标和边界
→ 约束
→ 候选方案
→ 决定与代价
→ 落地设计
→ 影响与风险
→ 验证、发布和回退
→ 未决问题
```

允许回环补证和修改决定，不允许为了把文档写完而跳过缺口。这条链只约束判断完整性，不规定正文目录。

## 五类陈述

| 类型 | 含义 | 处理要求 |
| --- | --- | --- |
| 事实 | 能由原始证据直接支持的陈述 | 保留来源、范围、时间或版本 |
| 推导 | 由事实推出的工程判断 | 写清推导依据，不冒充观测 |
| 假设 | 为继续设计暂时采用的前提 | 说明不成立时会影响什么 |
| 决定 | 当前选择的方案、边界或取舍 | 说明责任人、状态和代价 |
| 待确认 | 当前无法收敛的问题 | 说明由谁用什么证据关闭 |

最终正文不必逐句贴标签，但关键决定附近必须能看出哪些是事实，哪些仍是假设。

## 文档契约

开工前先写一句：

> 这份文档要让谁，基于哪些事实，对什么问题作出什么决定或动作。

文档契约至少确定：

- 文档类型。
- 主要读者。
- 读者完成阅读后的动作。
- 本文覆盖和明确不覆盖的范围。
- 当前状态。

文档契约属于内部工作记录，默认不印进正文。

## 证据账本

### 证据优先顺序

一般按下面的顺序取证：

1. 当前运行结果、真实数据和已验证输出。
2. 当前分支的代码、配置、接口定义和数据结构。
3. 当前有效的正式文档和已接受决定。
4. 历史方案、会议结论和人工陈述。
5. 模型推断和通用经验。

顺序只代表默认可信度。代码中存在一条分支，只能证明“有这段逻辑”，不能证明本次运行一定走到这里。

### 关键事实

一项事实发生变化后，可能改变以下任意内容，它就是关键事实：

- 问题判断。
- 候选方案。
- 推荐结论。
- 风险等级。
- 改造落点。

关键证据必须：

- 能回到原始来源。
- 说明适用的系统、环境、分支、版本或时间。
- 直接支持当前结论，或写清中间推导。
- 与其他关键证据没有未解释的冲突。

来源冲突时，不自行挑选。由事实源负责人确认；无法确认时保持阻塞。

证据账本默认不进入正文。正文只在关键判断附近引用必要来源，或在附录提供索引。

## 问题模型

问题必须独立于推荐方案，回答：

- 当前状态是什么。
- 目标状态是什么。
- 中间差距是什么。
- 差距造成什么影响。
- 保持现状会发生什么。

“需要引入某框架”是方案，不是问题。

## 目标、边界和比较标准

目标必须带验收证据。边界只在会影响理解、实施或验收时记录。

“非目标”是可选表达，不是必填字段。只有读者很可能把某项工作误纳入本次范围时，才需要写清；通常直接在相关段落中说明边界，不单独设“非目标”章节。

比较标准从目标和约束中推导，例如：

- 一致性要求。
- 延迟和吞吐目标。
- 兼容范围。
- 可回退性。
- 运维成本。
- 团队掌握程度。
- 迁移成本。
- 安全与合规要求。

不得在看到推荐方案后再设计一套只对它有利的标准。

## 候选方案

存在真实选择时，每个候选回答：

- 它如何解决问题。
- 它为什么在当前条件下可行。
- 它在统一标准下更好或更差的地方。
- 让它被选择或放弃的决定性代价。

候选必须是评审人可能真实提出的方案。禁止添加明显不可行的陪跑项。

如果目标和约束已经收敛成唯一做法：

- 不硬凑替代方案。
- 记录哪些约束消除了其他路径。
- G4 标为 `not_applicable`，并填写理由。

## 决定

推荐结论必须写清：

- 选择什么。
- 哪些事实和标准推动了选择。
- 主动接受什么缺点、债务或限制。
- 哪些假设仍未证实。
- 什么条件变化后需要重新评估。

没有代价的方案，通常只是遗漏了代价。

## 落地设计

只展开影响决定、协作和正确性的细节：

- 系统边界和职责变化。
- 关键接口、数据和状态契约。
- 主流程和重要异常流程。
- 兼容、迁移和生命周期。
- 具体改造落点和所有权。

完整代码、接口定义、表结构和原始调研放附录或权威链接。除非算法本身就是评审对象，正文不写代码流水账。

## 交付闭环

文档必须说明：

- 实现后用什么证据验收。
- 哪些指标和日志负责发现异常。
- 如何灰度、双跑、迁移或切换。
- 失败时如何回退，数据是否可逆。
- 哪些风险由谁在什么时候关闭。

具体检查项由风险触发矩阵决定，见 `quality-gates.md`。

## 标准决策对象

结构化记录使用下面的逻辑字段：

```yaml
document:
  title: 文档标题
  purpose: 要推动的决定
  audience: 读者及期望动作
  type: 技术方案 | RFC | 架构决策 | 重构迁移方案
  status: 草案 | 待评审 | 已决定 | 可实施 | 已实施 | 待复核 | 未采纳 | 被取代
  review_from: 进入待复核前的状态
  scope: 覆盖和不覆盖的范围

problem:
  current_state: 当前状态
  evidence: 现状证据
  gap: 当前状态与目标的差距
  impact: 业务或工程影响
  do_nothing: 保持现状的结果

criteria:
  goals: 可验证目标
  non_goals: 明确不做的事项
  constraints: 业务、技术、组织和时间约束

options:
  candidates: 可行候选
  comparison_criteria: 统一比较标准
  unique_path_reason: 方案唯一时的约束说明

decision:
  recommendation: 推荐或已接受的方案
  rationale: 选择依据
  accepted_costs: 接受的代价
  assumptions: 仍在使用的假设
  accepted_by: 决定责任人

design:
  system_boundary: 系统边界
  responsibilities: 职责划分
  main_flow: 主流程
  exceptions: 异常和边界
  contracts: 接口、数据和状态契约
  change_points: 改造落点

visuals:
  - question: 这张图替读者回答什么
    type: 图型
    audience: 目标读者
    scope: 图的范围
    view_state: 现状 | 目标 | 迁移过程 | 排期
    source_ref: 可编辑图源
    evidence: 支撑元素和关系的证据
    placement: 图在正文中的位置
    render_evidence: 实际渲染产物
    last_verified_at: 最近核验时间
    # 以下为复杂图或跨平台交付的可选记录，不是脚本强制字段
    semantic_ref: 节点、边、条件、汇合及终态的核对记录
    delivery_target: 正文 | 画板 | 幻灯片 | 打印
    reading_size: 实际验收的尺寸或缩放
    published_ref: 已回读验证的发布地址；本地交付可为空

delivery:
  impact_surface: 影响面
  validation: 验证证据
  observability: 感知办法
  rollout: 灰度和迁移
  rollback: 止损和恢复
  ownership: 负责人和依赖方

open_items:
  blockers: 未关闭前不能实施的事项
  questions: 可以继续收敛的问题
  follow_ups: 本次不做的后续工作
```

结构化对象是内部检查面，不是固定的正文目录。`visuals` 也是按需数组；没有需要图示的关系时可以为空。其他字段可以为空，只要它确实不影响当前决定；不得为了填满对象而给正文制造章节或图表。

图示语义、可编辑源、预览和发布地址各自承担不同职责。默认保留本地源和预览，图源随正文交付，不要求飞书或其他服务端 ID。普通文档不必为这些字段创建结构化记录。

## 状态机

| 状态 | 进入条件 |
| --- | --- |
| `draft` | 已建立文档契约，可以带非阻塞假设 |
| `in_review` | 作者可完成的门禁已关闭，没有阻塞项 |
| `decided` | 决定责任人接受方案，决定性评审问题已关闭 |
| `implementable` | G0 至 G12 通过或有理由地不适用，专项评审和交付措施已关闭 |
| `implemented` | 已链接实现和验证证据，并按真实落地更新文档 |
| `revalidation` | 新事实可能使原决定失效，禁止继续作为实施依据 |
| `rejected` | 提案被否决或撤回，保留理由但不作为当前决定 |
| `superseded` | 新决定已经取代原决定，旧文档指向替代文档 |

允许的主要流转：

```text
draft → in_review → decided → implementable → implemented
  │          │
  └──────────┴→ rejected

decided | implementable | implemented
  → revalidation
      ├→ review_from             原决定仍成立
      └→ superseded             新决定已接受
```

状态规则：

- `revalidation` 必须记录 `review_from`。
- 复核确认原决定仍成立，恢复 `review_from` 并附复核证据。
- 复核确认要改变决定，再建立替代草案。
- 替代草案被否决或撤回，进入 `rejected`。旧文档保持 `revalidation`，除非同时确认原决定仍成立。
- 新决定被接受，新文档进入 `decided`，旧文档进入 `superseded`。
- 任何状态变化都要记录操作者、时间和原因。

## 外部文档怎样组织

先问读者看完要回答什么，再排章节。内部字段不直接变成标题。

除非团队模板要求，默认不使用整张元数据表。状态影响阅读时，用一行说明即可。不要向读者解释“本次输入”或“当前材料”，直接陈述已确认事实，把未知项写成待确认问题。

### 轻量说明

适合局部、低风险、容易回退的改动。通常只需：

```text
改什么，为什么
影响到哪里
怎么验证
```

三件事可以写成几段话，不一定设小标题。

### 标准方案

适合跨模块或存在真实选择的改动。常见阅读顺序是：

```text
先给建议和决定依据
再交代当前问题与关键约束
随后说明方案和关键改造点
最后说明上线、验证与回退
```

章节名要跟随实际内容。例如“随机灰度会破坏重试幂等”比“风险分析”更有信息。

### 高风险方案

适合资金、鉴权、数据写入、隐私和核心稳定性改动。正文仍沿着读者问题展开，只把被风险触发的控制写详细。证据账本、完整门禁和原始接口放附录或独立审计产物。

方案涉及结构、关键运行场景、状态、数据或排期时，按 `diagram-guidance.md` 选择最小图集。图与正文共同构成规格，但图型由问题决定，不把“必须有架构图和时序图”写成固定模板。

### 条件章节

- 目标或验收口径需要评审时，单列目标。
- 范围容易被误解时，说明边界；一般不单列“非目标”。
- 有多个真实方案时，展开比较。
- 有未关闭问题时，列待确认项及关闭方式。
- 需要追溯大量材料时，增加附录。

没有真实内容就删除，不能输出空壳或“不适用”。

团队模板的处理方式见 `template-adaptation.md`。
