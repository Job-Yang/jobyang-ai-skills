# 技术图示方法

图用来表达文字难以稳定承载的关系：边界、层级、方向、时序、状态、依赖和时间。它不是装饰，也不是正文的缩略版。

选定图型后按需读 `diagram-recipes.md` 的对应段；正式成图读 `visual-design.md`，从 `assets/visual-examples/README.md` 选相近样例。分层结构、组织树、时间线、循环、矩阵、品牌屋、发布列车等常用模板读 `assets/diagram-templates/README.md`，其中包含输入格式与布局边界。涉及控制流程读 `process-modeling.md`，定量数据读 `data-charts.md`，交付读 `portable-delivery.md`。均随包提供，不要求在线服务或其他 Skill。

## 核心原则

### 一图一问

画图前先写一句内部说明：

> 这张图要让谁，看清什么关系，从而作出什么判断。

问题写不出来，不画。一个短句或小表格已经能说清，也不画。

### 一图一层

同一张图里的元素必须处于可比较的抽象层：

- 上下文图只画系统、用户和外部系统。
- 容器图只画可独立运行或存储数据的单元。
- 组件图只展开一个容器里的核心模块。
- 部署图只回答软件如何落到环境、节点和故障域。

服务、类、机房和业务目标混在一张图里，会让方框失去统一含义。需要多个尺度时，拆成可逐层放大的图集。

### 一图一态

现状、目标和迁移过程默认分开：

- 现状图用于证明问题。
- 目标图用于说明最终职责和边界。
- 迁移图用于说明如何从现状走到目标。

确需同图比较时，左右并列并使用相同的元素、命名和布局；只高亮发生变化的部分。

### 先语义，后样式

先确定：

- 实体是什么。
- 实体属于哪个边界。
- 关系的方向和含义是什么。
- 哪些路径是主路径、异常、异步或回退。

语义确认后再处理布局、颜色、图标和线型。视觉效果不能修改语义，也不能用颜色掩盖关系不清。

名称只能证明实体存在，不能证明它执行什么业务副作用。不能从 `Inventory`、`Billing` 等名称自行推出“扣库存”“生成账单”等动作；输入、代码或接口没有确认时，只写“业务处理”或明确标为待确认。

### 图文共同构成规格

每张图都要有自己的图前说明和图后结论。图前说明读者要看清的工程关系，图后说出由图得到的关键判断；相邻两张图不能共用一段引导或一段结论。

正文不逐框复述图。图已经清楚表达的结构和流程，从正文删除；图无法表达的原因、权衡、接口字段、阈值和例外仍由文字说明。

图示契约、正文宽度、拆图理由、布局取舍和 Mermaid、PlantUML 等语法选择属于内部制图过程，默认不进入正文。正文只解释工程边界和有意省略的技术范围，不向读者说明“为了缩放”“为了避免交互框”之类的排版动作。

### 视角先于图型

先确定谁在看：

- 业务和产品关注系统边界、能力和用户场景。
- 研发关注运行单元、组件、接口和关键时序。
- 测试关注场景、状态、异常和验收路径。
- 运维和安全关注部署、网络、故障域、数据流与信任边界。
- 项目负责人关注依赖、关键路径和可验收里程碑。

同一方案可以有多个视角，但不能在一张图里同时满足所有人。用最典型或风险最高的场景反向检查静态架构是否真的能支撑它。

## 先做视觉问题扫描

形成决策对象后，检查是否存在下列问题。命中才画相应视图：

| 读者要回答的问题 | 合适的图 |
| --- | --- |
| 系统边界在哪里，谁与它交互 | 上下文图 |
| 系统由哪些运行单元组成，各自负责什么 | 容器图 |
| 某个运行单元内部如何拆分 | 组件图 |
| 软件部署到哪些环境、节点和故障域 | 部署图 |
| 一个关键场景中谁先调用谁 | 时序图 |
| 流程有哪些判断、循环和异常出口 | 流程图 |
| 多角色或多团队如何交接 | 泳道图 |
| 并行工作何时汇合，消息和超时如何竞争 | BPMN 或明确标注控制规则的流程图 |
| 多条件如何组合决定结果 | 决策表；需要标准模型时用 DMN |
| 对象有哪些状态，什么事件触发转换 | 状态图 |
| 数据从哪里来，在哪里转换、存储和离开 | 数据流图 |
| 实体、键和基数是什么 | ER 图 |
| 任务如何并行、依赖和占用时间 | 甘特图 |
| 哪些可验证成果必须在何时达成 | 里程碑图 |
| 指标是否改善、波动或有长尾 | 折线、比较、直方图、ECDF 或箱线图 |
| 哪些维度形成热点、共同变化 | 热力图或散点图 |
| 总量来自哪里，变化如何构成 | 堆叠条形图或瀑布图 |
| 整体能力如何分层、分区 | 系统分层图或网格分组；调用方向另画真实边 |
| 谁管理谁，内容如何逐级包含 | 组织架构或层次树；多父关系不能硬改成树 |
| 一个主题有哪些分支 | 思维导图；不用于表达执行先后 |
| 事件何时发生、间隔多长 | 水平或垂直时间线；位置按真实时间计算 |
| 阶段完成要交付什么 | 阶段里程碑；等距排布不代表工期 |
| 哪些环节形成反馈 | 循环图或增长飞轮；正反馈仍需证据 |
| 主张由哪些支柱和基础支撑 | 品牌屋或金字塔列表；面积不代表数量 |
| 两组维度如何交叉核对 | 网格矩阵；数量强弱用热力图 |
| 如何按窗口组织发布与延期 | 发布列车概览；准入、阻断和回退显式标注 |
| 比例、逐级转化或多维表现如何分布 | 饼／环图、漏斗、二维坐标或雷达，见数据图指南 |

同一问题不要同时用流程图、时序图和大段文字回答。选择最贴近评审问题的一种。

精选模板用于扩大选择范围，不是每篇文档都要画一套。商业模式画布只在业务假设本身需要比较时使用；韦恩图和嵌套集合表达集合关系，不能凭圆面积估算规模。模板中的合成文字和数字必须替换并复核，不能直接进入真实技术结论。

## 图型选择

### 上下文图

回答“这个系统在什么边界内，和谁发生关系”。

应该包含：

- 当前讨论的系统及一句职责说明。
- 主要用户或角色。
- 外部系统、数据源和数据去向。
- 单向、带意图的关系。
- 明确的系统边界。

不要包含内部模块、类和表。上下文图不是缩小后的详细架构图。

### 容器图

回答“系统由哪些可独立运行或存储数据的单元组成”。

应该包含：

- 应用、服务、任务、数据库、队列等运行单元。
- 每个单元的核心职责和关键技术。
- 单元之间的调用方向、协议或消息形式。
- 外部依赖和系统边界。

不要把单个服务里的类和函数画进来。多数方案用上下文图或容器图已经足够，不为完整感继续画组件和代码层。

### 组件图

回答“一个复杂容器内部由哪些核心模块协作完成职责”。

只在组件划分本身是评审重点时使用。包含模块职责、提供与依赖的接口、主要依赖关系。模块过多时按业务能力拆图，不把目录树原样搬上画布。

### 部署图

回答“软件在什么环境和故障域运行”。

适合表达：

- 地域、机房、集群、节点和网络边界。
- 软件单元到基础设施的映射。
- 副本、扩缩容、主备、跨区和失效转移。
- 入口、出口和关键网络依赖。

不要把逻辑模块分层当部署拓扑。实际通过私网端点访问的服务，不能为了画面简单而放进错误的网络边界。

### 时序图

回答“一个具体场景如何按时间发生”。

规则：

- 一张图只画一个主场景或一组紧密相关的变体。
- 参与者按真实边界排列，不画每个内部函数。
- 请求经过中间层时，返回路径也要保持同一调用边界；不能为了少画一条消息，让响应绕过 Gateway、代理或适配层直接返回最外层调用者。
- 每条消息写清动作和关键载荷，不用含糊的“调用”“处理”。
- 区分同步、异步、返回、超时和取消。按图型约定箭头，不能把虚线一律等同于异步；具体符号见 `diagram-recipes.md`。
- 使用 `alt`、`opt`、`loop` 或等价表示展示会改变设计结论的异常、重试和并发。
- 异常不能遗漏，但不必全部挤进主路径。同一张时序图同时叠加 `loop + alt + par`，或嵌套超过两层交互框时，保留主因果链，把复杂分支拆成流程图、状态图或相邻文字。
- 交互框条件使用能独立判读的短标签，中文通常不超过 8 个字，例如“提交成功”“确认超时”。完整条件放在框前说明或图后正文；真实渲染后标签必须保持单行，不能出现孤立括号或尾字换行。
- 多个消费者遵循同一契约时，可合并成一个抽象角色生命线，在正文列出实例；只有交互差异会改变结论时才分别展开。抽象角色应写成“独立下游消费者（Inventory、Billing）”之类的职责名称，不能写成“消费者组”，除非它们确实属于同一个消息消费组。
- 时间顺序必须符合真实因果，不能为了排版调换。

当交互只在单个模块内部且没有重要时序约束时，代码或短文字通常更合适。

### 流程图和泳道图

流程图回答“经过哪些判断走向什么结果”。有真实分支、回路或异常出口时使用；纯线性三步流程用列表更清楚。

泳道图在流程图上增加职责边界，适合多角色、多系统或多团队交接。每个活动只能属于一个主要责任方；跨泳道箭头代表交付或协作。

决策节点必须写成可判断的问题，出口写条件。不要用菱形表达普通步骤。

具体做法见 `process-modeling.md`：先列主路径、排他分支、并行及汇合条件、失败出口和重试上限，再组织布局。不能把并列关系串成长链，也不能为了避免长链把真实串行画成并行。

BPMN 中区分 pool 与 lane、顺序流与消息流，以及 XOR、AND、OR 和事件等待。分支并非全部需要汇合，结束事件也不自动终止其他并行活动。规则组合多时改用决策表，不画大量交叉分支。

### 状态图

回答“对象允许处于哪些状态，什么事件或条件让它变化”。

应该包含：

- 初始状态和终止状态。
- 状态名称。
- 转换事件。
- 必要的守卫条件。
- 失败、取消、超时和补偿路径。

状态图不是业务流程图。流程步骤是“做什么”，状态是对象在某一时刻“是什么”。存在并发更新、重试、补偿或非法转换风险时，优先画状态图。

### 数据流图

回答“数据从哪里来、经过什么处理、存到哪里、向哪里去”。

应该包含：

- 数据源和接收方。
- 处理或转换节点。
- 存储。
- 方向和数据名称。
- 批处理、流式或实时属性。
- 涉及安全时的信任边界、分类、加密和脱敏。

数据流图不负责表达表之间的基数关系。

### ER 图

回答“核心数据实体如何关联”。

应该包含：

- 只与当前决定有关的实体。
- 主键、外键和必要约束。
- 关系基数和可选性。
- 新增或变化的字段。

索引、分区、唯一约束会影响方案时，应在图旁说明或补充物理数据模型。不要把所有字段都搬进主文档。

### 甘特图

回答“工作如何沿时间展开，哪些任务互相依赖”。

绘制前必须已经有：

- 可交付物和工作分解。
- 由实际执行者确认的工期估算。
- 负责人。
- 依赖关系。
- 可并行工作。

甘特图至少表达任务、持续时间、依赖、负责人和里程碑。关键路径只有经过计算或由有效计划工具给出时才标注；Mermaid 的 `crit` 仅是样式标记。没有依据的精确日期会制造虚假确定性；此时使用相对日期或阶段，或者只画里程碑。工作日历、区间约定和资源限制见 `diagram-recipes.md`。

甘特图是执行团队的工作视图，应持续更新。只在启动时画一次、之后不维护的甘特图会变成误导信息。

### 里程碑图

回答“哪些关键结果必须在何时通过”。

里程碑是零时长、可验证的结果：

- “接口契约由上下游签字”是里程碑。
- “开发接口”是任务，不是里程碑。

每个里程碑至少包含日期、负责人、完成证据和依赖。面向决策者时用里程碑图；需要管理每日任务和并行依赖时用甘特图。两张图都有时，它们应来自同一份计划数据。

## 最小图集

不要按模板凑图。常见技术方案通常从下面选择一至三张：

| 方案特点 | 建议图集 |
| --- | --- |
| 新系统或边界变化 | 上下文图或容器图 |
| 跨系统接口与异步协作 | 容器图 + 一个关键时序图 |
| 复杂状态与补偿 | 状态图 + 必要的关键时序图 |
| 数据迁移或同步 | 数据流图 + 迁移阶段图 |
| 数据模型变化 | 聚焦变更实体的 ER 图 |
| 多团队、长周期交付 | 甘特图；面向管理者再派生里程碑图 |
| 低风险局部修改 | 通常不画图 |

当前架构与目标架构只有在差异本身是评审重点时同时出现。否则只画读者需要的一态。

## 图的语义契约

每张图在内部记录：

| 字段 | 要回答什么 |
| --- | --- |
| 问题 | 这张图替读者回答什么 |
| 受众 | 谁会依据它作决定 |
| 类型 | 使用哪种视图 |
| 范围 | 包含和不包含什么 |
| 状态 | 现状、目标、迁移过程还是排期 |
| 事实来源 | 元素和关系由什么证据支持 |
| 图源 | Mermaid、PlantUML、SVG、Draw.io 或画板源文件 |
| 放置位置 | 在正文哪个判断附近 |
| 渲染证据 | 实际渲染后的预览或画板 |
| 最后核验时间 | 最近一次与代码、接口、计划对齐的时间 |

复杂图补充节点编号、边及条件、主路径、汇合规则、终态、责任方和来源。普通任务在草稿中核对即可；需要审计时记入 `visuals` 或独立图源附件，不强制创建 JSON，也不作为正文中的固定表格。

同时记录目标载体、阅读尺寸、图源与预览路径。图源、语义和发布地址分开保存，防止只能通过某个在线画板恢复技术信息。现有校验器未知的图型或格式使用 `other`，并在范围或图源说明中写出具体类型；这只登记元数据，不证明模型语法可执行。

## 统一绘图语法

无论使用什么工具，至少遵守：

- 标题说明图型、范围和状态，例如“订单系统目标容器图”。
- 元素有名称；架构元素补一句职责。
- 调用或数据移动关系使用单向箭头并写动作、数据或协议；ER 基数关系等按该图型符号表达，不硬加动作箭头。
- 动作关系按执行者定方向：在架构调用与时序视图中，箭头从执行动作的实体指向动作对象。例如读取方应指向存储方，返回记录再画成反向关系；数据流图则按数据移动方向连线。不能把“数据随后流向谁”当成“谁发起动作”。
- 连线端点必须是发生关系的实际实体。分组、泳道和系统边界只用于归类；除非边界本身就是关系参与者，否则不能用分组边框代替内部节点作为连线端点。
- 双向交互优先拆成两条单向关系。
- 同步、异步、回退和异常使用一致的线型或箭头，并提供图例。
- 颜色不作为唯一语义；同时使用文字、线型或边框。
- 缩写在图中解释，或在相邻正文首次出现时解释。
- 相同实体在整篇文档中名称、颜色和形状一致。
- 视觉重点围绕同一个阅读问题，避免多个无关焦点争夺注意；多个关键路径节点可以共同高亮。

### 按交付载体设计

先确定是正文、画板、幻灯片还是打印稿；具体口径见 `portable-delivery.md`。未指定时采用本地 Markdown，默认按 680 至 900 像素内容宽度设计并验收：

- 图缩放到目标正文宽度后，正文和箭头标签仍能直接阅读。
- 需要缩到原尺寸 70% 以下才能放进正文时，优先拆图或改为纵向布局。
- 同层横向并列一般不超过四项；更多元素按语义分组或改为上下布局。
- 节点文字控制在一个标题和一行说明，不把段落塞进框。
- 连线标签只保留动作、数据或协议，不把完整条件句压在线上。
- 单张图超过约 20 个节点、6 条生命线或需要大量交叉连线时，触发拆图检查。优先总览加详图；这些是正文的经验警戒线，不替代实际可读性验收。
- 纵向布局不是默认正确。图的自然宽度不足目标正文宽度一半、同时高度超过宽度两倍时，检查能否按职责或阶段拆分、分组。真实串行不为凑比例而折成两至三行，真实分支和并行才应在空间上展开。

可缩放画板允许大画布，但整体结构和局部文字分别验收；打印和幻灯片按页面检查。不能把一张通过画板验收的宽图直接缩成正文图片后沿用原结论。

时序图优先保留真正跨边界、会改变设计结论的参与者。入口透传、未变化的中间层和内部函数可以在正文说明，不需要全部占一条生命线。
真实渲染后，如果交互框标签出现碎片化换行、括号孤立或与消息线重叠，不用缩成难懂的缩写；应减少同图分支或拆图。
Mermaid 时序图使用 `autonumber` 时，要检查编号圆点是否遮挡消息文字。存在自调用或短生命线间距时，编号与标签重叠就关闭自动编号；编号不是规格，不能为了保留编号牺牲正文可读性。

结构图优先通过上下分层和语义分组减少宽度。部署图使用不同边框、标题或明暗表达主用、备用和待确认，不只依赖颜色。
Mermaid 的连线标签如果出现孤立灰底块，应减少非必要标签，并把 `edgeLabelBackground` 设为正文背景色，避免标签像脱离箭头的贴纸。

## 图与正文如何配合

推荐结构：

```text
一句话说明这张图要解决的问题。

[图]

一小段指出读者应该从图中得到的决定、约束或风险。
```

连续放置多张图时，对每张图分别重复这组结构，不能用一个总说明包住多张图。

正文与图的分工：

| 图负责 | 文字负责 |
| --- | --- |
| 边界、层级、方向和顺序 | 为什么这样设计 |
| 组件、参与者和关系 | 取舍和接受的代价 |
| 主路径、分支和依赖 | 字段、阈值和精确契约 |
| 排期、并行和里程碑 | 估算依据和变更规则 |

图后文字不要重新念一遍所有框和箭头。只说图中最值得评审的判断。

## 工具选择

核心方法与生成器、发布平台分离。先看交付环境和维护方式：

| 场景 | 推荐 |
| --- | --- |
| Markdown、GitHub、代码仓 | 支持语法时可用 Mermaid；否则引用本地 SVG/PNG 并附图源 |
| 复杂 UML 时序、状态或组件关系 | PlantUML |
| 需要精确视觉控制的正式图 | 自包含 SVG 或可编辑图形源，本地渲染检查 |
| 有向图交叉多、分组复杂 | 可用的 Graphviz dot 或 ELK，保留真实边和方向 |
| 需要人工拖拽和共同修改 | Draw.io 或原生白板 |
| 飞书或其他在线文档 | 按用户要求选择可编辑画板或图源加预览；仅发布步骤依赖平台 |

可按需调用 MindAI、`visual-docs` 等工具，但先核对工具能力和交付约束；缺少它们时仍按本指南生成和验收。参考图、模板和沿用同一图源的局部修改都能在本地实施，不属于某个服务专有的流程。平台适配与失败处理见 `portable-delivery.md`。

工程图不使用生成式位图作为唯一源，因为文字和连接关系难以稳定校验，也不利于版本维护。

## 图示验收

### 独立可读

把图单独交给一个不了解讨论背景的读者，他应能回答：

- 这是什么类型的图。
- 范围和状态是什么。
- 主要实体分别负责什么。
- 关键关系和方向是什么。
- 图希望他注意哪个决定或风险。

### 语义一致

逐项核对：

- 图中的实体在代码、接口、计划或正文中存在。
- 箭头方向与真实调用或数据流一致。
- 同步、异步、重试、失败和回退没有被简化掉。
- 排他、并行、汇合与事件等待没有混淆，重试上限和耗尽终态没有丢失。
- 现状和目标没有混写。
- 图、正文、表格和接口使用相同名称。

### 真实渲染

只检查源码不算完成。必须真实渲染后检查：

- 文字在正常阅读宽度下可读。
- 最终正文宽度下的主要文字不得小于约 12 像素；正文读者需要放大才能辨认，直接判为失败。画板按总览与局部常用缩放分别验证。
- 没有裁切、重叠和遮挡。
- 箭头没有指错、断裂或被节点遮住。
- 连线交叉不会导致关系误读。
- 图例完整。
- 黑白或色觉差异下仍能区分关键语义。
- 缩放到目标文档内容宽度后，文字、关系和分组仍然可辨认。

Mermaid 或 PlantUML 还要验证目标平台实际支持的语法版本。源码在一个环境能渲染，不代表在目标文档平台也能渲染。

只有图源、没有可用的渲染和查看能力时，明确交付“视觉未验收”的草案。平台发布缺权限，只阻塞发布；可独立完成的本地正文、图源和预览继续交付。正式复杂图交给独立读者看实际渲染，并要求其复述主路径、分支条件和失败结果；不以高分抵消语义错误。

### 生命周期

- 图源与文档保存在同一版本体系。
- 图记录适用版本和最后核验时间。
- 代码边界、接口、数据模型、排期或正文相关判断变化时，图必须一同复核。
- 已经过时且不再回答实际问题的图应删除或标为历史，不继续作为当前事实。

## 常见失败

- 一张“万能架构图”同时画业务、服务、类、机房、时序和排期。
- 只有方框和无标签箭头，读者只能猜关系。
- 把目录树完整搬成组件图。
- 时序图只画正常路径，遗漏超时、重试和补偿。
- 流程图没有真实判断，仅把步骤装进方框。
- 状态图把动作写成状态，或缺少非法转换。
- 甘特图只有日期和色条，没有依赖、负责人和完成条件。
- 里程碑写成“开发中”“联调中”等活动。
- 用颜色表达全部语义，没有文字和图例。
- 图与正文使用不同名称或不同方向。
- 只生成源码，没有看过渲染结果。
- 图源不版本化，半年后仍把旧图当当前架构。
