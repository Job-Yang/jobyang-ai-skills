# 常用技术图的画法

按需要读取对应图型。通用语义见 `diagram-guidance.md`，视觉设计见 `diagram-system.md`，细则见 `visual-design.md`。成图、源文件和复现方法见 `assets/visual-examples/README.md`。

## 架构图各自回答一个尺度的问题

| 图型 | 必须有 | 推荐版式 | 完成前核对 |
| --- | --- | --- | --- |
| 上下文 | 目标系统、角色、外部系统、带意图的关系 | 目标居中，外部参与者围绕；按交互方向排 | 没有夹入内部组件；目标边界明确 |
| 容器 | 独立运行或存储单元、职责、技术、协议 | 系统边界内按运行职责分区 | 容器不等同于容器技术；队列、任务、存储归属正确 |
| 组件 | 单个容器内模块、接口和依赖 | 入口、核心、适配器分组 | 箭头含义是调用还是代码依赖；不直接复制目录树 |
| 部署 | 环境、故障域、软件实例、入口与网络 | 故障域并列，软件实例嵌入真实运行位置 | 副本数、主备、路由与共享故障点有依据 |

架构图中的相对位置不天然表示调用顺序。能力地图只有分区而没有技术关系时，就叫能力地图；不能靠叠几层方框冒充运行架构。迁移前后对照采用同一命名和布局，只高亮真实变化；上线步骤另用流程或排期表达。

## 流程图和泳道图

主成功路径连续；真实分支在空间上展开，回路在外围回到准确入口。判断用问题或条件，活动用动词，终点写结果。每项重试包含上限、间隔或停止条件。并行启动与等待全部的汇合必须可见。

多角色交接时用泳道。选择横向或纵向泳道，让主交接方向自然前进；责任方稳定，跨道线标交接物。泳道不表示同时执行。不要为了对齐把不同责任方的活动塞入同一道。

复杂控制语义读 `process-modeling.md`。示例中的普通流程图不是 BPMN 模型。需要 BPMN XML 交换或 DMN 执行时，使用专用建模器并验证模型；本技能的方法说明不等于已经提供执行引擎。

## 时序图

输入先列参与者、消息顺序、调用类型、返回边界和异常。横向是参与者，向下是时间顺序；未给真实时间戳时，纵向距离不代表耗时。

| 关系 | 表达 |
| --- | --- |
| 同步调用 | UML 风格实线、实心箭头，按需加激活条 |
| 异步消息 | UML 风格实线、开口箭头；发送不等同于处理完成 |
| 返回 | 虚线并标返回值；沿实际调用边界返回 |
| 条件 | `alt` 或 `opt` 框，守卫条件与分支分隔明确 |
| 并发 | `par` 或等价说明；不能把普通上下排列称为并发 |
| 重试 | `loop` 写次数和触发条件；耗尽出口不能丢 |
| 超时与取消 | 表明由谁观测、谁取消，以及在途工作是否仍可能完成 |

使用 Mermaid 时，以实际版本为准：常见 `->>` 是实线实心箭头，`-)` 是实线开口箭头，`-->>` 是虚线箭头。语法名称不替业务语义，交付图必须有一致图例。不能照搬“虚线=异步”的泛化规则。

通过紧凑的参与者表头、浅色交互区域、编号与直接标签改善阅读。编号与短消息重叠时移位或取消编号。复杂组合框分图，避免嵌套细线将主路径切碎。成功图省略的失败机制应在邻近文字或配套状态图交代。

## 状态图

输入是一张“起始状态 → 事件 [守卫] / 动作 → 目标状态”的转换表。每个节点表示稳定状态，避免“执行校验”这类瞬时动作冒充状态。

将常见生命周期排在同一轴，等待与重试在一侧，失败或取消在另一侧。复合状态可减少重复线，但不改变合法转换。图上的终态意味着本次生命周期结束；允许重新开始时，明确是重开原对象还是创建新对象。未画的边是否禁止，要在范围中说明。

## 数据流图

先列数据源、处理、存储、接收方及数据名称。箭头表示数据移动方向，区别于架构图中的调用发起方向。批处理和流式、读取和写入、原始和转换后数据分别标明。

推荐按数据阶段组织，而非把服务器部署层级搬过来。存储有专门形状或类型标签，数据标签放在边旁。信任边界、脱敏点和跨区流出影响决定时必须可见；没有依据的加密或合规承诺不能补进图。

## ER 图

输入明确实体、键、关系两端的最小/最大基数及可选性。字段仅保留主外键与本次变更相关内容，其他字段不影响本图判断时省略。

每个实体用表格结构，标题与字段分开。关系线端点贴在实体边缘；采用乌鸦脚、UML multiplicity 或明确数字均可，但图例与全文一致。`1`、`0..1`、`0..*` 的含义不能只凭位置猜。主键/外键文字标识保留，不只用颜色。多对多是否需要关联实体取决于逻辑/物理视图，不自动替用户设计数据库。

## 甘特图

先确认任务、负责人、持续时间、依赖和日历；没有依据时用相对工作日和估算范围。不要先画日期条再凑任务。

推荐左侧任务与负责人，右侧共享时间轴。任务按工作流或团队分组；并行任务在同一时间刻度上可比较。用独立视觉通道表达进度和状态，不能拿条形长度同时表示工期和完成度。

- 明确区间约定，例如 `[开始, 结束)`；工作日、自然日和时区分开说明。
- Finish-to-start 依赖从前项结束指向后项开始；多依赖需全部满足。其他依赖类型需显式说明。
- 里程碑零时长，不用带宽度的任务条假扮。
- 只有经前推/后推计算零总时差，或由有效计划工具给出时，才标“关键路径”。有资源冲突、日历或延迟约束时必须纳入模型。
- Mermaid `crit` 只是样式标记，不会替你计算关键路径；`after` 和 `excludes` 的行为需按渲染器版本核对。
- “今天”线和进度只用于有状态日期的真实计划。示例不能制造虚假完成状态。

包内甘特例是明确假设下的 Finish-to-start DAG：任务估算已知、资源不冲突、以相对工作日计算。它演示依赖和关键路径，不是完整项目排程器。

## 里程碑与路线图

里程碑写可验收成果、时间、负责人和证据。示例“契约通过评审”是结果，“开发中”不是。与甘特同现时，从同一份计划派生，不另写一份日期。

按比例时间轴必须忠实日期间隔；等距阶段卡片应明确“阶段示意，不按时间比例”。路线图用于表达方向和时间窗口，不能把尚未估算的事项画成确定到日的承诺。

## 项目阶段总览图（One Page 类）

阶段/里程碑总览按三条规则画，比每个步骤都做成卡片清楚：

项目阶段/里程碑总览按三条规则画，比每个步骤都做成卡片清楚：

1. **编号横幅 `phase_banner`**：每阶段一行，行首浅色横幅，左侧实心方块写两位编号（`01`），后面是阶段名和一句箭头结论（"01 工程源与 Profile → 控制编译、链接和资源范围"）。它只是分组锚点，视觉比卡片轻，不要画成又一张卡片。
2. **状态只用"填充 + 描边"两通道，图例用迷你卡片 1:1 对应**：白底灰边=已有；强调色浅底+强调色边=新增；橙浅底+橙边=待确认/待部署；橙实心底=待修/待验收。用 `legend([("card","已有能力","neutral"),("card","项目新增","accent"),("card","待确认/待部署","orange"),...])`；小样必须和正文卡片同填充同描边，不要用圆点（只有填充没描边，对不上）。颜色之外还要有文字或线型（虚线）作第二条线索。图例由引擎按真实字宽排版：每项为 [方形小卡片][固定间距][文字][项间距]，一项行内排不下时自动换行、必要时整体等比缩放；色样与任何文字、相邻项之间重叠，或图例越过画布右安全边距，渲染期即报硬错误。
3. **阶段内"主链路一行 + 待办沉底"**：主链路从左到右，只在卡片间有真实数据/控制交接时画线，纯包含关系不画；待修/待验收用橙色 `note` 沉到阶段底部。主卡片仍受 12 张上限约束，超了就用 `rows=` 合并同类步骤。

评审结论类总览按需用 `verdict_bar` 收一句结论（浅底深字，不再用黑色大块），`category_card` 表示类别（中性或灰蓝，不按类别轮换粉米紫），`status_pill` 标明通过／待定／未过（绿／棕／红）。证据与动作仍可用 `evidence_action_row` 并排。全部组件共用统一色板，`warm-cream` 只保留为兼容名称，不再选择暖米底。

跨阶段连线用主线样式并写动词（产出、验证、计时），不要无标签长线绕图外一圈；跨阶段回退画虚线，写明回到哪步。

## 选择边界

| 需要的内容 | 处理方式 |
| --- | --- |
| 少量条件决定结果 | Markdown 决策表，列输入、规则优先级、默认结果；不必画图 |
| 方法调用的精确耗时 | 使用真实 trace 的 span 时间线；普通时序图不承担耗时分析 |
| 火焰图 / 调用栈 | 用 profiler 的采样结果与专用工具，保留采样口径 |
| 大规模依赖拓扑 | 先分层聚焦，再用图布局工具；总览不超过 12 张主卡片 |
| Sankey / 地图 / 网络流量 | 有流量守恒、地理或拓扑问题时再使用专门工具 |
| UML 全套或可执行 BPMN/DMN | 仅在交付要求触发，查对应规范与工具，不承诺包内样例覆盖 |

技术图集中的 12 种视图均有可复现示例。它们覆盖常见阅读任务，不构成所有符号组合、平台导入器和复杂输入的全面认证。

## 新增结构图版式（v2.3）

五个新版式均为纯标准库自包含 SVG，横向 680px；金标准在 `assets/diagram-templates/examples_extra.json`，画廊在同目录 `gallery/`。

### 阶段门 stage_gate

- **什么时候用**：工作被切成 2–3 个横向阶段、阶段之间有显式放行检查（评审、准出、验收），且检查有通过/阻断两种当前状态。只表达顺序与放行结论时用；不表达工期。
- **绘制要点**：阶段卡片横向等距，门禁用圆角胶囊（`rx=高/2`，内嵌 ✓/× 状态）卡在两阶段之间的连线上；通过用强绿、阻断用弱粉，近黑文字只用于阻断结论；被阻断的门禁向下引一条正交折线到阻断说明卡片，写明"阻断后回到哪里重验"。**不用多边形菱形**——`<polygon>` 会被飞书画板导入器冻结成不可编辑图片节点，圆角胶囊可编辑且语义同样清晰。
- **完成后核对**：每个门禁都能看到准入与准出条件；阻断分支不绕远、不穿过无关卡片；`--board` 检查无图片节点冻结；没有门禁时不要用门禁胶囊假装流程。

### 因果链 causal_chain

- **什么时候用**：解释"为什么 A 导致 B"的链条，每条影响有方向和强弱假设；比流程图更强调传导路径而非执行步骤。
- **绘制要点**：节点左到右单链推进，连线标极性——"+ 增强"用绿、"− 抑制"用红；延迟或条件作小注附在极性后；分支节点向上悬挂，支线与主线不交叉。
- **完成后核对**：每条边都有极性标注，颜色与文字一致；链条不回头；分支只挂在有明确旁证的节点上。

### 反馈回路 feedback_loop

- **什么时候用**：一个处理环节的输出反过来影响输入，需要说清这是自我放大（正反馈）还是自我收敛（负反馈），以及触发条件和人工干预点。
- **绘制要点**：输入→处理→输出三个节点一条直链，回环虚线走外围底部回到输入，不穿过任何节点；回环边上同时标注极性（自我放大/自我收敛）与触发条件；干预点作为小卡片坐落在回环线上。
- **完成后核对**：回环确实闭合回输入而不是悬空；极性与业务方向一致（收敛用绿、放大用红）；没有第二个未标注的回路边。

### 状态机 state_machine

- **什么时候用**：一个对象在稳定状态间迁移，迁移由事件触发、带条件和动作。避免把"执行校验"这类瞬时动作画成状态。
- **绘制要点**：实心黑圆是唯一起点，双线矩形是终态。布局由引擎按无交叉规则生成：主干状态沿一条水平主轴等距排列，前向迁移沿主轴直线推进、箭头落在卡片规范端口；异常/分叉状态从主干节点向上或向下侧引短支线，不横穿其它卡；回退/重试一律走卡片最外侧的专用虚线通道，多条回退按“源-目标跨度”分到不同通道层，互不重叠，标签放在通道内。
- **完成后核对**：起点到每个可达状态都有路径；任意迁移边不穿过非端点卡片、除回退通道的正交跨越外任意两边不交叉、同一对节点之间没有重叠边、回退边确实落在外侧通道带——这四条渲染期即硬错误；终态数量与生命周期一致；未画的边是否禁止要在正文说明。
- **回退规则**：分叉状态回到父状态（失败→重试、等待→恢复）画成与分叉边平行的短虚线；其余回退从卡片底边出入，每条独占一条走廊和一层通道。两条边共线重叠、回退横穿前向边都是渲染期硬错误。
- **可扩展性**：已用「订单支付履约」（`sm-order-fulfillment`，7 状态 1 回退）和「任务生命周期」（`sm-task-lifecycle`，8 状态 4 回退）两个金标准验证。

### 时序图 sequence

- **什么时候用**：一次场景里 2–5 个参与者按时间一来一回，读者要看清谁先找谁、哪一步是异步、谁回给谁。超过 4 步的交互都用它，不要画成泳道卡片。
- **输入**：`participants`（`id`/`label`/`emphasis`）、`messages`（`from`/`to`/`label`/`kind`：`sync` 实线、`async` 虚线、`reply` 灰虚线、`self` 自身处理）、可选 `groups`（`label`/`start`/`end` 消息下标，画成阶段底色）。金标准 `seq-agent-dispatch`。
- **完成后核对**：消息标签放得进两条生命线之间（放不下渲染期报错）；纵向只表示先后；成功路径一张图，异常另画或用状态图。

### ER 图 er

- **什么时候用**：对象模型里有「包含」「一对多」「每个 X 有多个 Y」，读者要知道实体、关键字段和基数。不画动作，不画箭头。
- **输入**：`entities`（`id`/`label`/`col`/`row`/`fields`/`emphasis`，网格 ≤ 3 列 × 4 行）、`relations`（`from`/`to`/`label`/`card_from`/`card_to`）。同行或同列直连，其余走 L 形；关系线穿过别的实体时渲染期报错，按提示调 `col`/`row`。金标准 `er-task-graph`。
- **完成后核对**：每条关系两端都有基数；字段只留键和决定关系的字段，完整字段表放附录。

### 截图标注 image_annotate

- **什么时候用**：评审意见、bug 复盘需要"对着截图指认问题"：底图 + 红框圈点 + 编号 + 右侧"问题→动作"图例表。
- **绘制要点**：底图按宽高比缩放内嵌，不越界；红框左上角放编号圆点；右侧图例逐行两张低饱和卡片——证据灰卡写问题、动作绿卡写动作，编号与圆点一一对应。
- **完成后核对**：每个编号在图上和图例中都出现且语义一致；标注框不压到底图关键信息之外。
- **已知限制**：底图是位图内嵌，导入飞书画板后整张底图会变成不可编辑的图片节点，仅标注层（红框、圆点、图例）可编辑；可编辑性以实测导入为准。

### 泳道 workflow（横向，紧凑可扩展）

- **什么时候用**：一件事在多个责任方（前端/网关/鉴权/服务端/库存/支付……）之间交接，要看清跨道线和交接物；角色 3 个到 6 个都用同一版式。
- **绘制要点**：横向泳道、时间从左向右，每个节点固定在所属泳道列内。引擎按内容紧凑排版：道高跟随本道最高卡片（卡片高随标题折行自适应），不设统一大道高；卡片在道内垂直居中，道间只留窄缝。跨道交接走两道路由槽内的短正交折线，跨多道回退沿空列竖直穿行，不绕泳道外侧、不穿无关卡片；交接物/动作写成边标签。
- **完成后核对**：责任方与泳道一一对应；道高没有明显大于本道卡片（渲染期对“道高 > 最高卡 × 阈值、卡片溢出道、跨道线穿卡、卡片重叠”报硬错误）；跨道边都有标签；只画约定的路径，其它分支另图。
- **可扩展性**：已用 6 角色、12 卡、含跨多道回退的压力金标准（`deep-lane-6-roles`）验证，角色/卡片增多时总高随内容增长、不留大片纵向空白。
