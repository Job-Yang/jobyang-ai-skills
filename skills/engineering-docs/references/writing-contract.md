# 正文契约：三层结构

读者先看到结论和全貌，再按兴趣进入细节。细节一条不少，但放在它该在的层。

## 三层各放什么

| 层 | 位置 | 放什么 | 预算（提醒线） |
| --- | --- | --- | --- |
| 首屏 | H1 到第一个 H2 之前 | 结论：做什么、为什么现在；要读者做的决定；范围一句话；总览图和一句读图提示 | ≤ 450 字（不含图） |
| 章节 | 每个 H2 与它的第一段 | H2 是总览里的一个节点或一个决策，标题写短关键词、不编号；第一段一到两句，给本章结论 | H2 3–7 个（≤ 9）；标题 ≤ 20 字；首段 ≤ 150 字 |
| 细节 | H3、表格、列表、引用块、代码、附录、折叠块 | 依据、参数、接口、推导、对比、测试矩阵 | 段落 ≤ 120 字；超过 300 字的章节至少一个表格或列表；超过 6000 字的文档必须有附录 |

**格式是默认，段落是例外**：每块内容先按 `formatting.md` 判断形状（对比→表格，步骤→有序列表，要点→无序列表，结论/前提→引用块），只有必须连着读的因果推理才写成短段落。

预算不是目标。超出时要能说出理由，例如一张必须完整展示的对照表。

## 首屏

首屏回答四件事，按这个顺序：

1. 结论：这次做什么，一句话能讲清的主张。
2. 为什么现在：推动决定的那个事实或风险，带数字。
3. 要读者做什么：批准、选择、补证据，还是照着执行。
4. 全貌：Level 1 总览图，下面一句话告诉读者怎么看这张图、后文按什么顺序展开。

不放背景史、术语表、全部风险和未决问题。它们属于章节或附录。

## 章节

H2/H3 是目录项，写一个**短关键词、模块名或方向**，不是一句话，也不是本章结论。读者扫目录就知道全文骨架；标题写宽一点，章节里才放得下这个主题的各种内容。顺序由标题在目录里的位置表达，**标题不编号**（不写“第 N 步”“1.”“一、”）。

- 标题只回答“这一章讲哪块东西”，不回答“这一章的结论是什么”。结论、具体作用域、验收方式都放章首第一段和正文。
- 写成具体结论会把章节限死：写了“聚合校验 为什么会被下掉”，以后想在同一章补 聚合校验 的接入方式就对不上标题。
- 需要限定主题时用一个宽泛的名词（“灰度发布”“版本回滚”），不用冒号后挂判断的长句。

| 不合适（一句话/编号/太具体） | 更合适（短关键词） |
| --- | --- |
| 聚合校验是什么，为什么调整它 | 聚合校验 |
| 两条观测数据线怎么对照验收 | 数据校验 |
| 一条指标数据的旅程：从触发构建到展示结果 | 指标链路 |
| 调整组件后应用表现有什么变化 | 运行表现 |
| 第 6 步：各模块到底包含哪些组件 | 组件明细 |
| 先讲清楚应用工程：从改代码到实际运行 | 背景与目标 |
| 方案 | 灰度发布 |
| 其他 | 发布与回退 |

每章第一块先给本章结论，再展开。读者读完第一块就可以决定跳过还是继续读。第一块可以是一句话、或带加粗标签的引用块（`> **结论**：…`）；不要直接以表格、列表或小标题开头——先用一句话告诉读者这张表/这组要点说明了什么。

横切章节（发布、风险、验收）写明它连接哪几个节点。

## 正文不写对话来源和个人信息

技术文档只陈述事实、判断和做法，不记录这段内容是怎么来的：

- 不写“老板/同学/领导/评审问、说、要求……”“你让我……”“我跟他说……”这类对话来源和提问者。谁提出的问题与文档结论无关，直接写成要回答的那个事实（“数据来源如下”而不是“老板问数据哪来的”）。
- 不写手机号、个人邮箱、真实姓名加称谓等个人信息，需要联系人时写角色或群组名。
- 这条适用于正文、图注和示例数据；敏感示例数据要脱敏。

## 细节去哪里

每段细节问一句：删掉它，评审结论、职责划分、失败处理或验收会不会变？

- 会变：留在章节里，放在该章结论之后。
- 只影响实现：放附录，章节里留一句“参数见附录 B”。
- 只用于复查事实：放证据附录或链接。
- 都不影响：删掉。

长列表、完整接口、字段表、推导过程和原始数据放附录或 `<details>` 折叠块。附录标题写清对应哪个节点，例如“附录 B：灰度批次判定参数”。

## 写法

- 一段一个意思，首句就是这一段的结论；段落 ≤ 120 字，不连排超过两段。
- 用具体事实代替评价：写“每天约 3 次误触发审批”，不写“显著影响体验”。
- 数字带单位和来源；估算写明是估算。
- 并列、步骤、属性用列表，多对象多属性用表格，取舍和代价用表格；只有因果推理写成短句。列表项可以是短语，但同一列表同类同语法。
- 加粗关键词和数字（≤ 16 字），不加粗整句；每段/每项最多一处。结论、待拍板、前提用 `>` 引用块加粗标签。
- 箭头（A → B）可以在列表、表格和短句里表示变化或流向；不要用一长串箭头代替完整的流程说明，长流程画图。
- 术语保留原词，第一次出现时用一行“**术语**：定义”说明它在本文里的作用。

格式选择、密度和改写示例见 `formatting.md`。

下面这些写法会让读者觉得是“AI 写的”，出现就改：

| 类型 | 例子 | 改法 |
| --- | --- | --- |
| 套话连接 | 值得注意的是、综上所述、事实上、由此可见 | 删掉，直接说事 |
| 空泛强调 | 至关重要、全方位、体系化、无缝、显著提升 | 写出具体后果或数字 |
| 黑话 | 赋能、抓手、打通、沉淀、闭环、落地、兜底 | 写出具体动作：谁在什么时候做什么 |
| 句式套路 | 不是……而是……、不仅……还……（连用） | 直接陈述正面结论 |
| 元叙述 | 本文将介绍、下面我们来看、如下所示 | 删掉，标题已经说明了 |
| 标题写成一句话 | 聚合校验 是什么、为什么会被下掉；tag T+1 怎么对照验收 | 标题只留短关键词（聚合校验、tag T+1），结论放正文；标题不编号 |
| 对话来源入文 | 老板和同学问数据哪来的；你让我对比两条线 | 删掉提问者，直接写事实（数据来源如下） |
| 个人信息入文 | 手机号、个人邮箱、张三老师 | 写角色或群组，示例数据脱敏 |
| 大段文字 | 一章全是 150 字以上的段落；“主要有三点。第一…第二…第三…” | 按 `formatting.md` 形状表改成表格/列表/引用块 |
| 整句加粗 | **本方案通过引入灰度机制有效降低了发布风险** | 只加粗关键词：降低 **发布风险** |
| 提到写作素材 | 素材里没有、材料未注明、根据提供的材料 | 读者手里没有你的素材。写事实状态：“未核实”“目前没有数据”“待某人确认” |

写作方法本身的术语不进正文，例如“黑盒摘要”“下钻”“章首”“口径”“收口”“门禁”。读者不需要知道你怎么组织文档。

## 改写示例

改写前（信息都在，但读者要读完才知道重点）：

```markdown
## 方案

本方案旨在构建体系化的配置发布机制，全面赋能各业务线的配置管理。值得注意的是，当前配置
变更存在一次性全量下发的问题，因此我们需要打通从提交到生效的完整闭环。具体来说，变更会先
经过 Schema 校验，然后下发到内部集群观察十分钟，再按 1%、10% 分批放量，最后全量生效。
与此同时，我们会为每次变更保存不可变版本……
```

改写后（结论在标题和首段，步骤和参数下沉）：

```markdown
## 灰度发布

每次配置变更分四批生效，每批观察 10 分钟，**指标正常**才进入下一批。

| 批次 | 范围 | 进入下一批的条件 | 不满足时 |
| --- | --- | --- | --- |
| 1 | 内部集群 | 错误率不高于变更前 | 自动回滚 |
| 2 | 1% 实例 | 同上，且 P99 延迟不升高 | 自动回滚 |
| 3 | 10% 实例 | 同上 | 自动回滚并通知负责人 |
| 4 | 全量 | — | 人工决定是否回滚 |

判定阈值见附录 B。
```

## 先写速读层，再填细节

1. 写标题、首屏和全部 H2 标题，每个 H2 只写第一段。
2. 运行 `python3 scripts/doc_check.py <doc.md> --skim`，只读输出的“速读层”，回答：做什么、为什么现在、主干怎么做、代价和风险是什么、要读者决定什么。答不上来，先改这一层。
3. 速读层成立后，再在每章首段之后填依据和细节，长内容放附录。
4. 定稿前再跑一次 `doc_check.py`，处理提醒项或写明保留理由。

## 更新已有文档

先通读全文和图，写下每节承担的判断，再确定新事实影响哪些结论。只改受影响的部分，但交付前回看：前后是否矛盾、图和正文是否一致、同一事实是否重复解释、已决定的内容是否需要标成待复核，而不是静默改掉。

更深的读者测试方法（总览测试、主线测试、随机章节测试）见 `human-reading.md`，高风险方案和正式评审时使用。
