# 技术文档共创流程

共创是 `engineering-docs` 的一种工作方式，不是另一项技能，也不是每次写文档都要完整执行的仪式。

## 默认直接推进

上下文足够时，直接完成取证、判断、起草和验证。不要先让用户选择“自由模式还是共创模式”，也不要机械询问文档类型、读者、目标、模板和约束。

只有缺失信息会改变核心判断时才提问。能从已有文档、代码、配置、日志、接口或项目历史中查到的内容，先自行读取。

## 何时进入共创

命中下列情况时，增加与用户的往返：

- 用户明确说“一起写”“边聊边改”“先对齐再写”。
- 目标读者、期望动作或文档边界存在歧义。
- 核心方案仍有多个真实选择，需要用户参与取舍。
- 现有材料相互冲突，无法自行确认权威来源。
- 文档影响跨团队协作、高风险发布或不可逆决定。

共创深度跟随风险和不确定性。局部、低风险更新不升级成完整工作坊。

## 收集上下文

先建立内部文档契约：

> 谁要读，读完要作出什么决定或完成什么动作，本文依据什么，覆盖什么范围。

随后按需读取：

- 用户提供的材料、链接和信息倾倒。
- 当前文档及其历史版本。
- 代码、配置、接口、运行证据和既有决定。
- 团队模板、术语和评审要求。
- 时间、组织和依赖约束。

把已确认事实、推导、假设、决定和待确认项分开记录。默认不把这套内部分类印进正文。

提问遵守三条：

1. 先读现有上下文，再问无法自行确认的内容。
2. 一次只问会改变当前决定的最少问题。
3. 给出候选答案或当前默认假设，让用户能短答，而不是重新讲一遍背景。

当已经能讨论边界、取舍、异常和验收，而不再需要追问基础概念时，结束上下文收集。

## 形成和打磨正文

先处理未知最多、最影响结论的部分。技术方案通常先确定核心建议和关键设计，再写摘要；更新已有文档时，先通读全文和相关图，再改受影响章节。

有真实选择时：

1. 列出可行候选和统一比较标准。
2. 让用户确认决定性约束。
3. 写出选择、拒绝理由和接受的代价。

没有真实选择时，直接说明约束如何收敛方案，不凑候选。

分段共创时，每轮只推进一个明确问题：

- 这一节需要读者回答什么。
- 现有内容缺什么或重复什么。
- 本轮建议保留、删除或合并什么。
- 修改后是否改变其他章节、图或结论。

不要默认生成 5–20 个脑暴选项。只有用户正在探索方案空间时才提供候选；数量服从真实选择，不服从模板。

用户反馈可以是自然语言，不要求按编号回复。收到反馈后做局部编辑，再回看全文骨架，避免补丁叠补丁。

## 更新已有文档

更新模式先做四件事：

1. 通读全文、图表和附录，概括每节承担的判断。
2. 确认新事实或新要求改变了哪些结论。
3. 列出直接修改点和受影响的下游章节。
4. 只改必要部分，再全篇检查一致性、重复和失效内容。

已决定或已实施的方案出现可能推翻原决定的新事实时，不静默覆盖历史；按 `decision-model.md` 进入待复核或被取代状态。

## 独立读者测试

成文后，把文档交给没有参与前文讨论的读者或干净上下文，只提供文档本身。至少验证：

1. 问题和关键证据是什么。
2. 建议做什么，为什么。
3. 适用边界和接受的代价是什么。
4. 具体改哪里，风险和依赖是什么。
5. 如何验收，失败后如何恢复。

测试前先锁定标准答案。读者答错时，判断是文档缺口、歧义还是事实本身未确认，再回到对应位置修正。

独立读者测试证明文档可理解，不证明技术事实正确。

## 协作收口

交付时说明：

- 当前文档状态。
- 已关闭的核心决定。
- 仍会影响实施的待确认项。
- 证据和图源位置。
- 下一位读者或责任人需要做什么。

用户不需要看到共创步骤、问题清单、脑暴过程或内部门禁，除非明确要求审计。
