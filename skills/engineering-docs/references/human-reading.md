# 面向人类阅读

> 默认写作规则、预算和改写示例见 `writing-contract.md`。本文是结构树和分层读者测试的深入说明，高风险方案和正式评审时读。

技术文档先帮助读者建立整体模型，再让他沿模型选择性下钻。完整不等于平铺；一份好方案应当是一棵可以逐层展开的树，而不是从头读到尾才显出形状的长链。

## 先做阅读地图

写正文前，先在内部回答：

```text
一句话主张：读者只记住一句，应该记住什么？
为什么现在做：哪项事实或风险推动这个决定？
边界：当前版本做什么，明确不承诺什么？
总体模型：有哪些工作线、组件或阶段，各自负责什么、如何关联？
读者动作：看完需要批准、选择、补证还是执行什么？
章节树：总体节点分别由哪一章展开，横切章节连接哪些节点？
章首摘要：每章在全局中的角色、结论、边界和子结构是什么？
下钻去向：接口、字段、完整证据和测试矩阵分别放哪里？
```

先确认这些答案构成一棵无环、无孤儿的结构树，再写内容。完整性检查用于防漏项，阅读地图用于安排先后和轻重；不能把决策记录的字段顺序直接当正文目录。

## 总体模型必须先于局部细节

复杂技术方案在进入组件、工作线或算法细节前，先给 Level 1 总览。总览可以是架构图、流程图、结构树或紧凑表格，但必须说明：

- 方案由哪些顶层节点组成。
- 每个节点负责什么。
- 节点之间是调用、数据、依赖、先后还是并行关系。
- 哪些节点会在后文展开。
- 最终怎样汇合成当前决定、交付或运行结果。

系统或 SDK 设计默认用目标架构图；迁移方案可用阶段图；多条治理工作线可用关系图或带关系的结构表。局部单点改动如果两三段就能说清，可以声明不需要独立总览，但仍要用一句话说明整体改动模型和豁免理由。

总览必须解释方案，不能只是目录或几个并列名词。“调用链”只有在它同时说明目标方案的职责和关系时才算总览；只描述现状问题链路，不算方案总览。

## 正文章节必须由总览派生

总览中每个需要展开的核心节点，对应一个主章节；章节名称与节点名称保持相同或可直接追踪。发布、验收、风险等横切内容可以单列，但要说明它连接哪些节点。正文不能另起一套与总览无关的分类。

每个主章节先用黑盒摘要回答：

```text
它在整体方案中负责什么
本章的核心结论是什么
输入、输出和边界是什么
哪些子节点值得继续展开
```

然后才进入白盒细节。某个节点内部确有多条支线时，先给本章子结构，再让 H3 与子节点对应。子章节继续遵守“先概括、再展开”；只展开重要、复杂、高风险或容易变化的节点，普通实现保持黑盒。

同级节点处于同一抽象层，并按一种逻辑排序：结构、运行顺序、因果、优先级或时间。不能把组件、风险、类名和里程碑混成同一层。

## 第一屏、正文和附录是树的不同视野

三个阅读区域继续保留，但服从同一棵结构树：

| 区域 | 读者得到什么 |
| --- | --- |
| 开场与总览 | 为什么做、目标与边界、Level 1 总体模型、当前动作 |
| 正文主线 | 总览节点的黑盒说明、关键关系、取舍、风险与交付闭环 |
| 实现附录 | 选中节点的白盒细节、接口、字段、算法、证据、测试矩阵与工作包 |

第一屏不再机械塞满所有决定、术语和未决问题。它先建立方向，并在紧邻位置给出总体模型。读者看完开场和总览，应能画出或复述全文结构。

正文只保留会改变决定、职责、主流程、失败行为、风险或验收的内容。完整接口、字段、算法、原始证据和全量测试进入明确命名的附录或权威链接。链接用于复查，不承担主线解释；不打开链接也能理解方案。

一个结论在总览、正文和小结重复出现时，总览保留短结论，正文只补依据和影响，不再换词复述。高风险只要求控制和失败行为留在正文，不要求把所有实现提前。

## 标题和段首必须提供导航

H1 和 H2 用稳定、简短的节点名称，说明“这一部分是什么”；需要时加冒号和不超过 12 字的判断，让只看目录的读者也能跟上过程，例如“灰度发布：先内部再全量”。完整结论放在每章第一段，不把整句判断塞进标题：

| 不合适 | 更合适 |
| --- | --- |
| 三条线 | 总体方案 |
| 客户端在外部扫描前恢复观察状态并保护后续上报 | 客户端兜底链路 |
| 数据侧只放保守种子，污染期结果继续隔离 | 数据观察准入 |
| 10 月 10 日冻结基线档或增强档 | 发布范围与排期 |
| 详细说明 | Manifest 晋升契约 |

H3 可以在清晰的父章节中使用“输入”“模式”“并发约束”等局部短标题；离开父章节会产生歧义并不构成问题。H1/H2 必须能从总览定位，孤立标题必须自解释。

章首摘要先概括下层，再给细节。不要让读者先记住一串前提，最后才在章末发现这部分为什么存在。

## 专业术语保留，但第一次要解释

“说人话”不等于替换准确术语。技术名词保留原词，在首次影响决定时用一句话说明它在本文中的作用：

例如文档第一次使用“观察开关”和“候选清单”时，要分别说明它们控制什么行为、包含哪些版本与校验信息。

缩写、内部代号和模式编号不能只在后文定义。总览使用它们时，就近给出最低解释。避免用“冻结、探针、门禁、收敛、抓手”等过程词制造专业感；它们只有在团队或系统中确有稳定定义时才保留。

## 高亮只标真正的优先级

- 首屏一个主结论引用块；每章最多一个引用块（结论/待拍板/前提），不叠加第二块长结论。
- 重点词可加粗，整段粗体会失去层级。
- 表格用于比较同构信息；顺序用有序列表，并列用无序列表。格式选择见 `formatting.md`。
- 图只在关系难以用短表表达时使用，并放在对应判断附近。
- “注意”“重要”“必须”不能遍地出现。多个强提示并列时，先判断它们是否真的同级。

## 详略用“是否改变行动”判断

每段细节都问：

> 删除这段后，评审者会不会改变决定，实施者会不会误解职责，风险会不会漏控，验收会不会失真？

- 会：留在正文，但先写结论再展开。
- 只影响实现者：放实现附录。
- 只用于复核事实：放证据附录或权威链接。
- 不影响任何行动：删除。

`writing-contract.md` 的字数预算是提醒线，用来发现没有分层的首屏和长段；某段细节是否保留，仍按上面的问题判断。压缩率只是结果，不是目标。

## 按结构层级验收

### 总览测试

只给读者开场和总体模型，让他回答：

1. 这份方案解决什么问题。
2. 顶层节点分别负责什么。
3. 节点怎样关联并形成最终结果。
4. 哪些节点会在后文展开。
5. 当前边界或读者动作是什么。

关键问题答错，正文不能进入正式评审。总览位于第一个 H2 时，测试范围应包含该节，不能机械截在第一个 H2 之前。

### 主线测试

只给读者总体模型、H2 和每章黑盒摘要，让他复述：

- 主章节是否与总览节点一一对应。
- 横切章节连接哪些节点。
- 每章的结论和子结构。
- 哪些内容保持黑盒，哪些可以继续下钻。

总览节点在正文消失、正文出现孤立主章节，或每章必须读完才知道结论，都算失败。

### 随机下钻测试

随机选择一个总览节点，只给总览和对应章节。读者应能回答它的责任、输入输出、边界、子结构和下钻位置，不需要阅读其他章节或外部链接。

最后才读全文，回答事实、取舍、改造落点、风险、验收和回退。下层通过不能抵消上层失败。测试前锁定标准答案；修正后保留首次失败记录并做定点复验。

## 机器检查只管确定的部分

机器可以检查：

- 新版严格记录是否包含总体模型和章节树。
- 总览是否出现在组件细节之前。
- 总览节点是否都有责任和章节映射。
- 核心章节是否都能回到总览，横切章节是否声明支持对象。
- H2 是否在 H3 前有章首摘要，标题层级是否连续。
- 总览、主线、随机下钻和全文测试是否完成。

机器不能判断：

- 总体模型是否真的解释了方案。
- 哪些细节会改变评审决定。
- 压缩是否损失了关键事实。

这些仍由作者和独立读者按标准答案验证。机器校验用于拦住明显漏项，不冒充阅读质量评分。

## 方法依据

- [Minto Pyramid Principle](https://staging.barbaraminto.com/)：每层概括下一层，相关观点分组后上升到单一顶层主张。
- [C4 abstractions](https://c4model.com/abstractions)：系统、容器、组件、代码的逐级抽象。
- [arc42 Building Block View](https://docs.arc42.org/section-5/)：Level 1 总览、黑盒责任、白盒选择性下钻和局部结构树。
- [NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)：初始层足以完成主要任务，下钻入口必须可预期。
- [NN/g：Chunking](https://www.nngroup.com/articles/chunking/)：信息块要在整体中有明确含义，并用标题、摘要和视觉层级支持扫读。
- [NN/g：Information Scent](https://www.nngroup.com/articles/information-scent/)：标签和邻近摘要帮助读者判断信息价值。

这些资料提供人类阅读方法，不替代技术事实、风险控制和团队评审责任。
