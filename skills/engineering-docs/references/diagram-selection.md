# 选图：先认关系的形状，不靠卡片数量

**图型由读者问题决定，不由组件名或步骤数量决定。** 原生适用时优先 Archify；缺少的专用视图用改良旧后端兜底。能力差集与实际边界见 `diagram-capabilities.md`；维护旧 `.py` 仍沿用 `diagram_kit`。

## 先确定四件事

1. **读者的问题**：要看组成、过程、状态、数据流、归属还是变化？
2. **主路径和支线**：哪条路径承担核心解释，其他路径如何连接？
3. **分组与边界**：哪些是职责组、部署边界、阶段或说明，不能全部用同一种大框。
4. **保留的条件**：谁有写入权、何时分支、等待或回退，未知关系不补画。

## 按关系选型

| 读者要看清 | 图型 | 不能混同 |
| --- | --- | --- |
| 组成、调用、运行单元、部署归属 | architecture | 框有真实归属，不只用于排版 |
| 动作、条件门、并行、跨责任方交接、闭环 | workflow | 有返回不一定要时序图，有六步也不一定是长链 |
| 一次场景中消息按时间的交互 | sequence | 生命线不是架构包含层级 |
| 稳定状态与事件迁移、取消和终态 | lifecycle | 状态不是瞬时执行动作 |
| 数据来源、变换、存储与消费 | dataflow | 线写数据，不把依赖共现当数据血缘 |
| 实体、字段、键与基数／类关系 | erd／class | 不删字段或关系迁就空白与卡片数 |
| 单父级包含 | tree | 多父关系不能硬改成树 |
| 真实日期／耗时、重叠与嵌套 | timeline／waterfall | 没有时间依据不伪造比例排期 |
| 多维同构比较 | 表格 | 本来一张表就清楚时不重复画卡片 |

执行与准确Schema路径见 `archify-bridge.md`。单独维护旧版对应视图时读 `diagram-recipes.md`。

## 图文互补，不机械去重

- 表格已列对象时，图仍可表达对象之间的新关系；名称一一对应不自动算重复。
- 如果只把表的每行改排成一张卡，没有关系、比较或定位增益，就保留表。
- 目录树已解释结构时，另图应解释谁写、谁读或运行关系，不再画同一清单。
- 一篇方案可有多张同类结构图，只要回答不同抽象层或不同问题；不要为了图型多样性换错图。

## 结构优先于样式

先选择主轴、分支、层级、回路或时序；再决定Group、色面、开放分栏和边框。良好的色面与对齐可以表达分组，不必处处套完整灰框。

- 拒绝把所有东西默认画成「分区＋等大白卡片＋折线＋三张结论卡」。
- 也不禁止矩形：矩形真正表达阶段、实体或边界时是合理的。
- 注释就近放置，长说明进正文；图例只解释编码，不代替实际关系。
- 旧引擎小改改善外观，不保证固定布局支持任意拓扑。类型能力缺口可以兜底；原生输入或执行失败必须明确处理，不能随意改图或删信息。
