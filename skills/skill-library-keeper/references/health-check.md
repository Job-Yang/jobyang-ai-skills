# 技能库健康体检

> 先跑 `scripts/library_doctor.py <库目录>` 做静态扫描，再人工补脚本看不出的判断。
> 产出统一是「问题 → 证据（文件:字段）→ 建议动作」清单；合并/删除/改名等动作需用户拍板，工具只报告不改文件。
>
> **一句话分工：机械的归脚本，语义的归人工，动态的归 Harness。**

## 规则分三层（不假装有静态能查一切）

| 层 | 谁来做 | 内容 | 可靠性 |
| --- | --- | --- | --- |
| **静态 P0/P1/P2** | `library_doctor.py`（纯标准库、零依赖） | 文本可判定的格式、引用、结构、绑定、密钥 | 有正反夹具证明，规则稳定 |
| **语义 P3** | 人/LLM 改技能时过一遍（本文件清单） | 退出条件、有限重试、可观察触发、选项默认、规则矛盾、双要素质量 | 正则不可靠，业界明确说不该硬写正则 |
| **动态** | Harness / 真实运行 | 真实触发率、乱触/漏触、文件实际读取顺序、端到端成功率 | 本技能坚决不做 |

## 一、静态规则（脚本，带稳定 ID）

跑法：

```bash
python3 scripts/library_doctor.py <技能库目录>            # 文本报告，有 high 问题时 exit 1
python3 scripts/library_doctor.py <目录> --json           # 机器可读
python3 scripts/library_doctor.py <目录> --save-baseline baseline.json   # 存现状
python3 scripts/library_doctor.py <目录> --baseline baseline.json        # 只报基线外新问题
```

基线用法（推荐）：当前库存量问题先 `--save-baseline`，以后日常只让**新增**问题冒头，不被存量淹没。
随包带了一份 `baseline.json`（26 技能现状），日常用 `--baseline` 跑即可。

### F 类 · frontmatter 与命名（P0 硬错误）

| ID | 判什么 | 修复 |
| --- | --- | --- |
| F001 | 缺 name | 补 frontmatter name |
| F002 | name 非法（非 `^[a-z0-9-]+$`、>64 字符等） | 改名 |
| F003 | name 含保留词 anthropic/claude | 改名 |
| F004 | name 与目录名不一致 | 统一 |
| F005 | 多个技能重名 | 消歧 |
| F006 | frontmatter YAML 非法/未闭合 | 修 YAML |
| F007 | 出现非常用 frontmatter 字段 | 确认宿主支持，否则移入 metadata |
| F008 | 缺 description | 补「做什么+何时触发+不适用」 |
| F009 | description >1024 字符 | 细节移正文 |
| F010 | description 含 `<` `>` | 去掉（会和标签冲突） |

### D 类 · description 路由质量（P1，决定技能会不会被正确触发）

| ID | 判什么 | 说明 |
| --- | --- | --- |
| D001 | description 过短（<60 字） | 太短难承载「做什么+何时触发+边界」 |
| D002 | 缺「何时触发」信号 | 路由只看这一行；中文「时使用/…时调用/当…用/不适用」都算 |
| D003 | 缺引号包裹的用户原话样例 | 加 1-3 个真实触发短语（当前库存 11 条，已入基线） |
| D004 | 正文与 description 都没有边界 | 边界至少要在路由行出现一次（不适用/不做/区别/分别走） |

> 判法刻意宽松：中文技能常用「时使用」「不做」「只用于」，且路由信息本就集中在 description，
> 不要求正文再重复一遍。长短只是表象，真正要的是「双要素 + 具体触发短语」。

### R 类 · 引用完整性（P0/P1）

| ID | 判什么 | 边界（避免误报） |
| --- | --- | --- |
| R001 | SKILL.md 正文引用的本地文件不存在（broken reference） | 只看正文 markdown 链接，去掉代码围栏里的命令；剥掉 `#锚点/?query` |
| R002 | SKILL.md / references 的代码围栏未闭合 | 只查 SKILL.md 与 references/，不查 tests/fixtures（负例夹具本就故意坏） |

### C 类 · 库级覆盖（P1，站在整版图上找"洞"）

单个技能的边界各自都对，拼在一起却可能围出一类**谁都不接**的真实任务——单技能体检发现不了。

| ID | 判什么 | 边界（只给线索，不替模型下结论） |
| --- | --- | --- |
| C003 | **覆盖真空**：≥3 个技能都碰到同一交叉地带（当前词表聚焦「源码/仓库调研 × 还要落成文档/分享」）却都排除/指走，且没有技能正面认领 | 技能级判定，阈值 ≥3 推走 + 0 认领；**必须人工用真实 query 核对** |
| C001 | **悬空技能交接**：明确写「走/交给 xxx 技能」，库里却没有 xxx | 要求同句出现「技能/skill」、目标无扩展名/路径，避免把 `backends.md`、`config` 当技能；外部/宿主技能走脚本白名单 |

> 真实案例（ponytail 调研）：feynman 把"调研成稿"推给 talk-smith，talk-smith 只接对外传播，
> engineering-docs 排除"没形成工程决定的调研"，cuihuo 只写对外观点——围出
> **「对内的源码/仓库深度调研还要落成文档」这个真空**，模型只能退回 lark-doc 等"工具人"，
> 协作技能一个没命中。修法是让 feynman 明确正面认领内外部调研成稿。
> 静态只提示"疑似真空"，是不是洞靠人工拿真实 query 判断；扩展交叉地带改脚本 `COVERAGE_VACUUMS`。

### P 类 · 平台可迁移性（P0/P1）

| ID | 判什么 | 边界 |
| --- | --- | --- |
| P001 | SKILL.md 正文写死绝对路径/宿主目录（/Users、/home、C:\、.doubaowork 等） | **只扫正文、不含代码块**；README 安装示例、CHANGELOG 变更记录、可移植性文档里的拷贝命令不算 |
| P002 | 引用了平台专属工具但没写「缺失则降级」 | 提示人工确认是不是软依赖 |

### S 类 · 结构与卫生（P2，低优先）

| ID | 判什么 | 边界 |
| --- | --- | --- |
| S001 | SKILL.md 正文 >500 行 | 建议下沉 references/ |
| S002 | references/ 下 >200 行且顶部既无锚点目录也无分节标题 | 有清晰 `##` 分节即放行；不查 README |
| S004 | reference 全技能没有任何文件点名（真孤儿） | 二级 reference（被别的 reference/脚本引用）是正常渐进披露，不算 |
| S005 | 技能根目录散落 example/sample/template 命名的空壳文件（<40 字节） | 正常模板库、测试夹具不算 |
| S006 | 疑似硬编码密钥 | 排除 tests/、fixtures、test_*.py（负例里会故意放假密钥串） |

> 已**下线**的旧规则：S003（reference 嵌套不超过一层）——违背正常渐进披露，实测全是误报；
> T001（关键词撞车）——靠正则猜意图分不清「精读/抉择/拆解」这类跨技能通用方法词，实测 8 条全误报。
> 这两件事移到下面的人工/动态层。

## 二、语义项（P3，只进人工清单，不写正则）

改/收技能时，由人或 LLM 对照下面逐条过，脚本只在报告结尾提示「以下需人工」：

- **退出条件**：有没有写清什么情况下停下、不硬撑。
- **有限重试**：外部动作失败时是否限制重试次数、不无限刷。
- **可观察触发**：description 里的触发短语是不是用户真会说的话，而不是自造术语。
- **选项有默认**：需要选择时有没有合理默认，不把小决定都抛给用户。
- **术语一致**：同一个概念在相关技能里用词是否统一。
- **规则矛盾**：相关技能对同一件事是否给出互斥指令（例：一个默认输出某平台文档、一个禁止默认绑定平台）。
- **一句话唯一性 / 定位漂移**：技能有没有在迭代中不断加功能、逐渐和邻居重叠。
- **触发撞车（替代旧 T001）**：不用关键词猜，攒一批**真实 query** 做盲测，统计两个技能是否都被激活、边界是否写清。

## 三、动态项（归 Harness，本技能坚决不做）

真实触发率、乱触/漏触率、文件被实际读取的顺序、端到端成功率、跨天稳定性——
这些只有在真实任务里埋点才测得出。本技能只在文档里写清边界，不假装静态扫描能覆盖。

## 四、先证明体检有效，再拿去修库

脚本的可信度由正反夹具保证（`scripts/test_doctor.py`，零依赖、临时目录、自动清理）：

- **正例零误报**：一个完全合规的技能，跑完必须一条不报（否则规则会冤枉好技能，不可信）；
- **反例全命中**：每类坏样例（坏 name、无 description、保留词、broken ref、硬绑定、超长、围栏未闭合、
  孤儿、假密钥）必须命中对应规则 ID。

跑：`python3 scripts/test_doctor.py`。**跑不过夹具，就不能拿 doctor 去修技能库。**

## 五、体检报告格式

```text
库根目录：……（如何发现/传入）  技能数：N
[严重度 规则ID] 问题 | 证据（文件:字段） | 建议动作
汇总：按 ID 计数
结论：体系健康度判断 + 最该优先处理的 1-3 项
（静态之外，另列 P3 待人工项；动态项提示归 Harness）
```

体检后若新增/合并/删除技能，记得更新库的关系图与分发位置（同步由库的同步脚本负责，本技能不执行）。
