# 准入闸门：要不要为它做一个新技能

> 五问全部通过才建。任一问答"否"，输出「不做的理由 + 已有的正确承接方」。判不准则记观察项，等真实需求反复出现。

## 第 1 问 · 需求成立吗

满足任一即可，但必须能举出真实场景：

- **高频反复**：这件事在你（或目标用户）的工作里经常出现，每次都痛。
- **低频高重要 + 长期解决不了**：频率不高，但一旦发生影响大，且现有手段长期拿它没办法。

不满足的典型："看到一个 prompt/技能觉得不错""好像以后可能用得上""听起来很高级"——这些是灵感，不是需求。

## 第 2 问 · 这个问题该归因到哪一层

先别假设"要加技能"。问题可能出在不同层，解法不同：

| 层 | 典型问题 | 正确解法 |
| --- | --- | --- |
| 模型能力 | 模型本身理解/生成不到位 | 更好的提示、换模型、拆步骤，不是建技能 |
| Harness 常驻规则 | 每次交互都要守的姿态/规矩（如提问节制、完成验证） | 进宿主的常驻规则/门禁，而非常驻技能 |
| 工具/脚本 | 需要确定性计算、读写、检索、外部系统操作 | 写工具脚本，技能只负责调用 |
| **技能方法层** | 有一套可复用的判断与流程、按需才需要 | **这才是技能** |

只有"该归技能层、且现有技能接不住"才继续。

## 第 3 问 · 业界/现成方案能不能直接用

先找现成的，按三档决策（不许跳过评测直接重造）：

1. **直接用**：质量够、可迁移、和现有不冲突 → 用，不复制轮子。
2. **炼化**：方法好但带平台绑定/风格不合 → 剥掉宿主专属部分，保留内核改成自有。
3. **重造**：评测证实有硬伤才自研。

评测要落到具体问题：它会不会改原意、降低准确性、编造事实、覆盖不到关键场景。

## 第 4 问 · 值得独立，且不与现有技能打架

- **一句话唯一性**：能用一句话说出它解决、而现有技能都不解决的问题吗？
- **同一件事检验**：它和某现有技能是"同一问题的不同流程"（→ 合并/吸收），还是"不同问题"（→ 可独立）？
- **流向图检查**：放进技能库关系图，看上游任务源、下游产出、共用枢纽；会不会两个技能对同一句 query 都触发？规则是否冲突、结论是否互相矛盾？

## 第 5 问 · 能持续变好吗

- 先定**成功判据**：做完怎么知道它真解决了痛（最好可观测）。
- 预留**评测/召回回路**：技能不可能一次满分，要有办法收集坏 case、定期回归（如写作类技能配评测台）。
- 明确它的**降级方式**：缺平台工具时怎么不阻塞。

## 范例：haohao-shuohua「好好说话」为什么被造出来

1. **需求极大**：文字创作是每个人每天都做的事；AI 写的文档 AI 味重、绕、不说事实，读者头大，还得人工返工——非常痛且高频。
2. **现成方案评测不达标**：业界 GitHub 上有去 AI 味/说人话工具，但评测发现它们为了口语化加入很多随意表达，某些场景反而降低文字准确性，甚至**凭空添加原文没有的意思、改变原意**（几万 star 也有这硬伤）。
3. **不得不重造，且先挖根因**：先剖析"为什么会有 AI 味"，追溯到语言学根源（对应那篇《为了去 AI 味，我翻回了 100 年前的语言学》），在理解机制后才动手，而不是调语气。
4. **承认不完美、配迭代闭环**：haohao 只能解决大部分问题，于是又有了基于每日召回/回归的 haohao-eval，用真实 case 长期纠偏。

这个范例说明：**技能产生于"高频痛点 → 分层归因 → 评测现成方案 → 证明非重造不可 → 预留迭代"，不是产生于"这个 prompt 看起来有用"。**
