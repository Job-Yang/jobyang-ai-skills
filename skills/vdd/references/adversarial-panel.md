# 多角色干净上下文对抗评测（按需查阅）

> 适用场景：对完整系统、工作台、插件钩子、多技能协同链路或高风险大改造做「客观找错与盲区排查」，避免作者在原对话里陷入自我确认偏误。单个需求或未动工的 Spec 对抗仍优先走 `spec-battle`，日常 PR 审查仍走 `diff-review`。

## 一、核心铁律（假独立无效）

1. **绝不延续作者上下文：** 每个评测角色都必须是**全新、无前置讨论记忆**的只读子代理，绝不 `fork` 原对话，也不向其传递作者的辩护理由、实现心路或自评结论。
2. **只认现行真实证据：** 只允许评测角色读取当前工作区里的真实源码、文档、配置与运行输出；任何问题都必须附带精确「文件位置 + 触发输入 + 实测或实读后果」。
3. **禁止为了显得严格而硬凑：** 未发现真正的问题时，明确签收「未发现可复现缺陷」，绝不硬编低价值格式挑刺。

## 二、标准 `3+1` 互斥评审团分工

当宿主支持多子代理时，按下面分工并行派发只读评测，再由独立裁判收敛（无子代理宿主可切换干净新会话按同一清单顺序自检）：

1. **角色 1 · 冷启动挑刺用户（体验与流转视角）**：
   - 不看实现者意图，只拿普通用户的日常大白话、改主意回流、多文件并行、中途切换工具或跨宿主迁徙场景去撞系统；
   - 专查：该触发时没接住、不该拦时乱弹窗、交接文档缺字段导致下一环断链、或文档与实际脚本行为打架。
2. **角色 2 · 红队破坏者（对抗与安全视角）**：
   - 假设输入和环境都不老实，专门构造绕过条件和极端边界去撞防线；
   - 专查：命令变形绕过危险拦截、路径拼写或软链绕过写锁与只读护栏、并发或中途失败污染状态文件、异常字符或敏感信息泄漏、多语言工程识别漏网。
3. **角色 3 · 怀疑论事实裁判（Skeptic Judge · 去误报收敛）**：
   - 汇总前两个角色的全部异议，切换为「专职证伪者」逐条回读仓库真实源码与配置核实；
   - 凡已被外层防线拦住、文档明确写定的预期边界或现实无法触发的猜测，一票剔除并写明核查依据；
   - 最终仅保留确凿问题，按「P0 必修 / P1 建议修 / P2 观察项」输出客观事实裁决清单。
4. **角色 4（可选 · 技能或提示词改动专用）· 强弱双模对照**：
   - 改了技能规范或钩子规则后，用强模型与较弱模型分别跑相同中性题与对抗边界题，验证新规则没有压低强模型上限，也没有因措辞含糊让弱模型掉底线。

## 三、有界收敛与交付

1. **最多一轮修复收口：** 依据 Skeptic 裁判确认的 P0/P1 事实清单完成修复与回归测试，对已修项做一轮针对性复核即收口；若暴露出跨架构大改，停下来带证据请人拍板。
2. **标准交付结构：** 向用户汇报时分三块写清——① **裁决保留项**（级别 + 位置 + 实证后果 + 修复结论）；② **已修并复核绿灯项**；③ **被 Skeptic 剔除项**（原异议 + 回读源码确认的误报理由）。
