# VDD · 代码终审与大改动防漂移

专职守好工程验证与大改动评审的两道防线：**未拿同场景实测证据前不报喜，对照清晰边界确实合格时敢明说「符合设计，不用改」**。

## 一 · 职责与邻近技能边界（不越权）

| 需求类型 | 归属 | 说明 |
| --- | --- | --- |
| 宣称完成前的实证门禁与跨轮防过度重构 | **本技能** | 独立核验证据模态、对照任务契约并守住不改边界 |
| PR/MR/分支/未提交 diff 的只读 Code Review | `diff-review` | 规模风险分级、Skeptic 去误报与审人评论草稿，不归本技能 |
| 报错、崩溃、回归缺陷的红灯定位与修复 | `code-bugfix` | 建秒级红灯复现回路、3 假设停损与红→绿回归测试 |
| 外部说法、统计数字、行业资料核真 | `claim-check` | 需外部一手检索与可信度定级，不归本技能 |
| 重大决策前的多源外部证据与反例调研 | `outside-view` | 开放检索预算与冲突裁决 |
| 尚未实现的假设、低成本可逆试错方案 | `minimum-experiment` | 控制变量与继续／停止阈值设计 |
| 工程技术方案（RFC / ADR）评审与出图 | `engineering-docs` | 方案架构、风控矩阵与 G0–G12 评审 |

**豁免不启用：** 纯闲聊、翻译、只列清单而不下工程判断、以及只改 1–2 处笔误的小编辑，直接交付，不跑完整门禁。

## 二 · 单次工程自证（证据模态必须匹配）

1. **先查隐藏前提与失败边界：** 确认用户前提是否成立、还缺哪项关键事实、这类改动常见坑在哪。
2. **改动有据且标清未改边界：** 大改动说清「改了什么（文件与动机）」以及「相关但确认不用改的地方」；拿不准时标清「这是推断，未实测」，不把猜想当观测结果。
3. **选对验证工具才算真验过：**
   - 验证数据或行为正确性 → 看运行日志、单测与真实命令输出，不凭源码措辞脑补通过；
   - 验证 UI 与排版 → 看真实渲染截图，不拿 grep 搜类名替代；
   - 核对关键四项 → 时间对应、范围覆盖全、机制说得通，且在重要改动上具备对照或反证；外部不可见环境如实写明「受限未覆盖范围」。
4. **有界收敛（最多 2 轮）：** 内部复核最多跑 2 轮；两轮仍卡在缺失环境或外部未证实假设时，诚实汇报阻塞点与未验项停手，不无限自我怀疑打转。若宿主具备干净上下文（如独立验收子代理），优先用只带「产物 + 验收口径」的干净视角复验，不把先入为主的推理链带过去；对完整系统、工作台、插件或整套技能做客观找错时，可按需查阅 [多角色干净上下文对抗评测](references/adversarial-panel.md) 启动独立角色评审团并经 Skeptic 事实核查收敛。

## 三 · 多轮大重构防漂移与终审裁决

跨多轮对话或大型重构时，**在动手前定一份简短任务契约**（防止目标随对话悄悄漂移）：

- **核心目标：** 1–3 条可验证结果；
- **关键方案选择：** 标明用户拍板项 vs 已有证据项；
- **明确不改边界：** 这次不碰的模块、接口或风格（越界即为过度修改）。

**终审与代码 Review 只有三种裁决：**

1. **符合设计与边界 → 明确说「符合设计，不用改」：** 绝不为了显得勤奋硬凑挑刺或强行重构合理代码。
2. **偏离预期或存在真实缺陷 → 给具体文件、行号与复现证据后修正：** 对应真实缺陷、回退或回归风险直接修好并重验。
3. **需求或约束超出原有契约 → 先对齐 3 条核心验收口径或与用户确认后再动：** 对存量开放式代码评审，先对齐验收基准再下判断，不以「缺预写文档」为由僵硬拒审。
