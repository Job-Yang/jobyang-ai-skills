# 分享实践分支（sharing）· 真实人味的技术分享写法

> **核心定位**：写给人看的经验分享、项目复盘、动手实录、工具安利与方法论传播。好分享不是套固定模板填表，而是像把工位旁同事拉过来看你的屏幕——讲清你真撞过什么墙、试过哪几步、拿到了什么结果、还有哪块没搞定。

---

## 一、六条高杠杆写作内核（来自真实高赞分享稿与工程博客共识）

1. **真问题驱动的发现弧（不报流水账）**
   按「撞上什么真问题 → 怎么想假设、拆办法试 → 跑出什么真实效果 → 又冒出什么新卡点」往前推。避免按「模块一 / 模块二 / 总结」做功能说明书——检验标准很简单：**抽掉中间一节，后面的因果还接不接得上？接得上说明写成清单了。**

2. **具象画面先于抽象判断（先甩现场，再拎一句 Learning）**
   不从「随着 AI 发展」「在当今工程中」入场，也不用抽象概念词堆砌。先扔具体现场：几段刺眼的反例原文、翻车时配了个多滑稽的音效、一组反常数字或三键小键盘照片（仅用输入里真实给过的现场、数字或反例；素材没给具体故障症状、页面名或版本起因时，直接从输入事实与公开工程机理切入，绝不为求画面感杜撰不存在的现场细节），再给出判断或 `Learning` 高亮锚点。**需要讲原理时，先用一两句话写清工程事实、实际步骤与适用边界，必要时再补一句通俗类比帮读者抓画面**，绝不拿比喻顶替机制。

3. **短段快呼吸 + 视觉间歇（给人扫读，不让人啃字块）**
   屏幕阅读最忌密密麻麻一整片文字墙：正文段落精干利落（通常 `50–120` 字，单段保持 `≤ 150` 字，一段讲清一件事），中间靠对比表、分点清单、核心引语/高亮块、代码或流程图锚点切开节奏。配图时在图旁附一句「这张图在看什么」。**篇幅服从内容真实信息量**：轻量安利千把字讲完就收，年度大复盘写五千上万字照常展开，不凑字数也不硬卡上下限。

4. **工位同事口吻与带呼吸感的小标题**
   拿平等聊天的口吻推进，用主动动词和直白短句，允许穿插「还真挺好玩」「给我听嗡嗡的」「好了，说点实践」这类自然人味，但**口语化不等于留错别字、重复词或乱码，也绝不写成自媒体标题党或口水感叹**（如「拿到的战果」「泼了一盆冷水」「理想很丰满，现实有边界」），平实直给比抖机灵更有同事感。章节 H2/H3 **不强制死板名词目录**——顺着思路自然使用直白发问（「前端为啥写得好？」「为什么非得用 Agent？」）、阶段小结论或轻快转场（「道理我都懂了，说点实际的」「当然，也有没搞定的」），能直接牵着读者往下读。轻松自嘲只从真实踩坑里顺手带出，**不设字数配额凑梗**；严肃事故复盘与官方发布场合保持平直克制，不做俏皮。

5. **真诚亮未完与边界，适度借外部锚点抬升视角**
   真没跑通、真靠半自动兜底、真绕过弯路的地方，如实摊开并写清「路虽没走完，但留下了什么」；不把未提及的私有脚本或假翻车桥段硬编进文章。做完具体经验沉淀后，在合适位置自然接一句外部权威证据、工程论文或行业共识，把一件事的折腾升华成同行也能共用的规律。

6. **结尾给出能带走的东西，不停在正确废话**
   用「如果你也想动手试，先改这一步」「如果再做一次，我会把这几件事前移」或几句沉甸甸的真实收束落地。跳过「以上就是我的全部介绍」「希望对大家有所帮助」类礼貌空话。

## 二、四类常见题材的松散组织法（参考思路，按材料裁剪）

| 题材 | 起手切入 | 主干推进 | 自然收尾 |
|---|---|---|---|
| **① 专项 / 年度复盘** | 可选 2–3 条按内容实词命名的紧凑 TL;DR（不套「这篇讲/最后引出」固定五字段），快速交代背景痛点 | 先亮真实成效或关键卡点 → 分阶段讲怎么一步步逼出解法（配高亮 `Learning`）→ 如实摊开局限与未解之题 | 提炼可跨项目迁移的方法原则 + 3–5 步立刻能试的动作 |
| **② 动手体验实录** | 先晒做出了什么（图/指标/链接），直接正面回答读者最关心的可行性结论 | 按真实打磨遇到的问题逐层展开：怎么对齐预期、哪个地方调不顺、加了什么新系统补闭环 | 「如果再做一次」前移清单 + 冷静期待或余韵句 |
| **③ 轻快工具 / 新做法安利** | 拿熟梗、反差画面或一句话疑惑直接破题 | 一句话点透核心收益与为什么现在终于好用了 → 晒真配置实拍 → 顺手答掉同行最疑虑的 `2–3` 个问题 | 零门槛渐进上手路径（先免费试哪个，再按需升级什么） |
| **④ 原理溯源 + 方法论传播** | 开篇先扔一串读者日常天天见到却说不清哪怪的典型症状/反例 | 先立住全篇唯一的中心概念词 → 讲清来龙去脉与背后机制 → 正反对照 + 一条能照着做的短流程 | 回到本质边界（工具帮你跑清单，最后靠什么真落地） |

> **分流提醒 · 遇到纯业务数据专题怎么办**：如果材料本身是一份「口径定义 + 多维切片数据 + 对照实验表 + 策略建议」的内部数据专题（不需要个人实战叙事），别硬套故事弧，直接采用「结论先行高亮块 + 口径定义 + 分维度论据表 + 策略建议」的汇报形态，或交 `engineering-docs` / `feynman-explainer` 处理。

> **默认图文成稿形态**：1 个简练 `#` 一级主标题（不照抄提示词原话、不夸大越界） + 开篇 1–2 短段亮背景与核心结果 + 3–4 个 `##` 章节按因果推进（每节用公开工程机理讲实「旧路为何挂、新路每步解决什么卡点、做不到的边界为何卡住」，不写成单薄一句提纲） + 实操收尾。交稿前逐句通读消掉病句与错字，并过 `haohao-shuohua`。

## 三、口头分享与演示分镜、配图协同

- **输出为演讲稿（`talk`）或演示分镜（`slides`）**：按需读取 `references/sharing-formats.md` 获取时长语速换算、口播设问过渡与逐页分镜要点，无需在普通图文里套用口播规范。
- **按需配图（缺失不阻塞）**：需要把重点道理画成直观对比图、步骤卡或封面时，可选交 `content-infographic`（附锚定正文与过渡句）；需要严谨架构图、泳道图、复合看板或一页式图文速读页时，可选借 `engineering-docs` 的 `diagram_kit render`（正文仍归本分支，不套 RFC 门禁）；缺图工具时直接用表格、简明流程或精确文字讲透。

## 四、事实边界与交稿前检查

- **专业术语保留原词**（如 `Refactor`、`Prefill`、`TTFT`、`Context Rot`），不强行翻译成失真白话；同行已知词直接用，仅对跨领域关键概念补一句白话定位。
- **严分两类事实边界**：
  - **私有团队事实与项目经过**（内部脚本名、配置字段、私有路径、真实线上数据、具体页面或模块名、事故起因与故障现象、模拟器与真机对比、报错类型或某团队归因、未跑完环节）：只用输入或查证里明确给过的，严禁脑补未提供的具体情节或替其他团队背锅；原文给出的核心观点与边界原意须原样守住，不擅自偷换成别的命题。
  - **公开工程机理**：若素材只给出高层动作，须围绕通用工程机理讲透「旧路为什么必挂、新路每一步具体解决什么卡点、做不到的边界背后有什么客观约束」，不把素材压缩成几句空提纲；示范配置须明确标出是示意。
  - **步骤不错位、不擅自加码**：多步方案的名称与正文动作严格一一对应（例如写「截图比对」就写截图与判异常，写「拉日志归因」就写拉日志定位原因，不把前一步职责写串进后一步）；原文未明说由 AI 执行的环节不擅自改写成 AI 动作。
  - **标题、数量与时间闭环**：有未跑通或人工兜底部分时，标题不夸大成「不再需要手工」「全覆盖」；核对 `总数 = 已完成 + 未完成`（不把总数误写成「在剩下的 N 个里」）；不拔高时间跨度（如把「两周」写成「最近几次发版」），也不把已拦下的缺陷擅自外推成「避免了某类未发生的线上事故」。
- **交稿前快速过四关**：
  1. **零上下文视角扫一遍**：前三段是否不用背景铺垫就能看懂在讲什么、和我有什么关系？节与节跳转顺不顺？有没有一连排好几段纯文字墙？
  2. **清口误、格式与事实口径**：确认带 `#` 一级标题、主章节用 `##`（不加「一、二、三」编号，不堆 `---` 分隔线），标题不越界、数字口径闭合、中英文与数字间距规范（如 `60 多个`、`iOS 团队`），逐句划掉输入未给过的具体页面名、版本起因、故障现象等脑补细节，清掉重复词、断裂标记与未核实 `TODO`/`待补`。
  3. **字面闸**：按需跑 `python3 scripts/writing_check.py 稿子.md --mode sharing` 清净半角标点与空洞导语。
  4. **过 `haohao-shuohua`**：交标准档去 AI 味、保事实，同时守住本分支的自然口吻、短段节奏与灵活小标题（不强改成死板报告清单）。
