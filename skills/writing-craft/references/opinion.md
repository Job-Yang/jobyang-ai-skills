# 直球观点与手记分支（opinion）· 口语化说透一件事

> **灵魂一句话**：靠观点、事实和想透了的判断服人，没有任何花里胡哨。**不端公众号专栏腔、不凑排比金句、不玩文字技巧**，拿懂行朋友坐对面聊天那种**自然、直白、稍微口语化**的口吻，把事情直球说明白。

本分支包含两种同源产物，按需求形态二选一：
- **观点硬文**：围绕一个可被同行反驳的核心判断直球推演（默认完整观点硬文通常 `1,000–2,500` 字，配 `# 主标题` 与 `2–4` 个直给判断句 `##` 小标题，把一线现场、`2–3` 层工程机理与可落地适用边界讲实讲透；仅当用户明确要求「写段三五百字短评」时才走 `300–600` 字不分节短评）。
- **锻造手记**：把一句话想法或一整篇材料，压成极精简的可追溯短思考（**`≤ 120` 字**，以 `≤ 80` 字为宜）。

> **硬底线**：完整观点硬文首行必须写 `# 一级主标题`（直陈判断、禁 `——`），正文配 `2–4` 个 `##` 小标题，通常 `1,000–2,500` 字讲透现场、工程机理与自洽边界（仅明确要求极短评才用 `300–600` 字无分节短评）。

---

## 零、姿态与口吻基线（最高优先级）

- **平视同事，口语直说**：作者心里那句「其实大家很多时候没想透」只是思考起点，绝不能端着架子写成「大厂都没看懂而我早就看透了」。像同组工程师坐工位旁边直接摊开讲：摆观察、讲机理、给事实，让读者自己点头，不装深沉、不喊口号。
- **口语化 ≠ 写水话**：要用日常主动动词（「别硬凑」「拿不住」「直接炸了」「谁也没空看」）代替端着的书面腔（「进行了系统性重构」「展现出显著价值」「引发了深刻反思」）；但**专业核心术语原样保留**（`Code Review`、`Context Window`、`重构`、`幂等`），不用失真白话顶替精确概念。

## 一、观点硬文写作法

### 1.1 主骨架（直进直出）
1. **定一个真主张**：逼自己说清这篇「只能留一句话」的核心判断。这个判断必须**具体、有边界、同行能站出来反驳**；左右逢源「A 重要 B 也重要」的正确废话直接淘汰。
2. **开篇直给靶子或反常现场**：第一段直接亮出核心判断，或甩出一个同行一看就懂的真实一线现场/取舍悖论。跳过「先定义背景」「先讲发展史」「先说套话再翻转」等前戏。
3. **一节只讲透一个判断**：靠真实机理 + 工程事实一层压一层推进。仅当用户明确要求极短评时走 `300–600` 字连续短段；常规观点硬文配 `# 主标题` 与 `2–4` 个直给判断句 `##` 小标题，把机理向下追到真实的工程约束（如作者盲区、架构与数据兼容性前提、审阅注意力被套话淹没、书面自证替代不了自动验证等），不停在「大家偷懒/敷衍/责任稀释」的表层心理。**盯准讨论对象，绝不把 A 机制和 B 机制串台**（例如不把表单填报问题混成多级审批流程，不把界面交互问题混成权限架构问题）。举常见公开工程场景（如锁表、空值异常、新老版本混跑状态冲突、跨系统发布顺序依赖等通用机制）能把判断砸实，属于正常工程论证而非编造私有事实；但严禁拍脑袋编造虚构团队故障数、私有项目名或「第 42 页」类假数字。**适用边界必须落到可执行机制且前后自洽**：写明日常只留什么（如 diff 看不出的客观上下文）、高危凭什么自动触发（如按目录/路径/标签/Owner 分级触发具体卡点且人工必须核对具体方案）、机器门禁接管哪些校验——写完顺手反查：**自己保留下来的做法，会不会重演前面刚批过的毛病？**（前文刚批某类人工填报流于形式，边界里就别再把同类手填项留回日常流程。）
4. **冷静一句话收住**：最后落在最硬的结论或取舍提醒上，即停——不加「值得深思」「赋能未来」类升华尾巴。

### 1.2 四条质量铁门

1. **标题与小标题直给判断，绝不卖关子**
   - 把这节想立的判断直接放进标题或小标题，拿平实陈述句或一个读者真会脱口问出的直白问句立住（「AI 让写代码变快了，为什么交付没跟着快？」「规范越写越厚，往往不是团队不够严」）。
   - **彻底避开**：标题用 `——` 破折号、悬念钩子（「我把它拆开看了」「你绝对想不到」「背后的秘密」）、机械编号（「第一刀 / 一、二、三」）、三连名词罗列（「意图债、理解债、认知投降」）以及「不是 X，而是 Y」式翻案标题。

2. **精确概念直接直述，不加为了降门槛而硬套的生活比喻**
   - 读者本身就是理性同行，已经拥有精确定义的工程概念（比如上下文窗口、调度延迟、抽象泄漏），直接把真实机制说准。
   - 不要「为了好懂」硬配「就像笔记本 / 就像球队前锋 / 就像交通指挥」等生活类比，更不准用「这就好比……所以……」拿比喻顶替中间的因果推导。只有极少数真正陌生的新理念、拿不掉又很难一句话说清时，才克制借一个极简锚点，讲完立刻回事实。

3. **动词和主语配得上，绝不生拉猛词**
   - 想写得有劲，靠判断和事实本身，不靠硬扯夸张动词。「账」只会亏空、算不平、糊不住，不会「崩盘/塌陷」（那是大楼和堤坝的事）；「规范」会没人读、沦为摆设、挡不住出错，不会「彻底窒息生态」。写完顺口念一遍，觉得哪个动作主语真做不出来，就换回朴实精准的词。

4. **反车轱辘话（精炼≠剪成抽象提纲）**
   - **反车轱辘话是删同义复述、空垫话和套话，绝不是把工程机理和可落地边界剪成三段抽象口号**；能一两句说完的判断不硬凑铺垫，只留带来新机制、新事实或新边界的句子。段落长短随论证自然错落（短断句与 `80–160` 字展开段交错），**避免每节机械切齐成等长三段方块网格**。
   - **彻底删掉**：正着说完再反着复述同一层意思；先预告「接下来我们看」、中间展开、结尾再总结一遍刚才说了什么；纯过渡垫话（「说到这里」「值得注意的是」「显而易见」）。多组离散数字/案例并列时直接上精简列表或对照表，比绕三句话省力得多。
   - **版式与交付**：单段保持短小精悍（`≤ 150` 字，避免大坨字）；有外部出处在正文句末挂 `[1](url)` / `[来源](url)` 可点角标、文末列完整来源标题，绝不把一长串蓝字标题塞进正文里打断阅读；遇到悬殊对比数据时可建议补直观图表或 `content-infographic`（缺工具就文字讲透）。

## 二、锻造手记（`≤ 120` 字，以 `≤ 80` 字为宜）

**核心原则**：手记只沉淀**主题本身想通的因果内核**，不记录「我怎么调研、用了什么方法、这篇总结了啥」的过程元评论。

### 2.1 先分两路输入
- **模式 A · 口语散想法**：去口癖（嗯/我觉得/大概），抽出隐藏的「条件 → 行为 → 结果」底层咬合机制写尖写准——不能只是删掉「我觉得」照抄原话，也不能编造原文没提过的新数字或新案例。**必须原样保住原话里的具体层级/数量、关键角色、动作与负面后果词**，只删口癖与废过渡，**严禁把具体教训抽空拔高成放之四海皆准的抽象社论**。
  - 单条对话直接交付 **1 段凝练连贯短文**，不叠 `**主题前缀** ·` 造成首句复读；多条归档进笔记文档时再加 `- **主题前缀** ·`。
- **模式 B · 从已写完的长文抽干货**：通读全篇找核心结论（往往藏在中后段「所以/卡点在」之后），绝不摘抄开头的背景引入，用平实口语把那个最核心的判断 + 最关键因果压缩出来。

### 2.2 铁律：因果环一个不许砍（防压丢核心代价）
提炼缩字数时**只砍铺垫、举例、废话和修饰词，绝不砍掉「条件 → 行为 → 后果」中的任何一环**——尤其不能把用户亲口指出的负面代价或反作用压没。**交稿前务必把原话按「条件 → 行为 → 负面后果/代价」拆环核对成稿；只要压丢了具体数字、关键动作或负面后果环，或磨成了抽象大词，立刻重写。**

- ❌ **错（后果环丢了）**：「`PRD 边界写太全，研发照着做就行，不再想为什么。写大概方向，他们反而会补全。`」（把原话里「出了怪需求也不知道为什么」的关键痛点后果删没了。）
- ✅ **对（同篇幅但环环咬合，约 55 字）**：「`**PRD 写太细，研发不再想为什么** · PRD 边界写太全，研发照着做，出了怪需求也不查为什么；写大概方向，他们自己补全，还会来挑战你。`」

### 2.3 口语想法锻造示范
- **输入**：「嗯今天想明白一个事，就是我们一直说 AI 写代码快，但你快了之后发现没人看你写的代码了，验收都变成跑测试，那人其实就从写代码退到去定义什么算好了，大概就这个意思。」
- **单条对话输出（约 65 字）**：「代码生成速度超过逐行审查的带宽后，人工走查自然让位于自动化测试。人真正剩下的位置不再是亲手写对每一行，而是把『什么算好』定义清楚。」
- **自检与落点**：写完数一遍字数（超 80 砍修饰词，超 120 重提），问一句「把主干那句盖住还剩什么」；若用户未指定要写进哪份笔记文档，直接在对话交稿即可，不另起尾巴追问路径。
