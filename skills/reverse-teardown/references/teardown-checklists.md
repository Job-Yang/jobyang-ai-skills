# 分对象拆解清单

> 按对象类型只读对应小节。这些维度是第 2、3 步的提问支架，不是输出模板；拆完不要把问题清单原样留在成品里。

## 目录

- UI / 交互
- 代码 / 架构
- 文档 / 方案
- Prompt / 技能

## UI / 交互

结构还原：

- 信息架构：内容怎么分类、层级多深、每屏信息量。
- 核心动线：用户完成最高频目标经过几步，有没有回头路和死胡同。
- 视觉层级：第一眼看到什么、主动作在哪、靠什么建立层级（大小/对比/留白/动效）。
- 状态：空态、加载、错误、无权限、极端内容（超长文本、无图）分别长什么样。
- 输入模型：遥控器/触摸/键鼠/语音，焦点或触控目标如何移动，误触成本。

关键选择追问：

- 它把复杂度放在了哪一侧——用户操作、界面，还是后台算法？
- 为「新用户第一次」和「高频用户第 1000 次」分别做了什么？
- 哪些东西被故意删掉了？删掉后谁受影响？
- 视觉/交互手法依赖什么资源（物料产能、数据、性能、屏幕尺寸）？

迁移高危点：大屏电视与手机的交互模型、观看距离、输入设备完全不同；移动端的 hover、侧滑、长按模式不能直接搬。

## 代码 / 架构

结构还原：

- 模块边界与职责：每个模块只回答一个问题吗，有没有上帝对象。
- 数据流与控制流：数据从哪来到哪去，谁拥有状态，同步还是异步。
- 关键抽象：用什么概念隔离了变化，扩展点开在哪。
- 依赖方向：有没有反向依赖、环依赖、对具体实现而非接口的依赖。
- 错误与并发：失败路径、重试、幂等、资源释放怎么处理。

关键选择追问：

- 这个抽象是为哪种变化频率买的保险？过度设计和刚好够用的分界。
- 它牺牲了什么——可读性、调试便利、性能、还是上手速度？
- 约束（语言、运行时、团队规模、历史包袱）去掉后，这个选择还成立吗？
- 测试 seams 在哪：代码是否可在不碰真实 IO 的情况下验证。

迁移高危点：大厂架构常为百人团队和高并发付费；个人/小项目照搬分层和中间件，只会复制成本不复制收益。

## 文档 / 方案

结构还原：

- 论证骨架：主张是什么，靠什么支撑，章节之间是并列还是递进。
- 每节的推理任务：给事实、做解释、立判断、还是提行动。
- 详略：哪里花了最多笔墨，哪里一笔带过，详略是否匹配风险。
- 读者路径：不同读者（决策者/执行者/质疑者）能否各取所需。

关键选择追问：

- 它怎么处理反对意见——回避、稻草人，还是先立最强反方再回应。
- 抽象层次是否统一，有没有在机制层和操作层之间乱跳。
- 它用什么建立可信度：数据、案例、推演，还是身份与语气。
- 删掉哪一段会让结论不成立？那段才是真支点。

迁移高危点：方案的有效性强绑定其组织语境（读者、决策机制、政治）；文笔结构可搬，论证权重不能照搬。

## Prompt / 技能

结构还原：

- 触发契约：description 是否讲清了「何时用、何时不用」，边界词是否可判别。
- 输入契约：需要什么材料，缺输入时是追问、降级还是 fail-closed。
- 处理流程：步骤是否有序、前一步是否真的喂给后一步，还是伪流程。
- 输出契约：成品长什么样、篇幅、格式、必含字段。
- 防呆机制：怎么阻止模型最常见的失败模式（脑补、堆砌、跑题、过早下结论）。
- 自检与收口：有没有可勾选的验收清单，标准是否可客观判定。

关键选择追问：

- 它把哪类「模型默认会做错的事」写成了硬规则？
- 哪些约束在提升质量，哪些只是作者的个人口味？
- 它假设的宿主能力（工具、子 Agent、长期记忆、检索）是什么？换到没有这些能力的环境会怎样。
- 规则之间有没有冲突，冲突时谁优先。

迁移高危点：为某个宿主/模型写的触发词、工具名、输出格式不可直接搬；公开 prompt 常假设「AI 没有工具，全靠文字姿态」，有工具链的环境照抄是降级。
