# Video Reader

> 一个给大模型（只能看图、看不了视频）配「看视频眼镜」的 **Agent 技能（Skill）**。

[English](./README.md) · **简体中文**

> [!IMPORTANT]
> **这是一个 Agent 技能（Skill），不是给你单独跑的命令行工具。** 它要作为技能安装（入口是 [`SKILL.md`](./SKILL.md)），由 AI Agent 来驱动。里面的 `scripts/video_frames.py` 是**技能内部调用的引擎**，不是让最终用户手敲的脚本。用法：把这个仓库放进你 Agent 的技能目录，然后用大白话说「看看这个视频」就行。

大模型能看图，但看不了视频。Video Reader 用纯代码（帧差）把视频拆成**带时间戳的关键帧 + 运动时间线**，让 Agent 能说出**「第几秒发生了什么」**——尤其擅长排查 App 滑动 / 交互问题。

它会自动跳过没动静的片段，只挑画面在变的关键帧，所以又快又省 token，不用你一张张截图。

## 为什么需要它

你手上有段视频——同事甩来的 App 滑动 bug 录屏、用户客诉、随手翻拍的操作过程——想让大模型帮你看看里面发生了什么。但大模型只能看图片，看不了视频。

这个工具就是干这个的：**你把视频丢给它，它能告诉你「第几秒发生了什么」**，尤其擅长排查 App 的滑动 / 交互问题（面板怎么动、状态怎么变、跳转对不对）。

| 适合 | 不适合 |
|---|---|
| 滑动、手势、状态切换、页面跳转等**交互逻辑**问题 | 帧率 / 卡顿等**性能**问题（截图看不出卡，请用日志 / Perfetto） |
| 排查「第几秒做了什么、对不对」 | 需要精确到像素的触点定位（翻拍视频尤其） |

## 特性

- 🎯 **零 token 挑帧** —— 帧差在 CPU 上跑，模型只看挑完的结果。
- ✂️ **自动折叠静止段** —— 静止帧没信息量，整段扔掉。
- 🔍 **先粗后细下钻** —— 先 `scan` 全片，再 `zoom` 进可疑区间（可多轮）。
- 🗺️ **九宫格概览** —— 一张大图把握全片节奏。
- 🎙️ **可选语音转写** —— 补画面看不到、只能听到的旁白 / 口述 / 报错语音。
- 📦 **不依赖系统 ffmpeg** —— OpenCV 自带解码，依赖首次运行自愈。

## 快速开始

### 环境依赖

- Python3 + `opencv-python-headless` + `numpy`（OpenCV 自带视频解码，**不依赖系统 ffmpeg**）
- `matplotlib`（仅 `--debug` 模式画曲线图时需要）

**依赖自愈**：脚本启动时会自动检测缺失依赖并尝试安装（`pip install --user --break-system-packages`，不污染系统环境），正常无需手动准备。仅当自动安装失败时，才会提示手动执行：

```bash
pip install --user --break-system-packages opencv-python-headless numpy matplotlib
```

### 幕后：技能怎么调用引擎

你一般不会自己跑这个——是 Agent 在跑。但供参考，技能粗扫一段视频时发出的调用长这样：

```bash
# 粗扫全片，拿到运动时间线 + 关键帧
python3 scripts/video_frames.py scan your_video.mp4
```

`stdout` 是结构化 JSON（含 `timeline`、`active_segments`、`frames[]` 每帧路径和秒数），`stderr` 是给人看的运动时间线概要。先读时间线，再决定要不要下钻。

## 四个子命令

接到视频任务先想清楚要哪个，别永远只用 `scan`：

| 子命令 | 什么时候用 | 一句话 |
| --- | --- | --- |
| `scan` | 默认起点；要定位「哪几秒在动 / 出问题」 | 帧差初筛 + 运动时间线 + 稀疏抽帧 |
| `zoom` | 已知可疑区间，要看那几秒的细节 | 指定区间高密度抽帧 |
| `grid` | 想先要个**全片概览**、一张图看节奏，或视频较长先扫一眼 | 均匀取帧拼成九宫格大图 |
| `transcribe` | 画面看不出、**需要听**（旁白 / 口述 / 报错语音） | 语音转文字（带时间戳，可选，需 ffmpeg + whisper） |

常见组合：**长视频/不确定从哪看 → 先 `grid` 看全片节奏 → `scan` 看运动时间线 → `zoom` 下钻可疑段**；涉及「说了什么」→ 加 `transcribe` 与画面时间线对齐。

## 核心工作流：先粗后细

不要一上来就把整段视频高密度抽帧，那样既慢又炸上下文。标准打法是两步：

```
第1步  scan（粗扫）
  └─ 脚本输出：运动时间线（文字）+ 活动段稀疏抽的几帧
  └─ 你看时间线 + 帧，判断「问题大概在 X-Y 秒」
        ↓
第2步  zoom（下钻）
  └─ 脚本在 X-Y 秒密集抽帧
  └─ 你看细节；若还不够，继续在更小区间 zoom（可多轮）
```

关键心法：**先读时间线，再决定要不要看帧、看哪段的帧。** 很多时候 scan 的运动时间线（纯文字）就足够判断该往哪下钻，这是最省 token 的方式。

## 上传被拦怎么办

很多平台（如 Mira 等）在上传时**直接禁掉视频 / 音频格式**，传 `.mp4` / `.mov` 会提示「不支持的文件类型」。**这不是死路，有两个绕过办法：**

1. **改后缀**：把 `xxx.mp4` 重命名成平台允许的后缀（如 `.txt` / `.bin`）再上传。拿到后不要被后缀骗了——它本质还是视频，改回 `.mp4`（或直接用原始路径）再喂给脚本即可。OpenCV 按文件内容解码，不认后缀，所以哪怕后缀是 `.txt`，只要内容是视频就能读。
2. **压成 zip**：把视频压成 `.zip` 上传（zip 通常不被拦），收到后先解压拿到里面的视频文件再喂给脚本。

> 一句话：平台拦的是「后缀 / 格式」，不是「内容」。改后缀或套个 zip 壳就能绕过，拿到真身后照常 `scan` / `zoom`。

## 它是怎么工作的

### 核心洞察

视频本质就是一串按时间排好的图片。所谓「原生支持视频」的大模型（Gemini、GPT-4o 等），底层做的也是抽帧——把视频按一定频率拆成帧再当图片喂进去。既然如此，把「抽帧」这步搬到外面自己做、控制抽哪几帧抽多少，反而比通用方案更省、更准。

### 解决的两个关键难题

| 难题 | 朴素做法 | 本工具的解法 |
|---|---|---|
| **上下文爆炸**：20 秒视频均匀抽成 20 张图全塞给模型，又贵又看花眼 | 硬塞 + 靠大窗口扛 | 只在「有动作」的地方抽帧，静止段整段折叠，一帧不抽 |
| **谁来挑关键帧**：让模型先把每帧看一遍才知道哪帧重要，等于没省 | 模型逐帧看 | **纯代码用帧差挑帧，零 token**，模型只看挑完的结果 |

这里的「帧差」，就是算相邻两帧的画面差了多少——纯数学计算，在 CPU 上跑，不经过大模型。画面没变说明没人操作，直接跳过；画面在变说明有滑动 / 交互，密集抽帧。

> 一句话：**通用大模型靠「塞得下」，我们靠「挑得准」。而挑准这步是免费的。**

### 整体流程

```
                  一段视频文件
                       │
        ┌──────────────┴──────────────┐
        │   纯代码处理（不花 token）      │
        │  1. 逐帧算帧差 → 运动时间线     │
        │  2. 静止段折叠，活动段抽帧      │
        └──────────────┬──────────────┘
                       │
              关键帧 + 运动时间线
                       │
        ┌──────────────┴──────────────┐
        │      大模型（看图 + 判断）      │
        │  看懂画面、定位问题、对照预期    │
        └─────────────────────────────┘
```

## 命令参考

### scan —— 粗扫全片

```bash
python3 scripts/video_frames.py scan <视频路径>
```

| 参数 | 作用 | 默认 |
|---|---|---|
| `--start / --end` | 只扫某段（已知大概范围时） | 全片 |
| `--density` | 活动段每秒抽几帧 | 2 |
| `--max-width` | 帧最大宽度（省 token），0=不缩 | 900 |
| `--threshold` | 运动阈值 | 自动估算 |

> 性能：scan 在区间起点只 seek 一次，之后顺序跳帧（只解码采样帧），长视频也不会因逐帧随机定位卡死；处理过程每约 5 秒在 stderr 打一行进度。

### zoom —— 对可疑区间高密度抽帧

```bash
python3 scripts/video_frames.py zoom <视频路径> --start 10.0 --end 12.0 --density 8
```

要看某个瞬间（如手指抬起那一刻），把 `--density` 加到 12~15，区间收窄到 0.5 秒以内。

### grid —— 九宫格概览

全片（或区间）均匀取帧拼成一张大图，每格左上角标秒数。一次 Read 一张图就能看全片节奏，省 token、好定位；看完再用 zoom 下钻可疑那一格。

```bash
python3 scripts/video_frames.py grid <视频路径>
python3 scripts/video_frames.py grid <视频路径> --rows 4 --cols 4 --start 0 --end 30
```

- `--rows / --cols`：网格行列，默认 3×3；`--cell-width` 每格宽默认 320。
- 输出 JSON 里 `grid_path` 是拼好的大图，`cells[]` 是每格的秒数 / 行列号。
- 和 scan 互补：scan 的运动时间线擅长「哪几秒在动」，grid 擅长「整段长啥样」。

### transcribe —— 语音转写（可选）

画面看不到、只能听到的信息（旁白、客诉口述、报错语音），用这个补。**可选软能力，缺依赖只提示并跳过，不影响 scan / zoom。**

```bash
python3 scripts/video_frames.py transcribe <视频路径> --model turbo
```

- 依赖：系统 `ffmpeg`（抽音轨）+ `openai-whisper`（pip 包，含 torch 较重，脚本「用到才按需装」）。任一缺失会打印安装方法并以退出码 4 跳过。
- 输出：stdout 是 JSON（`text` 全文 + `segments` 带时间戳分段），stderr 是逐段带时间戳文字。
- 用法：把转写时间戳和 `scan` 的画面运动时间线对齐，能更准说出「第 X 秒画面在做什么、同时说了什么」。无音轨的纯录屏会自动跳过。

### --debug —— 调试模式（默认关闭）

平时不用开。调试工具本身、或想搞清楚「为什么这段被判成静止 / 运动」时加上：

```bash
python3 scripts/video_frames.py scan <视频路径> --debug
```

- 帧存到**当前目录的 `video_reader_debug/<视频名>_<模式>/`**，稳定可复查（默认是随机临时目录，读完即弃）。
- 额外产出 `_debug/motion_data.json`（每个采样点的时间 + 运动分、阈值、分段）和 `_debug/motion_curve.png`（帧差曲线图，带阈值线和活动段底纹），看这张图就能一眼判断阈值定得对不对，据此调 `--threshold`。

### 常见坑：依赖「装了却用不了」

脚本每次启动都会先在 stderr 自报家门，打印它正在用哪个解释器：

```
[video-reader] 解释器自检 (排查'装了却用不了'看这里):
  - python   : /usr/bin/python3
  - version  : 3.13.5
  - user-site: <user-site>/python3.13/site-packages
```

> **症状**：明明 `pip` 装过 `opencv`，脚本却报缺依赖 / import 不到。
> **根因**：一台机器上常并存好几个 `python3`（系统 `/usr/bin`、Homebrew、pyenv），而 `pip --user` 按版本号分目录存包。装包用的是解释器 A、跑脚本命中的却是解释器 B，B 的包目录里自然没有。
> **怎么解**（任选一）：
> - 最省事：跑脚本时把 `python3` 换成装了包的那个解释器的**绝对路径**；
> - 最干净：建个 venv 锁死「一个解释器 + 一套包」——`python3.x -m venv .venv`，之后统一用 `.venv/bin/python` 跑。

## 设计取舍

- **静止段为什么直接扔**：截图是不会「卡」的，静止段对排查交互问题没信息量，只会浪费模型的注意力和上下文。
- **时间戳为什么用文字、不烧进画面**：模型读文字是 100% 准的；让它去认画面里烧的字，可能糊、可能挡画面、可能读错。所以时间戳放在文件名和返回数据里，模型读帧时一一对应即可。
- **喂给模型的帧为什么要压缩**：模型内部本来就会把图切成固定尺寸再处理，超高清像素根本进不了模型。脚本默认把帧缩到宽 900、JPEG 质量 70——既看清 UI，又省 token 和带宽。
- **翻拍视频（带手、反光、抖动）怎么扛**：帧差用了「缩小 + 模糊 + 分块」来吸收噪点和轻微抖动，所以翻拍视频也能大致定位运动段。但手指位置这类细节，翻拍下精度有限，只能定性看方向。
- **为什么不依赖「屏幕录制小白点」**：很多视频是真实用户客诉、或随手翻拍，没有小白点也没法要求规范。有就当福利，没有也能干活。
- **工具里为什么不写业务逻辑**：它不懂「卡顿」「面板」「跟手」是什么，只负责产帧。判断交给上层大模型。这样它今天能查交互，明天能查任何「想让模型看个视频」的场景，是个通用地基。

## 边界与已知限制

- **判断对错需要上下文**：不知道用户操作意图时，工具只做客观复述，不瞎猜对错。把吐槽 / 预期一起喂给模型，定位更准。
- **不适合查帧率 / 卡顿**：卡顿信号在「帧之间隔了多久」，抽帧会把时间抹平。查性能卡顿请用日志 / systrace / Perfetto。本工具擅长**交互逻辑问题**。
- **翻拍视频手指精度有限**：能看方向，难精确定位触点。
