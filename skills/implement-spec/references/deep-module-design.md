# 深模块设计与接缝指南（按需查阅）

> 用于界定模块粒度、挑出合适接缝与测试替身，或在核心抽象拿不准时对比多套接口方案。

## 1. 核心术语与设计准绳

- **深模块（Deep Module）**：用很小的公开接口（签名、前置约束、错误枚举）包裹住尽量多真实复杂性；如果把接口和实现体量一比，接口几乎和内部一样复杂，那就是**浅模块（Shallow Module）**。
- **信息隐藏**：存储格式、重试退避、缓存淘汰、并发锁顺序全部藏在实现内部，绝不让两个模块靠手工约定一起解析同一份结构。
- **接缝（Seam）**：不修改目标代码就能替换行为的边界，即模块接口所在处；把复杂内部拆成小辅助函数只是内部实现细节，不要顺手暴露成公开接缝。

## 2. 四类依赖与对应测试策略

| 依赖类别 | 典型例子 | 设计与测试策略 |
| --- | --- | --- |
| **进程内纯逻辑（In-process）** | 状态机、价格计算、解析校验 | 合并成深模块直接通过公开接口测，**不需要建假接口或 Mock** |
| **本地可替代（Local-substitutable）** | 数据库、文件系统、本地队列 | 依赖本地临时目录或轻量本地实例直接跑通；接缝留在内部，不暴露多余适配层 |
| **跨网络自有服务（Remote owned）** | 内部微服务 RPC/HTTP/MQ | 在接缝处定义精简 Port；业务逻辑归深模块，传输用注入适配器（测试用内存实现） |
| **不可控第三方外部（True external）** | 支付网关、短信、云厂商 API | 注入 Port 接口，单测提供确定性 Fake/Mock 适配器并覆盖超时/限流错误态 |

## 3. 存量代码嗅探与表征测试（Characterization Tests）

改造旧模块前，出现以下信号说明值得先「加深」再动：读懂一个概念要在四五个小文件间反复横跳；每个调用方都在重复同一套准备/校验顺序；改一个业务规则却要同步改多个包。

- **安全重构起手式**：在动结构之前，围绕旧模块现行公开入口补一套**断言现有真实输入输出行为**的表征测试（即便是历史怪癖也要先如实锁住），确保后续每步拆分都不悄悄改变外部行为。
- **以接口测试替代碎片单测**：深模块成型并接管接口级覆盖后，删掉只绑定旧内部私有函数的碎片单测，避免重构内部实现时测试一碰就碎。

## 4. Design-it-Twice（多方案对比接口，高风险枢纽按需选用）

针对长期难以修改的核心接口（如公共 SDK、存储引擎边界、跨团队协议），不直接拍第一反应方案，强制拟出 2–3 套风格迥异的候选接口再择优合并：

1. **极简接口派**：压到 `1–3` 个主入口，追求单个入口最高杠杆。
2. **最常见调用优化派**：让 80% 主流调用一行搞定，罕见参数退居可选配置。
3. **显式端口适配器派**：为跨进程/外部边界显式隔离 Port，兼顾可测性与可替换性。

对比三者的接口简洁度、改动局部性、误用概率与接缝位置后，给出**明确主推方案与合并点**（不要只甩菜单不表态）。
