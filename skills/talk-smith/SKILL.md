# talk-smith · 面向读者的技术分享锻造

> **唯一目标**：把一个技术主题做成**别人愿意读、听完能转述、明天能搬走用**的分享——技术准确（术语原词、机制不替换）+ 开头结构/递进/例子/节奏，回答"是什么、为什么是这样、怎么看怎么用"；幽默口语只是可选的执行风格，严肃技术分享一样归本技能。
> 判定它归不归 talk-smith，看的是**这篇是不是做来讲给读者/听众听的技术分享或经验叙事**，不是看对内还是对外，也不是看有没有幽默感：对内的技术 talk、个人工程实践、经验传播、项目复盘、团队 slides 一样归本技能；反过来，普通研究报告、机制解读、选型研判（哪怕对外发布、面向读者）仍由 `feynman-explainer` 直接写到底。
> 它不是"我自己搞懂"（feynman-explainer），也不是"扎一个观点"（cuihuo）、"畅想未来"（tangshan）、"写内部评审文档"（engineering-docs）。它是**输出型、讲给别人听的技术分享与经验叙事**。
> 文中允许的幽默是**技术分享里的人味**（自嘲、把读者当同事、服务理解），主题仍是把技术讲清楚——它不是汤山文学式畅想，也不是淬火式短观点硬文。

---

## 0. 触发与边界（先判这篇归不归 talk-smith）

**命中即启用**：写技术分享/技术文章/技术博客/深度解析/系列博客、分享稿/演讲稿/talk、分享 slides、个人工程实践复盘、经验传播、项目复盘、技术成果及工作总结、"用一个具体例子把 XX 讲给客户端同学听""给别人讲清楚一个技术或项目"。幽默口语只是可选风格，严肃无幽默的技术分享一样启用；行政周报、会议纪要等非技术写作不走本技能。

| 你要做的事 | 归谁 | talk-smith 的动作 |
|---|---|---|
| 把一个技术主题做成**面向读者、有叙事弧**的中长文/talk/slides（**对内分享、对外传播都接**） | ✅ **本技能** | 全流程走 §2 |
| 技术观点硬文（1200–4000 字扎一个可被反驳的判断）+ 锻造手记（≤120 字） | `cuihuo` | 不接，指路 |
| 把一个点讲透、我自己搞懂一个原理（含研究报告成稿，对外发布也算） | `feynman-explainer` | **单向吃它的研究结论**（见 §1） |
| 面向未来的技术想象/极端外推畅想 | `tangshan-style` | 不接，指路 |
| 落成 RFC/ADR/技术方案/评审决策文档（要评审、要拍板）+ 架构图/流程图 | `engineering-docs` | 只是讲一个技术的分享稿不转它；叙事分镜里要出架构图才交它（见 §1） |
| 本轮只问一句定义、或只要提纲不要正文 | —— | 轻答，不启用；但"写个分享/讲讲实践/就按提纲写"是明确输出意图，不论输入多短、预期篇幅多长，都按对应文体启用，不被"三句话能讲清"排除 |

> ⚠️ **防误触发**：用户说"帮我搞懂/调研一下 XX"但没说要写成讲给别人听的分享 → 那是 feynman-explainer，不是本技能。本技能的触发器是"**做一个讲给读者/听众听的技术分享或经验叙事**"。

## 1. 组合关系（单向握手，写死方向）

talk-smith 是**装配者**，不是万能工厂。涉及就调，调完收回自己的流程：

- **素材与机制 → 先读 feynman-explainer**：任务包含仓库、源码、论文或技术机制调研时，在检索与分析前读取费曼及其范例，完成研究后收回本技能组织叙事；已有经过核实的研究结果就复用，不重复调研。费曼交接分享成稿时，本技能只补尚未查证的部分，避免来回调用。
- **配图分三类，相辅相成、别送错**：
  - **传播型信息图/封面（直观、帮读者记）** → `content-infographic`：步骤链、对比卡、概念比喻、封面。多标签/英文术语/步骤默认走它的确定性渲染器（不糊字）；只有标签很少、要靠具象场景"演出来"的比喻和封面才用文生图。它强制"锚定这一节正文 + 一句过渡句 + 图注"，避免图文两张皮。
  - **精确工程结构图/时序/流程（严谨、要评审）** → engineering-docs 的 Archify 桥接：明确主路径、归属和条件，交付结构源与原生阅读产物；原生缺少的专用视图按其能力清单用改良旧后端兜底，维护已有 `.py` 图仍沿用 `diagram_kit`。
  - **同一个点可两类成对**：传播稿用 content-infographic 画直观版帮助记忆；若同主题另有要评审的方案，再用 engineering-docs 出严谨版。直观版不替代严谨版，反之亦然。
  本技能只产出"叙事弧 → 分镜/这张图要讲清什么道理、锚定哪段正文"，不自己摆节点、不自己画。
  > 软依赖（缺失不阻塞）：`content-infographic` 与 engineering-docs 都是**可选增强**，本技能不依赖它们就能独立成稿。环境里有就按上面交出去；没有 content-infographic 时回退为——分镜里写清"此处该有一张什么图、讲什么道理"，能用简单 SVG/画板示意就示意，不行就用文字把该看的关系讲透，并明确告诉用户"当前环境没有信息图技能/文生图能力，已用文字或简图标注代替"。绝不因为配图技能缺失而中断写作。
- **一页式分享增强（用户需要时）**：借用 engineering-docs 的 `references/archify-reading.md` 与桥接，将已核对的分享内容做成图表、步骤定位、来源与局部修订的 Explainer 页面。正文仍归本技能；不把普通文章强制改成网页，不主动发布。
- **定稿 → 统一过 haohao-shuohua**：成稿交付前，交它重档去 AI 味（它是中文去 AI 味的唯一事实源）。本技能的风格闸与它同源，冲突以它为准；它去的是"为俏皮而俏皮/硬挠痒/AI 式感叹号卖萌"，本技能保留的"自嘲、把读者当同事、服务理解的人味"不在它去除范围内，判定线见 `references/style-cn-tech.md` §4；**它不反向调用本技能**。
- **改既有稿结构前 → 先过 sansi-erhouxing**：本次是"改/扩一篇已成形分享稿"而非从零起稿时，先过三思看全文骨架、判断动一处会不会破坏叙事弧，再动笔。从零起稿可跳过。
- **发布 → 内容归本技能，平台只承载**：成稿要进飞书文档/语雀/公众号时，用 `lark-doc` 等平台技能或直接粘贴把**已定稿**的内容搬上去；选题、叙事弧、分节和分镜由本技能定，不由平台技能或画板主导。

## 2. 主流程（五步流水线，不是可选项）

### 第一步 · 选题访谈（动手前先把意图逼出来）
不直接开写。一次问清四件事（拿不准才问，上下文已足就直接推进）：
1. **讲给谁**（锁定一个默认读者工种，比喻从这个工种的日常取）；
2. **听完要他做什么/记住什么**（一句话主线——这篇只能留一句话，是哪句？要不要埋一个主线词）；
3. **三态选哪个**：article（中长文）/ talk（口头分享，通常 10–30 分钟）/ slides（分镜演示）；
4. **场合与争议**：内部复盘/对外发布/严肃事故复盘（决定幽默剂量，见 §3）；有争议才按评论体可选件处理。

### 第二步 · 技术核实（先保真，再谈叙事）
技术断言、术语、机制、硬数字、引用，逐条过 `references/accuracy-gate.md`。**这一步不过，后面全是空中楼阁**：术语保留原词、关键术语给一句白话定位（中英对照可选）；机制用"白话画面→命名术语→工程事实"段内三步讲，不分通俗/进阶双轨栏；数字带出处；吃 feynman 的研究结论而不是现场编。

### 第三步 · 叙事弧大纲
按 `references/narrative-arc.md` 搭一条推进链（不是要点清单）。**先选开头结构**（TL;DR 卡片默认 / 先成果后过程 / 现场钩子），再排链：
`开头结构 → 一句话主线 + 埋 1 个主线词 → 摆现象/背景痛点 → 拆"为什么是这样" → 最易想错的一点单独成节 → 自我诚实拆台（亮半成品 + 留下了什么） → 落到"对做XX的人可搬走什么" → 几点启示（3 条平实体会）`。
先出 5–8 行大纲给用户确认方向，再填正文——这是失控保护。

### 第四步 · 分态产出
按 `references/templates-article.md` / `templates-talk.md` / `templates-slides.md` 写对应产物；同一内核三态互转要点见各模板末尾。中文技术分享写法（术语/比喻/段落节奏/幽默剂量/口语上限）见 `references/style-cn-tech.md`。

### 第五步 · 质检（交付硬闸，跳过=没交）
1. 过 `references/qc-checklist.md` 五维评分（借鉴 stop-slop 思路自写的中文版，**< 阈值重写**）；
2. **幽默剂量自检**：数一遍自嘲/拟人/转场小幽默的位置（只在成果区拟人、节间转场、自我拆台三处）与数量（每 2000–3000 字一处、全文 8–10 处封顶）；严肃事故复盘/对外正式发布/法律安全场合应为零；判定线见 style §4；
3. 跑 `python3 scripts/talk_check.py <稿子.md> --state article|talk|slides`（纯标准库，机器能判的硬约束扫到净；新结构项只出 WARN，幽默不做机器硬判）；
4. **无上下文读者测试**（借鉴 doc-coauthoring Stage 3）：开一个全新无上下文视角，预测读者会问的 5–10 个问题，逐个对着稿子答，答不上来的地方补；
5. 定稿交 `haohao-shuohua` 重档去 AI 味。

## 3. 三类必做动作（写死）

- **开头先选结构，禁寒暄导语**：默认 TL;DR 卡片（五字段：干了啥/最大的坑/真正收获/这篇讲/最后引出），或"先成果后过程"（前部先亮数据看板再拆机制），或现场钩子（具体画面/真人一句话/读者反驳/反直觉数字，可选）。**禁止"本文将介绍……""在当今时代……""随着 XX 的发展……"式导语。**
- **术语保留原词**，关键术语给一句白话定位 + 一个本工种类比，不把术语全换成大白话，不强制首次中英对照。机制段内三步：先白话给画面，再抛术语命名，再给工程事实（公式/复杂度/边界），不分双轨栏、不配成套色块。
- **默认自我诚实拆台**：主动亮明经验值/半自动/半成品/路没走完，并紧跟"但留下了什么"。评论体三件套（开头声明立场/替外部数字拆台/证据修辞三分）仅调研评论体可选，建设型复盘不用。
- **结尾默认几点启示**：3 条平实、能落地的体会，不写对仗警句；立场金句、明天能做的动作、签名档/系列预告均为可选。
- **收束成可数结构**：把方法压成"N 阶段/N 条/N 项自检"，每块给不同验收口径，方便转述收藏；速记口诀/速查表仅内容复杂时可选，不强制。
- **幽默按剂量放**：只在成果区拟人类比、节间转场、自我拆台自嘲三处，服务理解或拉近距离；严肃事故复盘/对外正式发布/法律安全场合归零。

### ⛔ 不要固化（去个人化红线）
本技能**不规定**成套 emoji/配色标系统（🟢🔴 双轨、`> [!NOTE]` 栏目块是专栏外壳）；允许功能性状态符号（✅/❌/⚠️）、全文 1 处以内梗图。**不复制**任何作者的私人梗原句、口头禅、个人比喻库、连载栏目号与"下期预告"、个人篇章品牌标签；但**鼓励按作者自己的口吻造同类自嘲/互动小幽默**——有语气，不抄句子。保留"用一个类比垫脚""重点要被钉出来"这些**动作**，不复制**人设**。别人用本技能产出的东西不别扭。
