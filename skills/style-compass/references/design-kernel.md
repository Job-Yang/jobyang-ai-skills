# 视觉构图内核：先组织注意力，再做样式

quick 与 full 都在具体画页面前读取本页。它把方向简报变成可见关系，不新增用户审批关卡，也不替代 `visual-craft.md` 的候选协议与实渲检查。

## 正向构图：五个连续决定

1. **从任务和真实内容选主对象、主动作。** 主对象是用户此刻需要理解或操作的东西，可以是正在运行的任务、文档正文、选中记录、输入内容或结果，不默认是标题或宣传式 hero。主动作是推进该任务的下一步，不是按钮列表里视觉最响的一枚。
2. **决定主对象的相对尺度和位置。** 先给主对象一块有辨识度、能承载其真实内容的空间，再安放导航、摘要与工具。尺度由任务频率、内容长度和对照需要决定，不把页面惯性切成平均卡片，再在顶部补一排总数。
3. **组织辅助信息和阅读顺序。** 只保留理解主对象、判断状态或采取下一步所需的辅助内容；用位置、共同对齐线、组间距离、展开层级和滚动顺序告诉用户先看什么、后看什么。弱信息可以按需出现，但不能靠删除能力制造“简洁”。
4. **给字形角色和色面分工。** 先区分展示、阅读、操作、数据、状态等角色，再选择相互协调的字形、尺度与密度；背景、表面、文字、边界、强调和状态色各自承担层次，不把换强调色当成艺术方向。
5. **集中一个产品专属重点。** 选择一处真正属于这个任务的内容、组件或互动时刻，例如任务依据与产物的联动、数据变化的表达、独特的对象预览。周边保持纪律，让辨识度来自产品，而不是散落的装饰。

这套顺序有效，是因为它先分配注意力和空间，再让字体、色面与细节强化同一关系。若从组件样式开始，各区块会各自“合理”却彼此竞争，最后容易收敛成同权卡片、总数条和通用主按钮。

### 两个短例子

- **大工作区：长任务控制台。** 主对象不是四张任务总数卡，而是“当前任务＋正在发生什么”：它占据中央的主要工作空间，连续呈现阶段、依据、等待项和产物；待处理队列成为可扫视的侧栏，主动作贴着当前阻塞出现。字形把任务名、状态事实、日志和操作分成角色；产品重点放在“依据如何变成可验收产物”的联动上。
- **小弹层：新增并执行任务。** 主对象是用户正在定义的任务及其执行前置条件，输入区获得足够空间让长内容可读；补充选项按需展开，主动作紧邻结果预期。提交后原位转成排队、等待输入或失败等真实状态，而不是再塞一组平均小卡。产品重点可以是对执行范围的一眼确认，不靠固定色值、字体或尺寸模板。

## 参考校准：借关系，不抄表面

有可用材料时选择一至两个**适用的正向样例**，优先使用真实产品页、用户提供的截图、现有设计系统或可核验的公开成品。逐个记录：

- 来源和看到的具体页面／状态；没有素材就写“未取得”，不凭产品名编造观察。
- 它为何适用：任务、内容密度、用户熟练度、平台和品牌中哪些相近。
- 本案为何不同：内容长度、能力、安全、载体或使用频率要求哪些关系必须改变。
- 可借的关系：主体比例、留白与密度、字体角色、组件组织、真实内容和关键状态；不把配色、字体名或标志性构图当配方。

高视觉上限页面可走 **comp-led**：把选定 comp 当作实现之外的视觉目标，按同一视口宽度截屏，比较整页后再比较主对象、字形、色面和关键组件区域。操作型 UI 可走 **code-led**：先用真实内容和平台组件实现，再以浏览器实渲校准，不强迫每个任务购买或生成图片。

comp 是外部视觉目标，不是 Opus 的内部特性。截图和图像差异只能发现比例、位置、素材或表面偏差，不能证明动作可发现、状态正确或任务可完成。

## 提交前审视

1. 在浏览器使用相同尺寸查看候选与参考／原版；先看整页，再看主对象和关键区域，不用缩略图掩盖局部缺失。
2. 查看窄屏以及默认、展开、选中、长内容、空和失败等适用状态；操作型界面还要走代表性路径。
3. 分开记录**审美目标**（主次、比例、字形、色面、辨识度）与**任务目标**（内容、动作、状态、恢复、上下文）。lint 只守确定性底线。
4. 保留首次稿和修改稿，说明改动针对哪个观察；失败或未完成稿不悄悄替换。
5. 自查用于把不完整稿挡在用户面前，不把每一条自查变成人类审批。原有 full／OPC 阶段批准仍在最后按既有链路接收结果。
