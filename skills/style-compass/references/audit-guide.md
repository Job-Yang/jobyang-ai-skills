# 评审模式：给现有页面找问题、出改法

用户拿来一个已有的页面或产品，问“哪里不好”“怎么优化”时用本页。它不是新的关卡：产出一份问题清单，用户同意后再在副本上改，改完前后对比。可以和入场分流的任一路线叠加（见 `design-archive.md`）。

## 一、先拿到四样东西

1. **页面本身**：HTML 文件、本地能跑的工程，或截图。只有截图时，下面的脚本检查跳过，并在报告里写明。
2. **产品目的**：用问诊的 Q1 到 Q3 快速过一遍（给谁用、做什么、多频繁）。不知道目的，就无法判断“好不好”。
3. **档案**：产品目录里有 `DESIGN.md` 或 `design/direction.md` 就先读，按产品自己的方向评，不按通用审美评。
4. **核心任务**：从产品目的里挑两到三个最重要的任务，后面的走查都围绕它们。

## 二、按顺序检查

### 1. 确定性检查（脚本，几秒钟）

```bash
python3 scripts/lint_design.py check <页面.html> --phase final [--tokens design/tokens.json]
```

覆盖中文字体回退、行高和字距、`lang`、缩放、图标按钮名称、可点的 div、焦点样式、动效和减少动态、是否守 token（传了 `--tokens` 时查颜色、字体、字号、圆角和间距），以及常见的 AI 默认长相。工程项目先构建，或对关键页面的 HTML 分别运行。

### 2. 任务走查（技能自己走）

对每个核心任务，在页面上一步步做，每步问四个问题：用户会想做这一步吗？能看到该点哪里吗？能把这个控件和想要的结果对上吗？做完能看出有进展吗？任何一个“不能”，这一步记为不通过。

再对每个关键页面查状态矩阵：空（第一次用、清空后、搜不到）、加载、部分完成、失败、成功、禁用，缺的记下来。异步操作有没有失败后的重试，危险操作有没有撤销或写清动作的确认按钮。

### 3. 视觉检查

- 对照 `visual-craft.md` 的手段表：构图、主次、字体、图文、配色、组件细节、动效，各看一遍，每条意见都要指向具体区域。
- 有方向简报时，对照目标感受词和反面词：画面里哪块让人感到“拥挤”“冰冷”。
- 品牌测试：去掉导航后，首屏能不能认出是这个产品。
- 不给美观打分。模型给界面审美打绝对分接近随机：GPT-4V 在成对比较界面好坏时只有 51.58% 的准确率（UIClip）；两两比较比绝对打分可靠得多（WebDevJudge）。

## 三、分级

| 级别 | 含义 | 判断办法 |
|---|---|---|
| P0 | 任务做不下去 | 走查有一步不通过，且没有绕过的办法 |
| P1 | 很费劲，上线前要修 | 用户会因此找客服；脚本的 error 一般在这一级 |
| P2 | 别扭，但有办法绕过 | 多走一步、要想一下才明白 |
| P3 | 打磨 | 对任务没有实际影响的外观问题 |

拿不准时问一句：“用户会不会因为这个联系客服？”会，就至少是 P1。分级借自 impeccable 的 P0 到 P3 和 Nielsen 的严重度（频率、影响、是否反复出现）。一个评估者给的严重度不可靠，Nielsen 建议取约三个独立评估的平均；条件允许时，用两三个互不知情的子代理分别评，再取平均。

## 四、报告格式

先写三句话的结论（最严重的问题、最值得先改的一处、整体判断），再列清单：

| 编号 | 位置 | 问题 | 证据 | 级别 | 改法 | 代价 |
|---|---|---|---|---|---|---|
| F01 | 首页 · 筛选栏 | 筛选条件改完没有反馈，看不出是否生效 | 走查任务 1 第 2 步；无加载态 | P1 | 筛选后在列表上方显示“已筛选 3 项 · 清除” | 多一行高度 |
| F02 | 全站 | 中文落到浏览器默认字体 | `CJK-FONT-STACK`，styles.css:12 | P1 | 字体栈补 PingFang SC、Microsoft YaHei | 无 |

报告写成 `audit-<页面>.md`，放进输出目录。

## 五、修改和对比

1. 用户选要修的条目（默认 P0 和 P1）。只修选中的，不顺手重做整页。
2. 在副本上改，原页面不动。
3. 用 `scripts/compare_variants.py` 把改前改后并排，让用户两两比较，指出哪块变好、哪块变差。允许原版胜出。
4. 技能自己的批评最多做一到两轮：GPT-4 给的批评意见能抓到细小错误，但有用程度随轮数下降（Duan 等，CHI 2024）。之后以用户的判断和真实操作为准。用户否掉的批评，下一轮带上，别再重复提。
5. 用户确认的取舍用 `design_memory.py record` 记进档案；没有档案的产品，评审结束后可以建议走“补档”。

## 六、不做的事

- 有 P0、P1 时，不先处理纯审美问题。
- 不改已确认的任务语义；评审发现语义有问题，写进报告，交给用户决定是否回到交互关。
- 不把通用“最佳实践”当证据。每条问题都要有走查步骤、脚本规则或具体画面作证据。
- 不宣称“分数提高了多少”。模型评审只做筛查，结论来自用户比较和真实操作。

## 来源

- [NN/g：认知走查](https://www.nngroup.com/articles/cognitive-walkthroughs/)：每步四个问题，适合新流程。

- [Scott Hurff：UI Stack](https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/)：每屏的状态。
- UIClip（2024）、WebDevJudge（ICLR 2026）、Duan 等（CHI 2024）：模型评审界面的能力与局限。
