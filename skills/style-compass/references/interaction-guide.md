# 第 2 关 · 确认交互 —— 可点低保真原型，动线靠点不靠读

> **位置很关键：在结构定了之后、上视觉之前。** 这是把“怎么动”单独敲定的一关。
> 为什么单列：让用户从一张静态线框脑补整套交互，要求太高。动线必须能**点着感受**，不能只读文字描述。
> 分层铁律：UX 这关只管**交互动线**，仍然保持**灰阶、线框级、不上任何风格**。视觉是下一关的事，别混。

## 为什么不放到最后、不上风格

- **放最后**（UI 之后再确认交互）→ 用户得先接受一个视觉稿才谈动线，顺序拧了；而且交互若要改，视觉会白做。
- **上了风格** → 用户更容易去评论颜色好不好看，而不是“这个动线顺不顺”。灰阶有帮助，但研究里真正让注意力留在交互上的，是给用户具体任务去做（低保真和高保真能发现的问题数量相当，Walker 等，2002）。所以本关既保持灰阶，也用任务来评审。
- 所以：**灰阶可点原型专门敲定动线。UX 定了以后，任务语义、动作结果和状态流转不动；控件和构图仍可在视觉关重做。**

## 做什么：一个灰阶、可点、可讲解、可评论、可对比的低保真原型

在第 0 关的线框基础上加真实交互，**保持灰阶、不上品牌色和品牌字体**。原型必须套用 `review-framework.md` 的公共评审工作台：

- **体验模式**：走真实产品动线，检查步骤和反馈。
- **讲解模式**：点击大模块查看完整说明；右侧上下文检查器自动展开，支持从头讲解，不要求用户自己猜。
- **评论模式**：单击放评论钉，拖动框选区域；右侧检查器显示意见状态，评论模式不触发产品动作。
- **对比模式**：把二至四张页面按 A、B、C、D 并排，右侧检查器负责选择对比对象。

四个入口常驻画布左侧，用户打开页面就能看见。
左侧“项目内容”按需管理页面、状态、素材和产物，底部对象坞在本关显示旅程与状态。窄屏打开右侧检查器时，左侧面板必须自动收起，不能把画布夹在中间。

产品本身要做到：
- **状态可切换**：点列表项后选中态迁移，点页签后内容切换。
- **核心动线走通**：该产品最关键的路径要让用户亲手走一遍。
- **条件显示**：错误横幅出现／消失、空态、禁用态都要让用户点出来看，不能只听描述。
- **过渡**：状态之间给出真实过渡，让用户感受快慢和稳定程度。灰阶阶段先不追求动效精细，只确认逻辑是否顺畅。
- **真实文案**：按钮、状态、空态和错误提示写真话（“保存失败，网络断开。重试”），不用灰条或“这里是提示”。按任务测试原型时，最多的两类问题是“说法和用户想的不一样”（28%）和“看不出系统在干什么”（17%），占位文案正好把这两类藏起来。

## 给用户之前，技能先自查三件事

1. **状态矩阵。** 每个关键页面列出它该有的状态：默认、空（第一次用、用户清空了、搜不到）、加载、部分完成、失败、成功、禁用。适用的都要能点出来，不适用的写“不适用＋理由”。来源：Scott Hurff 的 UI Stack。用户不用读这张表，它是技能的检查清单。
2. **异步、危险和乐观更新。**
   - 每个要等的动作，写清加载时显示什么、失败后显示什么、怎么重试或返回。
   - 危险操作优先给撤销（“已删除，撤销”），其次才是确认框；确认框只留给严重且不可逆的操作，按钮写动作本身（“删除 3 个文件”），不默认选中“确定”。NN/g：确认框用多了，用户会不看就点。
   - 先更新界面再等服务器的动作，写清失败后回到哪个状态。
   这三类在 `index.design.json` 里有对应字段（见 `stage-contracts.md`），校验脚本会检查填全了没有。
3. **新流程走一遍认知走查。** 对用户没见过的流程，逐步问四个问题：用户会想做这一步吗？能看到该点哪里吗？能把这个控件和想要的结果对上吗？做完能看出有进展吗？任何一个“不能”，这一步就不通过，先改再给用户。标准流程（登录、普通表单）不必走查。来源：NN/g 的认知走查方法。

## 交互关必须留下什么

交互确认不能只留下一个能点的 HTML。还要在 `index.design.json` 中记录：

- `J`：用户从目标到结果的一条完整旅程。
- `A`：旅程中的用户动作、前置条件和结果。
- `S`：用户能观察到的默认、进行中、成功、失败和恢复状态。
- 能力的可发现性：必须常驻、可以按需展开，还是允许放进菜单。
- 本关的“已确认、可发挥、待确定、验证证据”。

视觉关可以改变 `A` 的控件形态和位置，不能改变它的含义、步骤、结果和反馈时机。新增或删除动作、改变异常恢复、把常驻能力藏起来，都必须退回本关重新确认。完整格式见 `stage-contracts.md`。

## 怎么给用户确认（标准手段）

1. 原型 HTML 写到用户或宿主指定的产物目录（如 `<产物目录>/prototype/ux-proto-<屏>.html`），不默认写进工程根。
2. 用 `scripts/scaffold_review.py <prototype目录>` 生成 `spatial-studio/v1` 固定工作台。这里只补画板内的真实动线和设计清单，不重写工作台外壳。
3. **起带评论写入能力的服务给链接**，让用户**自己点**：
   ```
   python3 scripts/review_server.py --root <产物目录> --port 8823
   # 给用户：http://127.0.0.1:8823/ux-proto-<屏>.html
   ```
4. 自己先验证四种工具、模块讲解、点评论、区域评论、页面对比、评论回跳和解决状态，再交给用户。
5. 回读 `review-data/comments.json`，确认意见真实落盘，不能只存在浏览器本地。

## 确认什么（挑刺维度）

不问“看着怎么样”，给用户两到四个从旅程里拿出来的具体任务，比如“把项目 A 的截止日改到下周五”“删掉一个项目再撤销”，让他在体验模式里自己做完。做不下去的地方就是要改的地方。

- 动线**顺不顺**：完成核心任务的步数对不对、有没有多余跳转。
- 状态**齐不齐**：pending／sent、空态、错误态、禁用态有没有漏。
- 反馈**够不够**：点了有没有明确响应。
- 逻辑**对不对**：比如“重复点已选键＝取消”这类规则，要点出来验证。

挑完 → 改 JS／HTML → 再点一遍，循环到用户认可动线。**UX 认可后才进第 3 关做视觉。**

进入视觉关前还要运行层间契约校验，确认核心旅程、必需动作和状态都有稳定编号。仅凭“用户点过了”不能证明下一关不会漏掉它们。

局部意见与阶段结论分开：

- 评论钉和区域评论负责具体问题。
- “确认交互，进入视觉方向”负责整个阶段是否通过。
- 还有未解决的“必须修改”评论时，不得进入视觉方向。

## 边界

- **只敲动线，不碰视觉**：灰阶到底，一个品牌色都不上。
- **动效精细度放到第 3 关**：这里只确认逻辑动线是否顺畅，丝滑缓动等细节在视觉定稿时打磨。
- 交付前运行 `python3 scripts/lint_design.py check <交互原型>.html --phase interaction`：灰阶关出现彩色、图标按钮没有名字、可点的 div 都会被标出来。

## 方法来源

- [Walker 等（2002）：低保真与高保真原型发现的问题](https://www.leilatakayama.org/downloads/Takayama.Prototypes_HFES2002_prepress.pdf)：两者数量相当；按任务测试时，28% 的问题是说法与用户想的不一致，17% 是看不出系统状态，只有 10% 关于美观。
- [Scott Hurff：UI Stack](https://www.scotthurff.com/posts/why-your-user-interface-is-awkward-youre-ignoring-the-ui-stack/)：每屏的理想、空、加载、部分、错误状态及其过渡。
- [NN/g：确认框](https://www.nngroup.com/articles/confirmation-dialog/)：只给严重后果，优先撤销。
- [NN/g：认知走查](https://www.nngroup.com/articles/cognitive-walkthroughs/)：每步四个问题，任何一个“不能”就不通过；适合新流程。
- 原型的交互实现是“示意动线”，不是最终生产代码；但它会进入 spec 的“交互说明”，供下游还原。
