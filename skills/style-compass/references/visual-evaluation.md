# 比较设计方法是否有帮助

仅在维护技能、用户要求评测或验证方法改动时读取。日常单页设计不自动启动整套实验。

## 生成前冻结比较条件

写明要比较的两个版本、任务、内容、素材、参考、可变范围和验收方式。保存完整技能快照及摘要，冻结原始输入。不能把成熟成品的改进实验当成从零生成能力。

选择有实际差异的任务，例如长内容、密集操作、图片主导。已有产品保留原版参照；想测试稳定性时增加独立重复，不能只挑最好看的样本报告。

每组使用同一模型、可用工具、内容与素材，给相同的生成机会和修复预算，记录实际工具次数与可取得的用量。宿主无法限制 Token 或采样参数时如实说明。若只给一组更多参考或素材，结论只对这一组合成立，不能归因于文字规则。

## 生成、修复和评审分开

有子 Agent 能力时，必须为每份独立候选启动干净上下文的生成 Agent，只提供该任务、对应版本的方法及共同材料；禁止继承另一版本、评审倾向或主 Agent 的设计解法。同一 Agent 不连续生成一组的新旧两稿。

首稿先冻结。两组使用相同的完整性、运行检查和修复机会，修复范围提前约定，保留前后差异。缺图、字体回退、内容删减、交互缺失或未完成样本都计入结果；不能把失败稿悄悄替换或删除。以视觉改进为目的的额外迭代应另立记录，不覆盖首稿实验。

独立评审必须使用新的子 Agent，上游只给共同需求、匿名稿和相同范围的截图及操作证据；不得给版本映射、作者解释或期望结论。至少两位评审独立判断时，保留分歧，不能为了求一致反复重评。没有子 Agent 能力时，改为人工评审或明确“作者自核”，不声称独立或双盲。

版本映射由协调者保存，评审前固定各对稿件的展示顺序并打乱新旧位置。用户看稿前可以先不给评审结论，降低暗示；结果揭晓后收到的意见如实标为知情反馈。

## 分开回答几个问题

| 问题 | 证据 |
|---|---|
| 内容与任务是否完整 | 原始需求对照、实际状态与操作记录；源码声明仅辅助 |
| 画面是否改善 | 整页和实际尺寸的关键区域；默认、展开、选中等相关状态 |
| 使用过程是否协调 | 关键路径的实际点击、联动与必要录屏 |
| 是否有吸引力和辨识度 | 匿名评审的整体偏好及具体画面理由 |
| 是否更适合目标用户 | 任务与情境下的取舍；AI 评审不代替真实用户研究 |

评审逐对给出“甲更好／乙更好／接近／各有优势／无法判断”，附具体区域或状态、改善、退步和不确定性。不要把可读性、功能、气氛混成一个固定总分。可以按本轮研究问题记录分项，但必须额外判断整页，不能靠组件逐项加分推出整体审美。

## 报告全部结果

保留输入、版本、提示、首稿、修复、匿名映射、截图和评审原文。原稿与修复稿分别报告；先揭示失败与缺失，再汇总偏好。

不同评审看同一稿不算增加独立生成样本；同类重复也不等于更多产品类型。小样本只能支持本轮倾向，不报告普遍胜率或因果收益。多个手段一起改变只能评价组合效果，确认具体贡献需要后续控制其他条件。

对比稿统一装入既有空间画室，按任务、方案与状态组织，不另写评审外壳。实验允许直接进入已冻结的视觉任务；阶段状态标为实验或待评，不能伪造产品的人审批准。若 iframe 无法支持模块评论或语义检查，明确限制并提供完整页面，不假称覆盖门禁通过。

技能机制验证与视觉效果验证分别收口。源码、打包和工作台测试通过只能证明交付链路正常；方法未显出增益时保留实用改动、撤回过强结论，不为制造“升级成功”继续改评测稿。

## 行为用例和确定性指标

每次改技能，先跑两样不需要人看的东西：

- **脚本单元测试**：在技能根目录运行 `python3 -m unittest discover -s tests`。
- **行为用例**：`evals/evals.json` 里每条用例给出输入、技能应该做的事和不应该做的事，比如“模糊需求不连环发问”“用户说‘像 Linear’时补一个反向候选”“删除操作用撤销而不是确认框”。改动后逐条过一遍，记录通过与否。

能自动算的指标：

| 指标 | 来源 | 说明 |
|---|---|---|
| 设计检查的 error、warn 数 | `lint_design.py check --json` | 按阶段比较，越少越好 |
| 候选拉开程度 | `lint_design.py diverge` | 每对候选的差异轴数，最少一对也要达到三轴 |
| 守 token 程度 | `check --tokens` 的 `TOKEN-COLOR`、`TOKEN-DRIFT`、`TOKEN-FONT`、`TOKEN-FONT-SIZE`、`TOKEN-RADIUS`、`TOKEN-SPACING` | 页面的颜色、字体、字号、圆角和间距有多少不在 tokens 里 |
| 感受词命中 | `design_memory.py record --words` | 用户看图选出的词里，目标词和反面词各几个 |

这些指标有一个缺陷要写进报告：新版技能知道这些规则，用新版自己的检查去评新版，天然占便宜。它们只能证明“规则被遵守了”，证明不了“更好看”。

## 模型评审的边界

- 不让模型给界面审美打绝对分。GPT-4V 在成对挑选更好的界面时只有 51.58% 准确率，接近随机（UIClip，UIST 2024）。
- 要用就用两两比较，配检查清单和多状态截图。网页开发评审中，两两比较稳定好于单独打分，但最强的模型与专家的一致率也停在约 70%（WebDevJudge，ICLR 2026）。
- 模型的批评只做一到两轮：有用程度随轮数下降（Duan 等，CHI 2024）。
- 一个人的口味只能由这个人判断。n=1 的偏好结果只说明“对这位用户这一轮”，不外推。
