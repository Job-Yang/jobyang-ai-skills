# 设计阶段契约

结构、交互和视觉可以分开确认，但不能各做各的。每一关都要把已经确认的事实写进同一份 `index.design.json`，下一关只能在明确允许的范围内继续设计。

## 每一关都记录四类信息

- **已确认**：下游必须继承。要修改时必须退回产生该结论的关卡重新确认。
- **可发挥**：下游可以重新组织，不需要逐项请示。
- **待确定**：本关有意不做决定，必须写清由哪一关继续处理。
- **验证证据**：说明本关凭什么通过。可以是需求验收项、浏览器操作结果、截图或结构化校验报告。

四类信息缺一不可。只写“已确认”会把后续锁死；只写“可发挥”会让能力在重画时丢失；没有“待确定”会把模型猜测混进结论；没有证据则不能进入下一关。

## 稳定语义编号

编号表达产品语义，不表达控件长相：

| 前缀 | 对象 | 示例 |
| --- | --- | --- |
| `R` | 需求 | `R01`：用户能查看设计项目 |
| `P` | 页面或稳定工作区 | `P02`：设计工作台 |
| `J` | 用户旅程 | `J03`：针对具体区域留下意见 |
| `A` | 用户动作 | `A05`：提交区域评论 |
| `S` | 可观察状态 | `S06`：评论保存成功 |

视觉关可以把 `A05` 从页内按钮改成工具栏、浮层或右键菜单，但不能删除 `A05`，也不能悄悄改变它到达的状态。语义发生变化时，退回交互关。

## 各关边界

### 需求

必须确认：

- 目标用户、问题和成功标准。
- `in-scope` 与 `out-of-scope`。
- 每项需求的验收标准和稳定 `R` 编号。
- 平台大类与关键约束。

可以发挥：

- 页面数量、布局、控件、视觉和技术实现。

门禁：

- 每项范围内需求都可验证。
- 关键问题没有被模型擅自补全。
- 用户明确批准需求工件。

### 结构

必须确认：

- 页面或稳定工作区及其 `P` 编号。
- 每项需求由哪个页面或模块承载。
- 页面职责、信息层级和页面关系。
- 必须常驻、允许按需展开和允许隐藏的能力。

可以发挥：

- 精确尺寸、网格、组件形态、颜色、字体和动效。
- 在不改变页面职责的前提下调整区块位置。

门禁：

- 每个 `R` 至少映射到一个 `P`。
- 不增加需求外功能，不遗漏范围内功能。
- 用户能通过灰阶线框理解页面关系并明确批准。

### 交互

必须确认：

- 核心旅程及其 `J` 编号。
- 每个旅程中的动作 `A`、前置条件、结果状态 `S` 和反馈。
- 成功、空、加载、错误、禁用和恢复路径中与任务成立有关的部分。
- 能力的可发现性：必须常驻、可以收起，还是允许藏进菜单。

可以发挥：

- 按钮、菜单、抽屉、工具栏等具体控件。
- 精确位置、视觉层级、品牌风格和动效曲线。
- 不改变步骤和结果的文案微调。

门禁：

- 核心旅程可以从头点到尾。
- 必需动作和状态都有稳定编号。
- 每个 `A` 的触发条件与结果状态明确。
- 未解决的“必须修改”意见为零。

下面这些变化必须退回交互关：

- 新增或删除动作。
- 改变完成任务的步骤。
- 改变动作的结果、反馈时机或异常恢复。
- 把已确认的常驻能力藏进菜单。
- 改变页面职责或入口关系。

### 视觉定稿

视觉定稿保留一个正式关卡，但包含两个检查点。

#### 方向候选

必须确认：

- 构图方式、组件语言、信息密度、导航呈现和视觉气质。
- 每个候选如何承载交互关确认的 `J`、`A` 和 `S`。

可以发挥：

- 导航、控件和空间关系的具体实现。
- 色彩、字体、图标、圆角、材质、层级和动效表达。

候选不必展开所有重复页面，但必须覆盖：

- 全部核心旅程。
- 所有不同的交互模式。
- 会决定布局是否成立的关键状态。
- 支付、删除、权限、数据写入和错误恢复等高风险状态。

门禁：

- 每个候选的方向必需 `J/A/S` 覆盖率为 100%。
- `A` 对应真实可操作控件，不能只写在说明里。
- 每个候选单独看都像成熟产品。
- 用户只是在这里选择或融合方向，还没有批准最终交付。

#### 全量完成

选定方向后，继续在同一关展开：

- 全部 `P` 页面或工作区。
- 全部最终必需 `J/A/S`。
- 响应式、真实文案、边界状态和动效细节。

门禁：

- 交互关的用例在选定高保真方案上重新执行并全部通过。
- 所有页面、动作和状态覆盖率为 100%。
- 视觉截图、交互证据和未解决意见都已回读。

只有通过这个检查点，产物才叫“视觉定稿”。此前统一称“高保真方向候选”。

### 设计交付

必须确认：

- 最终 HTML、`index.design.json`、设计规格和评审记录一致。
- `R → P → J → A → S` 可以完整追溯。
- 下游能从原型和规格还原行为，不需要回聊天记录猜。

可以发挥：

- Coding 节点的框架、代码结构和具体工程实现。

门禁：

- 运行 `validate_stage_contract.py --phase final` 通过。
- 最终原型在目标桌面与窄屏真实渲染通过。
- 人工批准设计交付后才能进入 Coding。

## `index.design.json` 最小结构

```json
{
  "schema": "design-stage-contract/v1",
  "projectId": "product-topic",
  "phase": "direction",
  "stageBoundaries": {
    "requirements": {
      "confirmed": ["R01"],
      "flexible": ["页面布局"],
      "deferred": ["具体控件"],
      "evidence": ["prd 已人审"]
    }
  },
  "requirements": [
    {"id": "R01", "title": "查看项目", "acceptance": "能进入指定项目"}
  ],
  "pages": [
    {"id": "P01", "title": "项目总览", "requirementIds": ["R01"]}
  ],
  "journeys": [
    {
      "id": "J01",
      "title": "进入项目",
      "actionIds": ["A01"],
      "directionRequired": true,
      "finalRequired": true
    }
  ],
  "actions": [
    {
      "id": "A01",
      "title": "打开项目",
      "fromState": "S01",
      "toState": "S02",
      "directionRequired": true,
      "finalRequired": true
    }
  ],
  "states": [
    {"id": "S01", "title": "项目列表", "directionRequired": true, "finalRequired": true},
    {"id": "S02", "title": "项目已打开", "directionRequired": true, "finalRequired": true}
  ],
  "variants": [
    {
      "id": "direction-a",
      "phase": "direction",
      "pageIds": ["P01"],
      "journeyIds": ["J01"],
      "actionIds": ["A01"],
      "stateIds": ["S01", "S02"]
    }
  ]
}
```

HTML 中使用相同编号：

```html
<article data-review-variant="direction-a" data-design-journey="J01">
  <button
    data-design-action="A01"
    data-design-result="S02"
    data-prototype-action="state:project-open"
  >打开项目</button>
  <section data-design-state="S02">项目内容</section>
</article>
```

一个元素可以承载多个语义编号，属性值用空格分隔。`data-design-action` 所在元素必须同时具备真实的 `data-prototype-action`，并用 `data-design-result` 标出动作结果，避免“声明覆盖，实际点不了”。

## 验证责任

- 用户确认产品取舍和视觉偏好。
- Agent 负责生成契约、检查覆盖、执行交互路径并提供渲染证据。
- 校验脚本负责查编号、引用和覆盖完整性。
- 任何一方都不能用“看起来差不多”替代上一关的明确结论。
