# 多人协作大仓生产安全清单（按需查阅）

> 面向多人迭代的中大型代码仓（接口兼容性、数据库变更、并发热点、灰度回滚与最小验证范围），仅在涉及对应变更时按需核对。

## 一、向前与向后兼容（新老版本混跑安全）

滚动发布、蓝绿切换与多客户端版本并存期间，**新老代码与新老数据必然同时运行**：

- **接口与协议（HTTP / RPC / MQ / 缓存值）**：
  - 新增请求字段设为可选并提供兼容默认值；新增响应字段不破坏既有强校验消费方。
  - 严禁直接重命名、删除或改变仍在被调用的字段类型/枚举值；需要淘汰旧字段时先双写或兼容读取，确认旧流量归零后再另起 PR 清理。
  - 序列化/缓存 Key 若变更结构，必须显式升级版本号或键前缀，防止反序列化旧缓存崩溃。

## 二、数据库与持久化迁移（Expand-and-Contract）

在 `release` / `release-solo` 阶段，严禁一把梭破表或长锁阻塞线上读写：

1. **Expand（只增不破坏）**：新增可空列/带轻量默认值的列、新表或新索引（大表索引使用在线无锁建索引策略），保持老版本代码仍能正常读写。
2. **Backfill & Dual-Write（分批回填与双写）**：先上线兼容新旧结构的代码，再通过可限流、可断点续跑的离线脚本分批回填存量数据，避免单次大事务打满连接池或主从延迟飙升。
3. **Contract（延后清理）**：待全量实例切到新代码且回滚窗口已过，再单独提小 PR 移除兼容分支与废弃列/表。

## 三、并发、幂等与热点保护

- **状态与缓存一致性**：先落持久化真相源再失效/更新缓存，避免先删后写或并发旧读回填脏数据；读路径不应隐式顺手改写主状态。
- **幂等与防重**：写接口、消息消费、异步任务与定时补偿必须基于业务唯一键或状态机 CAS 保证幂等，重试不能重复记账或发重复通知。
- **锁粒度与超时**：严禁在持有数据库事务或分布式锁期间发起外部网络 RPC；跨资源加锁固定顺序以防死锁；外部调用均须显式设连接/读取超时与有界重试，拒绝无上限重试与全表扫描。

## 四、灰度开关、可观测与一键回滚

- **高危改动必带逃生开关**：涉及核心链路改写、新算法切换或第三方依赖替换时，优先挂配置开关或百分比灰度开关，确保无需重新发版即可秒级切回老逻辑。
- **回滚预案先于合入**：明确该变更若线上出问题能否直接回滚代码；若含不可逆数据结构调整，必须提前写明兼容读取方案与数据订正边界。
- **关键观测信号**：只增加能定位失败原因的结构化错误日志、关键路径耗时与错误计数，避免打印明文凭证、敏感 PII 或高频刷屏日志。

## 五、多人大仓的最小高置信验证策略

- **不强跑全仓耗时长构建**：优先跑变更所在包/模块的单元测试、类型检查与静态分析，加上所有直接下游调用方契约测试；无法跑全仓时在汇报中明确写清实际运行范围与未覆盖部分。
- **隔离脏树防假绿**：若本地工作树同时有其他改动或未提交文件，验证 PR 级改动前开临时 detached worktree 独立运行，避免未入库文件掩盖缺失依赖或构建错误。
- **跨团队公共表面标红**：改动共享 SDK、公共 Schema、权限拦截器、CI 工作流、构建/发布脚本或删除路径时，强制标记需对应模块维护者人工复核。
