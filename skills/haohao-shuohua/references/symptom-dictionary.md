# 症状词典：AI 味的五层病灶

按「一眼就能扫出」的可操作性，从浅到深排列：标点级 → 句式级 → 词汇级 → 结构级 → 结构排比级。前几层看得见，后两层最难看出但最致命。

每层给「命中模式 + 改法」，不给穷举，词表只是兜底。

---

## 一、标点级(最容易一眼抓)

### 1. 破折号 `——`

**头号 AI 味标点。** AI 用破折号做三件事，中文都不需要：
- 「停顿显得深刻」
- 「补一个金句尾巴」
- 「连接两个半句撑节奏」

**改法**：全篇搜 `——`，能换逗号就换，能句号就句号。全文最多留 1-2 个真的需要顿一下的地方。

**例**：
- ❌ 这条路的尽头，是一个新的开发范式——一个人机共写的时代。
- ✅ 这条路走到底，写代码就变成人和 AI 一起写。

### 2. 引号里的抽象词

「底层逻辑」「顶层设计」「范式」「心智」「抓手」这类词一旦加引号，基本是在给自己壮胆，潜台词是「我知道这词有点玄，先加个引号免责」。

**改法**：要么删引号直接说人话，要么把这个抽象词换成具体判断。

### 3. 括号里的英文注释

「上下文工程(Context Engineering)」「自主智能体(Autonomous Agent)」这种，除非是术语首次出现、读者可能陌生，否则一律删。多次出现的英文注释是 AI 露馅的地方，它记不住哪些是术语、哪些是常识。

### 4. 满屏加粗

AI 爱机械地给一堆词甩 `**加粗**`，一段里五六处，看着像重点，其实哪儿都不是重点。**全加粗，等于全没加粗。**

**判据**：一段里加粗超过一两处，先问哪个是真正想让人记住的一句。
- 留那一处，其余全删。
- 通篇没有一处非加粗不可的，那就一处都别加。
- **不算满屏加粗的**：列表项开头的标签（`- **保留期**：`）、引用块标签（`> **结论**：`）、表头。它们是结构的键，帮读者扫读，不删。技术方案、分享稿里给每段最要紧的那个词或数字加粗，也是正当的扫读锚点，每段一处即可。

- ❌ 更新改进了 **界面**，通过 **优化算法** 加快了 **加载时间**，还加了 **端到端加密**。
- ✅ 更新改了界面、优化了加载速度，还加了端到端加密。(哪个都不用加粗；真要强调，只加最想让人记住的那一件。)

## 二、句式级

### 1. 「不是 X，而是 Y」

**头号 AI 味句式。** 正文翻案壳与「不在 A 而在 B」默认拆净；仅上下文确实属于非此即彼的事实排错或引语原话时豁免。

**改法**：有话直说，不要先否定一遍再翻转。
- ❌ 这不是简单的技术升级，而是一次范式的重构。
- ✅ 这次改的是范式，不是升级。(或：这是范式变，不是升级。)

### 2. 「更是……也是……」/「既是……又是……」

表演式对仗默认砍掉；确实讲两种独立用途时按实分说。
- ❌ AI 更是工具，也是伙伴。
- ✅ AI 现在主要当工具用；真要写长流程，也能顶半个协作者。（若两半说的是同一层意思，直接砍掉后半。）

### 3. 「前者……后者……」

英文代词回指，中文没这个说法。**重复主语更自然。**
- ❌ Copilot 和 Cursor 都在做代码补全，前者更保守，后者更激进。
- ✅ Copilot 和 Cursor 都在做代码补全。Copilot 更保守，Cursor 更激进。

### 4. 「值得深思」「值得关注」「不禁让人思考」

元话语，拔高姿态，一律删。要判断就给判断，不要「值得」判断。

### 5. 「我们不禁要问……」「这引出了一个更根本的问题：……」

假想对话、自问自答，写议论文的老套路，砍。真有问题直接问，不要先铺一句「我们不禁要问」。

### 6. 「上述」「此」「该」

英文「the aforementioned / this / said」的直译。中文写「这个」「这」就够了，再不行就重复主语。

### 7. 「被」字句滥用

英文被动语态的直译。中文早有一套不靠「被」的被动：「糖吃光了」「稿写了一半」「饭做好了」，受事往前一放，被动的意思自己就出来了，不用「被」。AI 爱把每个被动都翻成「被 X」，读着一股译文腔。

| 改前 | 改后 |
|---|---|
| 我不会被你这句话吓倒 | 你这句话吓不倒我 |
| 这个问题已经被解决了 | 这个问题解决了 |
| 新大陆被发现了 | 发现了新大陆 |
| 方案被大家一致通过 | 方案大家一致通过 |

**判据**：「被」删掉、改主动，意思没变还更顺，就是滥用。真要强调吃了亏、要追责，或者施事不明才留「被」(「他被开除了」「钱包被偷了」这种，留)。

## 三、词汇级

### 1. 后缀病：XX 化 / 性 / 型 / 度

「化」「性」「型」「度」这一批后缀，来路有两条：一条是近代日本翻译欧洲著作时造的词(用「～化」「～性」对译 -ization / -ize / -ity)，中文译日本书时整套搬了过来；另一条是后来从英文 -ization / -ity 直接译的。**绝大多数删掉后意思不变，还更清楚。**补一句边界：这批后缀属恶性欧化，中文本来说得清，套层英文架子反而更糊，该删。善性欧化不在此列：「她」「它」的代词分工、「与其说……不如说」这类连词，是欧化带进来、如今真给中文长了本事的，别顺手一起砍了。拿不准先照 SKILL.md「去 AI 味」里那把朱光潜的尺量。

| 改前 | 改后 |
|---|---|
| 前置化 | 提前 |
| 系统化（空洞凑字时） | 做全 / 讲透 |
| 闭环化 | 走通 |
| 协作属性 | 一起干 |
| 颗粒度 | 多细 / 拆多细 |
| 滞后性 | 拖得太晚 |
| 复用性（非技术属性） | 能照搬 |
| 系统性梳理（空泛套话时） | 全面理一遍 |

**术语与实意红线：有确切工程定义的术语（如 `重构`、`解耦`、`可扩展性`、`可维护性`、`高可用`、`幂等`），以及表达方法范围的正常偏正短语（如「系统性排查方案」「系统化测试」），不按后缀病机械拆成大白话，一律保留原意。**

### 2. 「XX 这一环节 / 这一过程 / 这一维度」

冗余名词化，双重赘余。直接删「这一 XX」，把「环节 / 过程」也一起删。
- ❌ 验证这一环节需要被前置化。
- ✅ 验证要提前。

### 3. 强调副词泛滥

「至关重要」「极其关键」「从根本上」「在很大程度上」「毫无疑问」，**靠副词撑分量，说明判断本身不够硬**。

**改法**：删掉副词，把判断本身改到不需要副词撑。
- ❌ 这一点至关重要。
- ✅ 没这一步别的都白搭。(把「重要」翻译成一个具体后果。)

### 4. 万能动词：「进行 / 实现 / 完成 / 作出 + 名词」

这类词余光中叫「万能动词」，最泛滥的两个是「作出」和「进行」，他说这俩「恶势力之大，几乎要吃掉一半的正规动词」。奥威尔把这种没肉的动词叫「文字的义肢」。英文「conduct / perform / achieve / make + noun」的直译架子，全靠它们撑着。**把假腿卸掉，让底下那个真动词自己站起来，事情一句就成立。**

| 改前 | 改后 |
|---|---|
| 对代码进行验证 | 验证代码 |
| 实现效率的提升 | 提效率 |
| 完成对方案的讨论 | 讨论方案 |
| 作出决定 | 定下来 |
| 作出重要贡献 | 出了大力 |
| 对方案进行系统性的梳理 | 把方案全面理一遍 |

### 5. 空形容词

「深刻」「重要」「颠覆」「值得」「令人震撼」「深远」，**删掉，用事实让读者自己感受**。
- ❌ 这带来了深远的影响。
- ✅ 三个月后，团队里没人再手写单测了。

### 6. 凭空归因(和保事实是一对镜像)

「有研究表明」「业内普遍认为」「专家指出」「不少人认为」「相关数据显示」，AI 爱造一个查无此人的权威给自己壮胆。

**这条和第一原则「保事实」正好是镜像**：保事实防你把真来源(「Kenneth Li 等，ICLR 2023」)简化成「有研究发现」；这条防你根本没来源、却凭空编一个。

**判据**：这个「权威」能不能指名道姓？
- 能 → 补上真出处。
- 不能 → 要么删掉这半句直接说结论，要么老实认账，改成「我」的判断。

- ❌ 有研究表明，验证前置能显著降低缺陷率。
- ✅(有真源)据 DORA 2023 报告，验证越靠前，线上缺陷越少。/(没源就认)我自己几个项目试下来，验证提前，线上问题肉眼可见地少。

### 7. 同义词循环：一个东西换着叫

同一个所指，AI 怕重复，换着法儿叫，一会「Agent」一会「智能体」一会「该体」一会「这一系统」。这是模型的重复惩罚机制闹的，中文不吃这套。

**中文不怕重复，重复主语反而清楚**(和句式级「前者后者」那条一个道理：中文靠重复衔接，不靠代词回指)。

**判据**：同一个东西换了 3 种以上叫法 → 统一成最准的那一个，从头叫到尾。

- ❌ Agent 先规划任务，该智能体再执行，这一系统随后复盘。
- ✅ Agent 先规划，再执行，然后复盘。(从头到尾就叫 Agent。)

### 8. 「当……时 / 当……的时候」滥用

英文「when / while + 从句」的直译。中文很多时候不用先起个「当」，把事直接说出来就行。
- ❌ 当模型收到指令时，它会先做规划。
- ✅ 模型收到指令，先规划。

### 9. 时间、地点前硬加「在」

英文 in / on / at 的直译，句首时间地点前面塞个「在」。中文本来不用。
- ❌ 在昨天的会上，我们定了方案。
- ✅ 昨天开会，方案定了。

### 10. 「作为」硬译 as

英文「as a ...」的直译。中文说身份、说角色，多数时候直接说，不用先「作为」起头。
- ❌ 作为一名工程师，我觉得这样不妥。
- ✅ 我是工程师，我觉得这样不妥。

### 11. 「是……的」判断句

英文 be + 形容词 / It is ... that ... 的直译。中文形容词能直接当谓语，不用先立一个「是」、末尾再补一个「的」。
- ❌ 这一步是至关重要的。
- ✅ 关键就在这一步，少了它别的都白搭。

### 12. 「最……之一」

英文「one of the most ...」的直译。中文本来没这个说法，要么说它最，要么老实说它是其中一个，别嫁接（**场合豁免**：产品介绍、招聘 JD、活动宣传文案中的「最具……之一」按 `SKILL.md`「场合分档」保留，不按此条硬拆）。
- ❌ 这是今年最重要的更新之一。
- ✅ 今年几个大更新，这是其中一个。

### 13. 「一个 / 一种 + 一长串定语 + 名词」

英文「a + 从句 + 名词」的直译，把一整句修饰硬塞进「一个……的 X」里。中文把事说完再落到名词上。
- ❌ 我们要的是一个能够充分理解上下文并据此做出合理决策的智能体。
- ✅ 我们要一个 Agent，能看懂上下文，再做决定。

> **8–13 合用一条边界。** 这六项都是英文骨架的直译，但每种都有正当的中文双胞胎：「在这个问题上」「作为惯例」「这是必要的」本身没病。判据看骨架，是硬把英文架子套进中文，还是中文本来就这么说。念一遍，顺的留下，硌牙的才动，别见「在」「作为」「是……的」就一律删。

### 14. 英文机翻怪词与强行全中文化

AI 写工程文和方案汇报时，常把英文软件名词直译成五金、裁缝、电工或教育学冷门词，或者把大家平时本来直呼英文的词强行全中文化。

**先过防误杀保护边界（动手前必看）：**
- **代码、字段名与框架专名不动：** 反引号内的代码、API/协议字段名（如字段本身叫 `payload`）、框架约定专名（如 `pytest` 的 `fixture`）以及含「门/网/钩」等字的特定模块与编译器专名（如「裁决门」）一律原样保留。
- **引文与真实语境不动：** 引号内他人原话或被批评原词不动；真实物理、法律与特定算法语境（如车间机床夹具、小区刷卡门禁、房屋租赁契约、A* 启发式搜索算法、论文消融实验）保留原意。
- **场合让路边界：** 仪式与品牌宣示场合（品牌/官方对外公告、感谢信、内部信、公关、培训定性）遵从 `SKILL.md`「场合优先」，保留官方宣传提法与行业常见修辞（如「数字底座」「安全护栏」「全链路遥测」），不强行拆改。
- **只做等义换顺：** 替换怪词时不顺手添原文没有的限定词或承诺，也不用「测试 Mock」「Harness 框架」这类中英叠词。

**第一档 · 明确换掉（12 项生硬机翻，习惯直呼英文的直接留英文）：**

| 怪词（原词） | 改法 | 例外边界 |
|---|---|---|
| 夹具（fixture） | 测试样例 / 测试数据 | pytest 语法语境留 `fixture`，车间机床夹具除外 |
| 门禁 / 硬闸（gate） | 检查卡点 / 拦截检查 / 通过门槛 | 物理刷卡门禁、特定模块/编译器专名（如「裁决门」）除外 |
| 接缝（seam） | 隔离口 / 可替换接口 | 物理缝纫除外 |
| 替身（test double） | 模拟对象 / 按实指写 `Stub`、`Mock`、`Fake` | 影视替身、测试分类学专讲「测试替身」除外（勿叠加写成「测试 Mock」） |
| 挽具 / 线束（harness） | `Harness` / 运行框架 | 马具、汽车线束实体除外（勿叠加写成「Harness 运行框架」） |
| 套接字（socket） | `socket` | 平时直接用英文 |
| 钩子（hook） | `hook`（代码机制）/ 回调・触发点 | 代码语境留 `hook`；内容创作「悬念钩子 / 开头钩子」与物理挂钩留中文 |
| 载荷（payload） | 请求体 / 数据内容 / 消息体 | API 字段本身叫 `payload`、航天/货运「有效载荷」除外 |
| 评分量规 / `Rubric` | 评分标准 / 打分清单 | 教育学研究专引原词除外 |
| 制品 / 工件（artifact） | 产物 / 构建包 / 交付文件 | 考古文物/实体零件除外 |
| 接地（grounding） | 核对事实 / 有据可查 | 电工物理接地、俗语「接地气」除外 |
| 遥测（telemetry） | 埋点 / 监控上报 | 航天/工业硬件遥测除外 |

**第二档 · 看语境优先换（9 项偏 AI 味词，非论文/底层特定语境优先换自然中文）：**

| 偏味词（原词） | 建议改说 | 可保留语境 |
|---|---|---|
| 护栏（guardrail） | 安全限制 / 红线检查 | 安全产品专名、实验「护栏指标」、模型安全护栏（LLM Guardrails）或道路实体 |
| 契约（contract） | 接口约定 / 协作规范 | 法律合同、接口契约测试、数据契约 / 契约式设计 / 社会契约 |
| 漂移（drift） | 跑偏 / 走样 / 不同步 | 讲数据分布漂移专业概念 |
| 消融（ablation） | 对比测试各项的作用 / 分开验证改动效果（按具体对象重写，勿照搬「某项」空词） | 写算法实验、论文复现 |
| 句柄（handle） | `handle` / 引用 / 操作入口 | OS / Windows 底层 API 文档 |
| 基元 / 原语（primitive） | 基本操作 / 最小单元 | 操作系统并发原语语境 |
| 锚点 / 锚定（anchor） | 基准 / 参照 / 标尺 | 页面/文档/视觉锚点、锚定效应、价格锚点、目标锚框 |
| 分诊（triage） | 分类 / 分流 / 排优先级 | 医院急诊真实流程 |
| 启发式（heuristic） | 经验规则 / 按经验推出来的做法 | A* 启发式搜索等算法专语（不用轻佻口语） |

**显式放行白名单（行业已习惯，不误杀成大白话）：** `编排`、`脚手架`（建项目/框架初始化语境；作文章过渡比喻时改直述）、`鲁棒性`、`柯里化`、`副作用`、`蒸馏`（模型/知识蒸馏算法语境；禁跨物类写「把摘要蒸馏到邮件里」）、`涌现`、`对齐`、`冒烟测试`，以及 `重构`、`幂等`、`回滚`、`竞态`、`死锁`、`冷启动`、`脱敏`、`吞吐量` 等已有稳定共识的技术术语，原样保留；原文已写自然中文（如「运行框架」「模拟对象」）时勿回译成英文。

## 四、结构级(最难看出，但最致命)

### 1. 段末打钉

**每段最后一句都在空喊拔高。** 段末贴一句宏大升华或空口号（如「标志着一次深刻变革」「永远在路上」「受益终身」），是这类 AI 养成的习惯，不是中文的写法。

**改法**：段末删掉空喊升华与复述废尾巴，让段落收在最后一件实事或核心判断上（注意区分：如果原句本身指出了明确因果后果或决策影响，属于核心论断而非空升华，去腔保留，不误砍）。
- ❌ ……三个月后，没人手写单测了。这标志着开发范式的一次深刻变革。
- ✅ ……三个月后，没人手写单测了。

### 2. 逢三凑数

「更快、更强、更稳」「前置化、系统化、闭环化」「体验债、沟通债、认知投降」。

**看到三连罗列先问：是真的有三样，还是凑的？** 大部分是凑的。挑一个真的、砍掉另外两个，或者用一个更准的判断替代整个三件套。

真有三样（三项风险、三个批次、三种方案），就别砍，也别塞进一句话：拆成列表或表格，见 `reader-layout.md`。

### 3. 过度均衡

下一个判断后紧跟一句「当然，也不能忽视……」「另一方面……」「值得指出的是……」把话说回来。

**这不是严谨，是害怕。** 判断本身应该敢下、可被反驳。要补充例外，单独开一段说，别在判断后头立刻缩回去。

### 4. 「A 和 B 是同一个 X」

英文「A and B are the same X」骨架。中文更自然的说法是把它拆掉，用因果或转折。
- ❌ 这套评分标准和欧化中文的病灶是同一个东西。
- ✅ 评分员看重什么，欧化中文的病就长什么样。

### 5. 铺垫—展开—小结三段式

一段里先说「我要讲 X」→ 讲 X → 「所以刚才讲了 X」。**直接讲。** 铺垫和小结都是废话（若是多节技术文档里用来界定覆盖边界的真实范围声明，如「横向扩展暂不展开，本节只讲顺序」，属有效结构路标，写简洁后保留）。

### 6. 正文里的免责尾巴

正文写完，后面再跟一句交代自己依据了什么、没核实什么：「以上仅依据你提供的情况，未做额外核验」「以上判断只基于这两个月的数据」「未核实实际进度，以上时间按你的预估表述」。这句话是写稿的人在交代自己怎么写的，收信人用不上。正文要转发出去，这句会原样带给收信人。

它常常是从「核对出处」「给作者提醒」这两条规矩里漏出来的：核对本来是写稿人自己的检查，提醒本来该单独写给作者，结果都混进了正文。

**判据**，两种都删：

- 这句在交代正文是怎么写出来的：依据了什么、核没核实、按谁的预估。
- 这句只是把正文已有的不确定再说一遍，比如前面写了「预计最早明天下午」，后面又跟一句「具体时间还得看结果什么时候返回」。删掉原文没有的承诺以后，最容易在原来的位置补上这么一句。

原文自己写着的「尚未核实」「还要看结果」是原意，留着。真有要提醒作者的，单起一段，以「【给作者】」开头。

- ❌ 我建议继续保留工程师的合并审批……以上判断仅依据这两个月的尝试，尚未验证 AI 在其他代码中的表现。
- ✅ 我建议继续保留工程师的合并审批……（到正文最后一句为止，不加那句尾巴。）
- ❌ 实验报告今天下班前交不了了……预计最早明天下午能交。这两项结果目前还无法核验，交付时间还要看结果什么时候返回。
- ✅ 实验报告今天下班前交不了了……预计最早明天下午能交。（「最早」已经把不确定说了，不用再补一句。）

## 五、结构排比级(AI 最爱，双族)

模型特别喜欢生成有编号感、有对仗感的内容，看着条理清晰，读着像机器打印的。**核心判据：数量和对仗本身不是判断，只是形式。用数量和对仗给内容贴标签，就是排比病。** SKILL.md 主体只留判据，反例改法在这里。

### 显性族

**A1 · 量词标题与表演标签序列（标题、正文段落与列表项同适用）**：标题、正文或列表项拿「数字 + 动作/武侠/闯关量词」贴标签，如「第一刀·第二刀·第三刀」「三板斧」「组合拳」「杀手锏」「第一关 / 过三关」「四个步骤」「五个维度」。病在拿数量和戏码当标签，不在用列表：步骤本身用有序列表 `1. 2. 3.` 写清每步做什么，是对的。
- 判据：把「第 N 刀/关/步/条」或「组合拳/三板斧」直接删掉，换成本节/本句真正要做的具体动作或论断，换完更清楚就是表演量词病（不要换成另一套武侠词敷衍）。
- ❌ 把去 AI 味的方法写成「减法五刀」，列「第一刀……第五刀」作标题；或在正文写「这套组合拳分三关打通」。
- ✅ 去掉「刀」「关」「组合拳」，每节标题直接陈述本节观点，正文直接写具体做法和前后顺序。

**A2 · 分号/破折号串三连**：用分号或破折号把三个及以上子句串成一句，强迫读者一口气跑完多个并列判断。
- 改法：断开成独立句，按逻辑顺序排列。

### 隐性族(不带数字，藏在句子里，更容易漏)

**B1 · 「X 不 X」三连以上**：反复用「X 不 X」并列判断，超过两个就是排比。
- ❌ 节奏管的是顺不顺、憋不憋气、够不够口语。(三个串一起。)
- ✅ 节奏管的是句子顺不顺、憋不憋气，不是够不够口语。(前两个对同一件事，末一个改陈述句。)

**B2 · 「不是 X 而是 Y」变体族(含翻案体)**：含「这不是 X」「A 不是病，B 才是病」「管的是 A 不管 B」「不在 A，而在 B」；以及先抑后翻的翻案体「你以为 X，其实 Y」「看似 X，实则 Y」「表面上 X，实则 Y」「回头才发现 X」「真正 X 的是 Y」「A 不重要，重要的是 B」。标题级极易露 AI 味，正文级同样是主要 AI 味源。
- 改法：正着立出 Y；X 若只是虚设垫话才删去，若 X 是前文真实前提、症状或权重参照，按上下文顺改为让步或因果主次句（「虽然……」「只做 X 解决不了，重点在于 Y」），不硬删造成前后断层；确属非此即彼的事实排错或引语原话豁免。
- ❌ 这不是玄学 / AI 味不是标点问题，是句法问题 / 管的是节奏，不管口语度。
- ✅ 这一步不玄 / AI 味的病根落在句法上，不在标点。(正着说，一个判断说完。)
- ❌ 你以为改的是标点，其实改的是句法。/ 看似是词的问题，实则是骨架的问题。/ 回头才发现，真正难的是节奏。
- ✅ 改的是句法，标点只是表面。/ 词只是表象，骨架才是根。/ 最难的是节奏。(翻案体按语义拆壳，先抑若属虚设垫话则删净，把结论正着讲。)

**B3 · 二连对仗**：「就该 A，就该 B」「不必 A，更不必 B」「A 是病，B 也是病」这类前后完全同结构的两小句。密度低不算病，但一段出现两次以上、或一句就用两次，即排比病。
- 改法：合成一句陈述，或只保留最关键的那半。
- ❌ 技术文档就该严谨，就该有长句。/ 不必拆成短句，更不必掰成口水话。
- ✅ 技术文档该严谨，长句该有。/ 补个逗号让它喘得上气就行，不必拆句。(结构不再对称。)

**B4 · 段内三连罗列**：一句里连着甩三个以上并列的名词/动词/短语。
- 改法：合并同义(取最准的一个)，或改成一句判断。三项是真不同的东西、各自还带说明，就拆成列表，不合并。
- ❌ 念到哪里卡壳、拗口、气喘不上，就是那里还没治干净。(三个近义并列。)
- ✅ 念到哪里读不顺，就是那里还没治干净。

**双族统一判据**：把这几个并列项都盖住，只留一个最要紧的判断，读者理解会不会少？不会 = 排比病，删或改陈述句。会 = 保留，节奏上补一处停顿。

## 下刀(按顺序机械做)

改稿时按这个顺序走，走完大半 AI 味就没了。

### 名词化，还原成动词

AI 中文最深的病灶。改法：把名词化的动作还原成真的动词。

| 改前 | 改后 |
|---|---|
| 需要对生成的代码进行严格的验证 | 要认真验证生成的代码 |
| 验证驱动开发的核心，在于将验证这一环节前置化 | 验证驱动开发的关键，是先验证再写 |
| 辞职人数的增加是由日渐上升的压力所导致的 | 压力越来越大，辞职的人越来越多 |

### 后缀病，删掉或换掉

见上面「三、词汇级」第 1 条。

### 破折号，换逗号或句号

见上面「一、标点级」第 1 条。全篇最多留 1-2 个。

### 前者后者 / 上述 / 此，重复主语

见上面「二、句式级」第 3 条。英文代词回指，中文靠重复主语衔接。

### 长复合句，断成短句串珠

AI 爱写一句话塞五六个成分，靠「的」和「从而/进而/基于」串起来。中文的呼吸是短的，一节一节推进。

**改法**：找连词，断句；找「的」字长定语，拆成前后两句。

- ❌ 基于对大量线上问题的分析，我们发现，在当前的开发流程中，验证环节的滞后性是导致代码质量问题的一个不可忽视的重要因素。
- ✅ 看了一大批线上问题，一个共同的毛病：验证做得太晚，代码质量就出问题。

## 密度快速判定

扫完一段，数命中数：

| 密度 | 判定 | 处置 |
|---|---|---|
| 0-2 处/段 | 局部小毛病 | 逐处替换即可 |
| 3-5 处/段 | 整段翻译腔 | 全段重写更省事 |
| >5 处/段 | 骨架全错 | 建议删整段(范围限句段时进删除清单；可动结构时直接重写) |
