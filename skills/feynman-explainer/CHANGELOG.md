## 0.2.4 — 2026-11-05

- 精确流程／时序／工程图交 engineering-docs 的Archify桥接，不在画板里从零摆节点。
- 用户需要一页式讲解、源码导读时，可借图表、步骤定位和来源增强；研究与正文仍归本技能，不默认把普通回答变成网页。

## 0.2.3 — 2026-10-23

技术调研入口软加固：
- 精简 description，把仓库、源码、论文、提示词和技术机制调研前置；明确“调研一下，写个飞书文档”无需点名同样适用。
- 入口固定为读方法、取证讲透、成稿检查、写入发布；平台读取可用于取证，建骨架和文件搬运按原平台流程，不全面禁止先加载平台技能。
- 快答例外只覆盖无需调研的单点问题；不再用指令长度或预估篇幅排除技术调研。
- 成稿归属不取消研究环节；交接已有查证结果，避免费曼与分享技能循环调用。中文定稿显式执行好好说话。
- 保留费曼逻辑链、范例、画图能力和已有交付方式；这是软约束，静态检查不证明宿主自动召回，也不替代真实会话验证。

## 0.2.2 — 2026-10-22

召回修复（bad case：对内的 Ponytail/提示词调研成稿没走费曼，被 lark-doc 裸写）：
- 明确**任何技术调研，无论对内对外、无论弄懂还是落成文档，都先走费曼**；费曼可直接交付内部调研报告/机制解读/选型研判成稿，不再把“成稿”一律外推给 talk-smith。
- 与 talk-smith 的分界从“对内/对外”改为“要不要人味地传播”；§0 路由表、description、§5 交付形态同步。
- 新增防误触：研究对象是 GitHub 仓库/论文/提示词/Agent 实践也走费曼，不因主题涉及“技能”而调 skill-library-keeper。
- 明确 lark-doc 只承载成文，内容与调研骨架归费曼；成文过 haohao-shuohua 轻档。

## 0.2.0 — 2026-10-16

### 修复（对应原诊断 P1/P2）
- **P1 触发词覆盖过宽、无量化线**：开头可见区与 §0 新增"启用前第一道闸门"——三句话内能讲清、且用户没说「展开/讲透/为什么/帮我搞懂」→ 一句话快答，不启用；description 可见区同步写入该闸门。
