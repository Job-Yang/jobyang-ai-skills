# Feynman Explainer · 费曼讲透法

> **唯一目标**：能把一个东西讲到外行也能听懂，才算真懂。
> 这个技能强制用费曼技巧组织「总结 / 调研 / 解读」类输出，杜绝「术语糊弄、看着懂实则没懂」。
## 入口

技术调研请求即使只有一句话，也先读取本技能（需要校准文风与比喻密度时按需翻 `references/style-examples.md`），再开始检索与分析。不要要求用户点名费曼，不用“三句话能答完”排除一项调研任务。

执行顺序：

1. **读方法**：读取本技能，明确要解释的问题、证据范围和成稿归属（需要样本校准时按需看 `references/style-examples.md`）；不把工作清单印进正文。
2. **取证讲透**：按 §4 获取原文与必要运行证据，区分已查证、作者自述、推测和未知，再用费曼逻辑链解释机制。
3. **成稿检查**：普通调研由本技能独立成稿时，中文定稿显式读取并执行 `haohao-shuohua` 核对事实与表达；被 `talk-smith`、`cuihuo`、`engineering-docs` 或 `tangshan-style` 作为前置调研阶段调用时，只交核实结论与机制骨架，不在此环节调用 `haohao-shuohua`，由最终成稿技能统一收尾。
4. **写入发布**：用 `lark-doc` 等发布载体技能写入已检查的内容。读取原文可在取证阶段调用平台技能；用户明确要建文档骨架、复制或整理已有文件时，也可直接按平台流程操作。

“飞书文档”说明交付到哪里，不决定内容怎么写。不因平台技能已加载就省去内容方法；这些顺序约束是本技能的软加固，不是宿主强制拦截，也不保证自动召回。

快答仅适用于无需调研的单点定义、事实或明确要求不展开的问题。技术调研指令短，不代表任务简单。

> **两条铁律**：① **逻辑链，不是要点清单**——节与节首尾因果咬合，拒绝「要点 1/2/3」平铺；节内真并列内容照常列表或表格，一段 ≤ 150 字、不写大段堆砌。② **脚手架要拆**——「费曼比喻 / 难理解点在哪 / 要点 X / 【P0】」只是内部构思工具，成稿只留融进句子的自然行文（见 §1、§2）。

## 0. 触发判断

**先分调研和快答**：技术调研、源码解读、论文或机制研究先读本技能。只有无需调研的单点定义、事实或明确要求不展开的问题，才走快答；不要用预估篇幅排除调研。

| 场景 | 承接 | 说明 |
|------|------|------|
| 「调研一下这个 GitHub 仓库，看看有什么好东西」 | 本技能 | 先读方法，再取证分析；不要求点名 |
| 「调研一下，写个飞书文档」 | 本技能 + 平台技能 | 本技能负责研究与内容，平台负责写入 |
| 「总结一下这篇复杂文档/论文/方案」 | 本技能 | 解释关键机制与证据关系 |
| 「调研一下 XX 技术/产品/概念」 | 本技能 | 对内对外都接 |
| 「讲透 / 讲明白 / 帮我搞懂 XX」 | 本技能 | 只展开必要的内容 |
| 解读源码 / 黑盒机制 / 硬核技术 | 本技能 | 不凭简介替代源码或机制证据 |
| 「一句话告诉我 XX 是啥」「简单说就行，别展开」 | 直接回答 | 用户只要单点快答时不启动研究流程 |
| 无需调研的单点定义或事实 | 直接回答 | 快答例外不覆盖技术调研 |
| 纯创作 / 翻译 / 润色 / 文件搬运 | 对应技能 | 不以主题里的技术词触发调研 |
| 内部调研报告 / 机制解读 / 选型研判成稿 | 本技能 | 直接完成研究与成稿 |
| 讲给别人听的分享文 / talk / slides（个人工程实践、经验传播、项目复盘、博客演讲叙事，普通研究报告不算） | `talk-smith` 成稿 | 其中技术调研先用费曼；交接已有研究结果，避免循环调用 |
| 可被反驳的观点硬文 | `cuihuo` 成稿 | 其中技术调研先用费曼 |
| 需要评审拍板的内部技术方案/RFC/ADR | `engineering-docs` 成稿 | 其中技术调研先用费曼；不因成稿归它而跳过研究 |
| 面向未来的技术想象 / 极端外推畅想 | `tangshan-style` 成稿 | 不将想象当作查证结果 |
| 拆解单个优秀成品、提炼可复用规律与清单 | `reverse-teardown` | 对象是学习具体成品选了什么解法，而非搞懂技术原理 |
| 为重大决策做多源外部取证与冲突裁决 | `outside-view` | 纯外部行业共识、反例与可信度取证 |

拿不准文体时，结合用户目标和已有材料判断；只有会改变范围或主要结论的歧义才追问，不要求用户选择内部技能。
> **多轮重判**：以最新任务为准——前一轮是快答不锁定后一轮，用户接着说"写成报告/整理成文档/讲清楚这个机制"就正常展开成文，不因输入短或前面是快答而排除。
>
> ⚠️ **和输出型技能的分工**：费曼是**调研与讲透的事实源**——任何技术调研（对内、对外）都先过费曼。
> 费曼可以**自己交付研究报告、机制解读、选型研判**（对内对外都接，哪怕对外发布、面向读者）；需要把研究结果做成**讲给别人听的技术分享、个人工程实践/经验传播、博客或演讲叙事**时，把研究结果交给 `talk-smith` 成稿。已有查证结果直接复用，只有新的研究缺口才补取证，避免循环调用。
> 分界不是"发不发出去/对不对外"（公开研究本来就面向读者），而是这篇是不是"讲给读者听的技术分享/经验叙事"；幽默口语只是执行风格。普通调研稿由费曼直接写到底。扎观点→`cuihuo`，评审方案→`engineering-docs`，畅想→`tangshan-style`，成稿归属不取消其中的技术调研环节。
>
> 📌 **调研主题是“提示词 / Agent / 技能 / 某个 GitHub 仓库怎么写的”也照样走费曼**：判断标准是“你在调研一个外部实践并想搞懂它”，不是看主题词。不要因为内容跟技能有关就去调 `skill-library-keeper`——那是管理/优化“你自己这套技能集合”时才用的元技能，不是调研外部资料的方法论。

## 1. 费曼五步（构思顺序，不作排版标签）

这五步是串起来的推进链，成品里不印这些步骤名，只体现它们的效果：

1. **先按读者水位立问题，以高分辨率机理撑满篇幅**：面向非同行/初学者时，开头用大白话说清「解决什么问题 / 哪里反直觉」再引术语；面向懂基础开发的工程师/同行时，直接以他熟悉的底层基元（如 OS 虚拟内存/页表、`fork()` 写时复制、Cache、调度与并发原语）做锚——减少生活比喻绝非写成干瘪抽象的要点提纲，而是沿着「瓶颈如何产生 → 核心解耦机制 → 底层算子/运行时如何落地与真实代价」写透完整工程闭环。
2. **顺着问题往下追**：每一节接住上一节的疑问（「那为什么不行 / 于是怎么解」），不平起平坐列词条。
3. **正面点破难点**：硬核转折处在正文中直接点破新手误区，紧跟真实机制（不套「你以为 X，其实是 Y」翻案壳）。
4. **30 秒可复述自检**：心里检查外行能否听懂，不在成稿中留「费曼检验：……」字幕。
5. **链式收口**：结尾用一两句话把整条链复述一遍；内容确实复杂时才补一张自然总览表。

## 2. 输出结构：逻辑链为主轴、节内按需列表

### 2.1 节间因果与节内版面

**费曼讲透 =「问题 → 朴素做法为何不够 → 真实机制 → 代价/新麻烦 → 收口」的因果推导链。** 相邻两节间能自然用「于是 / 但问题是 / 所以」接上（若任意抽掉一节后面仍不受影响，说明写成了并列清单，需重新串链）。节内则按内容形状排版：

| 节内内容 | 怎么写 |
| --- | --- |
| 本节结论 | 长文（> 1200 字）或面向初学者科普时，可选在节首加粗一句点明结论（每段 ≤ 1 处）；`600–900` 字工程师向讲解可直接进机制展开，不必每节硬贴独立加粗总结句 |
| 推理、机制运作、融进句中的类比 | 短段落，一段 ≤ 150 字、一段一事 |
| 真并列的形态、方案、参数、对比 | 列表或表格（≥3 项 × ≥2 维度用表格），列完用一句话接回主链 |
| 读者最容易误解的点 | 单独成段或 `>` 引用块点破 |
| 勾出下一节的疑问 | 可选（长文帮助抓线；`600–900` 字工程师向讲解靠因果推进自然咬合即可，不硬补每节结尾悬念问句） |

### 2.2 反面模式与拆脚手架

| 要避免的写法 | 正确做法 |
| --- | --- |
| 「要点 1/2/3」或「特点 1.2.3.」平铺、把「先问/于是」直接当小标题 | 用有信息量的小标题（如「泄露与劫持：同一个漏洞的两张脸」）并用因果流串联 |
| 外露 `💭 费曼比喻：`、`🤔 难理解点在哪？`、`【P0】`、`费曼检验：` | 类比按读者水位克制融进句子，难易靠篇幅轻重体现，不挂牌子 |

```text
【开场 1~2 段】直立真问题与读者已知锚点（总比喻与悬念问句仅面向初学者可选；工程师受众可直接从工程现象与共享底层基元切入）
【主线 · N 节串联】## <有信息量小标题> → 机制与因果展开 / 必要列表或表格（节首加粗结论与节末过渡句仅长文按需选用）
【收口】1~2 句复述整条链（仅足够复杂时补一张总览表）
```

## 3. 风格约束

> **独立成稿后调用 `haohao-shuohua` 标准档做清洗；被 `talk-smith`、`cuihuo`、`engineering-docs` 或 `tangshan-style` 作为前置调研阶段调用时，只交核实结论与机制骨架（面向工程同行的写作下游可跳过 `references/style-examples.md` 里的基础生活比喻示例），不在此环节调用 `haohao-shuohua`，由最终成稿技能统一收尾**（唯一主责协议：本技能保留逻辑链骨架、节间因果关节词与对比图表，下游只去 AI 味、坏动词与真翻案壳，不将逻辑链改成纯目录、不删正当类比）。
> **正当类比与坏比喻分界**：按 `haohao-shuohua/references/verb-metaphor-gate.md` 保留有助理解机制的清晰类比，清理混搭串线/空心装深刻/以喻代机制的坏比喻。

### 3.1 读者水位、机制与类比节制
- **去 AI 腔与按水位讲术语**：像懂行的朋友面对面掰扯明白；仅对陌生跨界术语用一句大白话定位它干嘛用（读者已掌握的工程术语直接用）；短句优先，纯段落不连排超过 3 段，版式底线见 `haohao-shuohua/references/reader-layout.md`。
- **高分辨率机制写透在前，类比按读者需要克制使用**：核心机制用准确工程事实与运行链路写透（数据流、状态转移、复杂度、硬件/内存/底层算子或 Kernel 调度实景，并善用标明为举例的典型工程量级，如「如 `4096` 上限」「如每块 `16` token」）；面向初学者可配 `1–2` 处贴合日常的生活类比搭桥；**面向懂基础开发的工程师同行，全篇 `0–1` 处同构系统类比即可（减掉生活比喻后用更高工程精度补足篇幅，避免写成干瘪抽象的要点清单）**。
- **诚实与边界**：黑盒、未查到直接说明不编造；区分确证事实与合理推测；引用外部资料用 `[标题](url)`。

### 3.2 可视化：按需画关系图

**判据：关系一句话能说清就跳过；靠文字绕几句才理顺才画图。** 图需体现推进方向并紧贴所解释的段落。

| 场景 | 画什么 |
|---|---|
| ≥3 项 × ≥2 维度的多方对比 | 对比表格 |
| 流程 / 时序 / 多路径并列（机制传播类） | 可选交 `content-infographic`（默认确定性渲染器排多标签/术语，少数标签场景图走文生图），并传原段落与过渡句做图文对账 |
| 精确工程架构 / 时序或一页式 Explainer | 仅可选借用 `engineering-docs` 的 `diagram_kit render` 脚本或 Explainer 阅读器（只借图与阅读器、不走 `engineering-docs` 文档流程，普通回答不改网页） |
| 单一定义、单点事实或纯粹装饰图 | 跳过，直接文字讲清 |

> 配图工具属可选增强：缺失时不阻塞，可用文字或简明示意把关系讲透并告知用户。

## 4. 调研类任务前置动作

任务是「调研 XX」时先读方法再取料：**区分信息源**（内部用环境检索，公网搜+抓原文交叉验证，文档/PDF 读全文）→ **并行检索** → **有限重试**（同一关键来源连续受阻换至多 `2` 种路径，仍拿不到即停并如实标「黑盒 / 未查到」，不硬猜或拿二手摘要充源码）→ **先在心里串出逻辑链再成稿**，不把原始检索流水账直接甩给用户。

## 5. 交付形态与篇幅

| 情况 | 交付方式 |
|---|---|
| 默认 | 对话内直接用费曼逻辑链回答 |
| 用户要文档（含内部调研报告） | 本技能负责全部内容与结构；需要写入飞书文档时可选交 `lark-doc` 承载（不决定调研骨架，缺失平台工具时直接输出完整 Markdown）；独立成稿后过 `haohao-shuohua` 标准档去 AI 味 |
| 长内容（>5 环节 / 预计 >1500 字）| 先给 3–5 行逻辑链骨架对齐范围再补全正文 |

建议篇幅 **600–1500 字**（简单主题 2–3 节 600–900 字，硬核主题 5–9 节 1200–1500 字；用户明要长文不受此限，仍先对齐骨架再补全）。

## 6. 交付前自检清单

- [ ] 调研开始前已读取本技能（未因指令短或平台技能已加载跳过内容方法）；独立成稿与平台写入分离，且独立中文定稿已过 `haohao-shuohua`
- [ ] 全文是一条首尾咬合的逻辑链（非「要点 1/2/3」平铺，无 `💭 费曼比喻：` / `🤔 难理解点在哪？` / `【P0】` 等外露脚手架）
- [ ] 开场立住真问题与读者已知锚点，核心转折先用工程事实讲透机制；生活类比仅在真能降低理解成本时克制使用（工程师受众可 `0–1` 处，不硬凑比喻；已知黑盒/推测处如实标注，无编造）
- [ ] 单段 ≤ 150 字、纯段连排 ≤ 3 段，真并列内容已上表格或列表（安装有 `haohao-shuohua` 可跑 `quick_scan.py 稿子 --checks wall`）
- [ ] 结尾用一两句复述整条链
